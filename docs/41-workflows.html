Chapter 41

A workflow or an agent?

Some requests need a model to decide each step. Many do not. How do you tell them apart, and what does a wrong choice cost?

An agent decides its own path: which tool to call, in what order, and when to stop. That freedom is what the loop of chapter 15 buys. It is paid for on every request, in model passes, in time, and in the chance that one of those passes goes wrong. Many requests do not need the freedom. Their path is the same every time, and plain code can follow it.

Definitions

A workflow is a path fixed in code. It may call a model at fixed places, for example to read a request or to write a plan, but the code decides what happens next.

Routing sends each request down one of several paths, chosen by a rule or a small model that looks at the request first.

Chapter 39 already built one workflow without naming it. "Plan, then code" calls the model once to write the plan, and from then on code runs every step. The model fills in one box of a path that does not change. "Step by step" is an agent: after each result, the model decides what comes next.

By hand: one request, four ways

Take what is 23 tims 45?, with a slip in it.

  • Code only. A parser written by hand expects what is <n> plus|minus|times <n> …?. tims is none of the three words, so the parser fails and the service says it cannot help. No model was used.
  • Plan, then code. The model writes a plan in one pass, whatever the wording, and code runs it. Whether the answer is right depends on whether the model read tims as times.
  • Agent. The model writes a call, reads the result, then answers: two passes for one sum.
  • Route. The parser tries first. It fails, so the request goes to the agent. For what is 23 times 45? the parser would have succeeded, and no model would have run.

300 requests, four ways

code/ch41_workflow.py serves one mix of 300 requests, with number pairs no model saw in training: 150 single sums worded as usual, 90 chains of two to four links, and 60 single sums with a slip in the operation word, the slips of chapter 43. The model is the agent of chapter 39.

def code_only(q):
    """A hand-written parser: the expected shape, or nothing. Returns (answer or None, model passes)."""
    m = SHAPE.match(q)
    if not m:
        return None, 0                                     # "sorry, i only understand sums"
    v, rest = int(m.group(1)), m.group(2).split()
    for op, n in zip(rest[::2], rest[1::2]):
        v = w.TOOLS[w.WORDS[op]](v, int(n))                # the code does the work itself
    return v, 0

def agent(run, q):
    got, calls, _ = w.run_steps(run, '\nU ' + q + '\n')
    return got, len(calls) + 1

def plan_then_code(run, q):
    got, _, _ = w.run_plan(run, '\nU ' + q + '\n')
    return got, 1

def route(run, q):
    """The parser first; only what it cannot read goes to the agent."""
    got, passes = code_only(q)
    return (got, passes) if SHAPE.match(q) else agent(run, q)

Times measured on the laptop-class machine that ran the script. The parser takes microseconds; a pass of our small model takes milliseconds; a pass of a large model takes from a fraction of a second to many seconds.

  • Code alone was right on every request it could read: all 240, with no model and in microseconds. The 60 slips got nothing.
  • The workflow and the agent were equally right: 266 and 265. Both answered all 240 ordinary requests and about 26 of the 60 slips. But the agent took 2.65 passes and 23 ms per request, the workflow 1 pass and 16 ms. On these requests the agent's freedom bought nothing, because every step was known from the words.
  • The route matched the agent's 265 with 0.45 passes per request and a fifth of its time, because 240 of the 300 requests never reached the model.
  • No way did well on slips: under half. That is the model's limit here, words it never saw (chapter 43), whichever way it is called.

Which one, when

The table turns into four questions to ask about any job before building an agent for it.

Our chains do not need an agent. Their steps are all known in advance from the words. An agent is needed when the next step depends on a result: search, read what came back, decide where to look next. Chapter 39 discusses that limit of a plan.

Four ways, on your own request

Try this. Pick a kind of request and serve it all four ways. Then write one with a slip of your own, and one the parser can read, and compare the model passes.

What you should have seen. A single sum or a chain is answered by the parser with no model pass, and the route does the same. The agent takes one pass per call plus one, and the workflow one pass in all. Slips are where the model is needed, and where it is unreliable. what is 79 tims 4? was read as times and answered right. what is 65 take away 59? was read as times too. what is 22 x 27? sent the agent into four calls of its own invention, five passes for a wrong answer.

At full size

  • Start with the simplest thing that works. Builders of large agents give the same advice: a single model call with good context first, then a fixed workflow, and an agent only when the steps cannot be written down in advance.
  • The common workflows have names. A chain of model calls, each one working on the output of the last. Routing to specialised paths. Running independent parts in parallel and joining the results (chapter 32). A model that writes and a second one that checks, in a loop with a fixed number of rounds (chapter 25).
  • The costs scale. A large model pass costs money and seconds where ours cost a few milliseconds. An agent that takes 20 passes for a job that one workflow pass could do is 20 times slower and dearer.
  • Agents earn their cost on open tasks. Fixing a bug, researching a question, working through a website: the number of steps is unknown and each step depends on what the last one found. There the loop is the only thing that works.
  • A router is usually a classifier. At full size the first stop is rarely a hand-written parser. It is a small model or a cheap call that labels the request, like the guard of chapter 28.

What this chapter glossed over

The parser is generous to code. Our requests come in one grammar, and a regular expression covers it exactly. Real requests are rarely that tidy. The "code only" column is what code gets when the shape is known.

The slips are few and invented. 60 requests, with the misspellings and synonyms of chapter 43.

Time is measured on one machine, for a model of a few hundred thousand weights. The ratios between ways matter more than the milliseconds.

One run, no sampling. The model chose its most likely character at every step.

In short

  • A workflow is a path fixed in code, with model calls at fixed places. An agent chooses its own path, one pass after another.
  • On 300 requests whose steps were all known from the words, the agent was no more accurate than a one-pass workflow (265 against 266) and took 2.65 passes against 1.
  • Code alone was right on all 240 requests it could read, and free.
  • Routing gave the agent's accuracy for 0.45 passes per request: code for the many, the model for the odd ones.
  • Use an agent when the next step depends on a result. Until then, a workflow is cheaper and as good.

Check yourself

"Plan, then code" calls the model. Why is it a workflow and not an agent?

Because the model is called once, at a fixed place, and code decides everything after that. An agent is called again after each result and decides what comes next.

90% of a service's requests have a fixed shape. What does routing them to code save, compared with sending everything to an agent?

Every model pass for those 90%: their cost, their time and their mistakes. Only the 10% the parser cannot read pay for the model.

Name a task where a plan cannot be written before the first step.

Any task where the next step depends on a result: searching and reading until something is found, debugging until a test passes, following links. The number and order of steps are not known in advance, so a loop has to decide them.

A route sends a request to code, and the code answers it wrongly. How could that happen?

The parser accepted a request it misread: its rule matched, but the meaning was different from what the rule assumed. A router is only as good as its test of what it can handle.
