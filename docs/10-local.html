How a text predictor becomes a chat

One piece is new. The model still does only what chapter 1 said: it continues text. It has no notion of "you" and "me". So where does a conversation come from?

From formatting. During fine-tuning, the makers of a chat model showed it a great many conversations written out as one long document, with special tokens (chapter 2) marking where each speaker starts and stops. The model learned what such documents look like. To chat with it, the server writes your messages into that same document format, ends it at the point where the assistant is about to speak, and lets the model continue. When the model produces the end-of-turn token, the server stops and hands you the text.

What the model actually receives

Try this. Edit the messages and switch between model families. The blue pieces are special tokens. Tick the second turn and notice that the entire conversation is sent again: the model keeps no memory between calls.

Each model family has its own format, called its chat template, and it is stored inside the model file so the server can apply it for you. If the wrong template is used, the model still produces text, because it always can. It just produces worse text, since the document no longer looks like the ones it was trained on. When a local model behaves strangely, this is one of the first things to check.

Do it

The quickest route is Ollama, a free program that bundles a runtime with a server and a model downloader. Pick a model whose size fits your memory by the arithmetic of chapter 9.

# 1. Install Ollama from ollama.com, then download a model and talk to it:
ollama pull qwen3:8b        # about 5 GB; pick any model that fits your RAM
ollama run qwen3:8b

# 2. Talk to the same model from this repository, with no extra libraries:
python code/ch10_chat.py

Model names change every few months. Browse the library on ollama.com for a current one; the arithmetic for choosing a size does not change.

If you would rather use llama.cpp directly, its llama-server program does the same job and listens on port 8080; LM Studio offers a graphical interface and listens on port 1234. All three speak the same HTTP dialect, so the code below works with each. Tell it where to look:

export MICROAI_BASE_URL=http://localhost:8080/v1    # llama-server
export MICROAI_BASE_URL=http://localhost:1234/v1    # LM Studio
# default, if unset: http://localhost:11434/v1       (Ollama)

Build it

def _post(path, payload, stream=False):
    req = urllib.request.Request(BASE_URL + path, data=json.dumps(payload).encode(),
                                 headers={'Content-Type': 'application/json', 'Authorization': 'Bearer local'})
    resp = urllib.request.urlopen(req, timeout=600)
    return resp if stream else json.loads(resp.read())

def default_model():
    if os.environ.get('MICROAI_MODEL'):
        return os.environ['MICROAI_MODEL']
    with urllib.request.urlopen(BASE_URL + '/models', timeout=10) as r:
        return json.loads(r.read())['data'][0]['id']       # whatever is installed

def chat(messages, tools=None, model=None, **options):
    """Send the whole conversation, get back the assistant's next message (a dict)."""
    payload = {'model': model or default_model(), 'messages': messages, **options}
    if tools:
        payload['tools'] = tools
    return _post('/chat/completions', payload)['choices'][0]['message']

def stream(messages, model=None, **options):
    """Same, but yield the text piece by piece as the model samples it."""
    payload = {'model': model or default_model(), 'messages': messages, 'stream': True, **options}
    for line in _post('/chat/completions', payload, stream=True):
        line = line.decode().strip()
        if line.startswith('data: ') and line != 'data: [DONE]':
            delta = json.loads(line[6:])['choices'][0]['delta']
            if delta.get('content'):
                yield delta['content']

From code/llm.py. A complete client: send the list of messages as JSON, read the reply.

def main():
    print(f'model: {default_model()} at {BASE_URL}   (ctrl-c to quit)')
    messages = [{'role': 'system', 'content': 'You are a concise, helpful assistant.'}]
    while True:
        try:
            user = input('\nyou> ')
        except (EOFError, KeyboardInterrupt):
            break
        messages.append({'role': 'user', 'content': user})
        reply = ''
        for piece in stream(messages, temperature=0.7):   # tokens arrive as they are sampled
            reply += piece
            print(piece, end='', flush=True)
        print()
        # The server keeps no memory. The "conversation" exists only because
        # we send the whole transcript again on every turn.
        messages.append({'role': 'assistant', 'content': reply})

When it misbehaves

  • Slow. Compare your tokens per second with the ceiling from chapter 9. Far below it usually means the model is not using the graphics processor, or it does not fit and the system is swapping memory to disk.
  • Forgets the start of long conversations. Servers often load a model with a smaller context window than it supports, to save memory. Look for the context-length setting (Ollama calls it num_ctx).
  • Rambling or odd formatting. Suspect the chat template or an extreme temperature.

What this chapter glossed over

How these scripts were tested. They were written against the API that Ollama documents as its OpenAI-compatible endpoint, and run end to end against the small fake server in code/mock_server.py. If a real server on your machine disagrees, the server is right; the fix will be a line or two in llm.py.

"Local" means on your machine. The address localhost never leaves your computer. Your prompts go nowhere else unless a program you add sends them. Some of these tools also offer cloud-hosted models under the same commands, so check which model you are actually running.

Small is not the same as weak, or as strong. A model that fits a laptop is far smaller than a frontier model and will make more mistakes on hard reasoning. For many bounded tasks it is plenty. The only reliable way to know is to test it on your own task.

Check yourself

Where does the "memory" of a chat live?

In the messages list held by your program. The server receives the full transcript on every turn. Its KV cache may make this cheap when the beginning is unchanged, but that is an optimisation, not memory.

What makes the model stop talking?

It samples the end-of-turn special token, and the server stops the loop. If that token were never produced, generation would continue until a length limit.

A 16 GB laptop, and you want an 8-billion-weight model with an 8,192-token context. Which format?

Q4_K_M is about 4.9 GB plus roughly 1 GB of cache: comfortable. Q8_0 at 8.5 GB plus cache would still fit, at about 60% of the speed. F16 at 16 GB will not.
