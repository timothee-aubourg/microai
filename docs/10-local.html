Chapter 10

A real model on your machine

You download one file, type one command, and a capable assistant answers with the network cable unplugged. What is in the file, and what is the program doing with it?

Nothing you have not already built. Chapters 1 to 9 covered every moving part. A real model on your own computer has the same parts at a larger size, written in faster code. This chapter lines them up, and then you run one.

Four pieces of software are involved, and their names come up in every guide, so here they are once.

Definitions

The model file holds everything the model is: its weights, its vocabulary, its sizes. The common format for personal computers is called GGUF, and such files end in .gguf.

The runtime is the program that does the arithmetic: it loads the file and runs the forward pass, the KV cache and the sampling of chapters 6 and 8.

A server is a program that keeps the model loaded and waits for requests. A client is a program that sends it a request and reads the answer. Your own code is a client.

An API is the agreed form of those requests and answers. Here it is a list of messages sent as text in a format called JSON.

How a text predictor becomes a chat

One piece is new. The model still does only what chapter 1 said: it continues text. It has no notion of "you" and "me". So where does a conversation come from?

From formatting. After its first training, the makers of a chat model trained it further on a great many conversations, each written out as one long document. Chapter 12 does this kind of further training, and chapter 24 looks at it closely. In those documents, special tokens mark where each speaker starts and stops.

Definitions

A special token is a token added to the vocabulary to carry structure and no text, such as "a speaker's turn ends here". Chapter 2 met one.

A role says who a message is from. There are three: system for the instructions given by whoever set the assistant up, user for the person, assistant for the model.

A chat template is the rule that writes a list of messages into the one document the model was trained to continue.

By hand: two messages become one document

Your program sends two messages:

RoleText
systemYou are a concise assistant.
userWhat is the capital of France?

With the template used by many open models, the server writes them out like this. Each <|im_start|> and <|im_end|> is one special token:

<|im_start|>system
You are a concise assistant.<|im_end|>
<|im_start|>user
What is the capital of France?<|im_end|>
<|im_start|>assistant

The document stops just after the word assistant. The model does what it always does: it continues the text. In the documents it was trained on, what follows at this point is an assistant's answer, so it writes one. When it produces <|im_end|>, the server stops the loop of chapter 8 and hands your program the text. The model never knew it was in a conversation.

What the model actually receives

Try this. The box shows the by-hand document. The blue pieces are special tokens. Tick the second turn and read the document again. Then switch between the three model families. Edit the messages if you like.

What you should have seen. The first document has 5 special tokens and ends where the assistant is about to speak. With the second turn ticked it has 9, and it contains everything again: the instruction, the first question, the answer Paris., and the new question. The whole conversation is sent on every turn, because the model keeps nothing between calls. The other families write the same conversation with other tokens: 15 of them in the Llama 3 style, 8 in the Gemma style, which has no separate system role and puts the instruction at the start of the first user turn.

Each model family has its own chat template, and it is stored inside the model file so the server can apply it for you. If the wrong template is used, the model still produces text, because it always can. It just produces worse text, since the document no longer looks like the ones it was trained on. When a local model behaves strangely, this is one of the first things to check.

Do it

The quickest route is Ollama, a free program that contains a runtime, a server and a tool to download model files. Pick a model whose size fits your memory by the arithmetic of chapter 9.

# 1. Install Ollama from ollama.com, then download a model and talk to it:
ollama pull qwen3:8b        # about 5 GB; pick any model that fits your RAM
ollama run qwen3:8b

# 2. Talk to the same model from this repository, with no extra libraries:
python code/ch10_chat.py

Model names change every few months. Browse the library on ollama.com for a current one; the arithmetic for choosing a size does not change.

If you would rather use llama.cpp directly, its llama-server program does the same job and listens on port 8080; LM Studio offers a graphical interface and listens on port 1234. All three accept the same form of request, so the code below works with each. The address localhost means "this computer", and the number after the colon, the port, says which program on it. Tell the code where to look:

export MICROAI_BASE_URL=http://localhost:8080/v1    # llama-server
export MICROAI_BASE_URL=http://localhost:1234/v1    # LM Studio
# default, if unset: http://localhost:11434/v1       (Ollama)

Build it

def _post(path, payload, stream=False):
    req = urllib.request.Request(BASE_URL + path, data=json.dumps(payload).encode(),
                                 headers={'Content-Type': 'application/json', 'Authorization': 'Bearer local'})
    resp = urllib.request.urlopen(req, timeout=600)
    return resp if stream else json.loads(resp.read())

def default_model():
    if os.environ.get('MICROAI_MODEL'):
        return os.environ['MICROAI_MODEL']
    with urllib.request.urlopen(BASE_URL + '/models', timeout=10) as r:
        return json.loads(r.read())['data'][0]['id']       # whatever is installed

def chat(messages, tools=None, model=None, **options):
    """Send the whole conversation, get back the assistant's next message (a dict)."""
    payload = {'model': model or default_model(), 'messages': messages, **options}
    if tools:
        payload['tools'] = tools
    return _post('/chat/completions', payload)['choices'][0]['message']

def stream(messages, model=None, **options):
    """Same, but yield the text piece by piece as the model samples it."""
    payload = {'model': model or default_model(), 'messages': messages, 'stream': True, **options}
    for line in _post('/chat/completions', payload, stream=True):
        line = line.decode().strip()
        if line.startswith('data: ') and line != 'data: [DONE]':
            delta = json.loads(line[6:])['choices'][0]['delta']
            if delta.get('content'):
                yield delta['content']

From code/llm.py. A complete client: send the list of messages as JSON, read the reply. chat waits for the whole reply; stream hands it over piece by piece as the model writes it.

def main():
    print(f'model: {default_model()} at {BASE_URL}   (ctrl-c to quit)')
    messages = [{'role': 'system', 'content': 'You are a concise, helpful assistant.'}]
    while True:
        try:
            user = input('\nyou> ')
        except (EOFError, KeyboardInterrupt):
            break
        messages.append({'role': 'user', 'content': user})
        reply = ''
        for piece in stream(messages, temperature=0.7):   # tokens arrive as they are sampled
            reply += piece
            print(piece, end='', flush=True)
        print()
        # The server keeps no memory. The "conversation" exists only because
        # we send the whole transcript again on every turn.
        messages.append({'role': 'assistant', 'content': reply})

When it misbehaves

  • Slow. Compare your tokens per second with the ceiling from chapter 9. Far below it usually means the model is not using the graphics processor, or it does not fit and the system is swapping memory to disk.
  • Forgets the start of long conversations. Servers often load a model with a smaller context window than it supports, to save memory. Look for the context-length setting (Ollama calls it num_ctx).
  • Rambling or odd formatting. Suspect the chat template or an extreme temperature.

What this chapter glossed over

How these scripts were tested. They were written against the form of request that Ollama documents as compatible with OpenAI's, and run end to end against the small fake server in code/mock_server.py. If a real server on your machine disagrees, the server is right; the fix will be a line or two in llm.py.

"Local" means on your machine. The address localhost never leaves your computer. Your prompts go nowhere else unless a program you add sends them. Some of these tools also offer cloud-hosted models under the same commands, so check which model you are actually running.

Small is not the same as weak, or as strong. A model that fits a laptop is far smaller than the largest models and will make more mistakes on hard problems. For many bounded tasks it is plenty. The only reliable way to know is to test it on your own task.

In short

  • A model on your computer is four layers: your program, a server, a runtime, and a model file. Each is a larger version of something chapters 1 to 9 built.
  • A chat model only continues text. A chat template writes the messages into one document, with special tokens between the speakers, that stops where the assistant is about to speak.
  • The whole conversation is sent on every turn. The memory of a chat is the list of messages in your program.
  • The reply ends when the model writes the token that ends a turn.
  • A complete client is about thirty lines: send the messages as JSON, read the reply.

Check yourself

Write the document the server would send for a single user message, Hi, with no system message, in the template of the by-hand example.

<|im_start|>user, a line break, Hi<|im_end|>, a line break, then <|im_start|>assistant and a line break. Three special tokens, and the document stops where the assistant is about to speak.

Where does the "memory" of a chat live?

In the messages list held by your program. The server receives the full transcript on every turn. Its KV cache may make this cheap when the beginning is unchanged, but that saves work. It is not memory.

What makes the model stop talking?

It writes the special token that ends a turn, and the server stops the loop. If that token were never produced, generation would continue until a length limit.

A 16 GB laptop, and you want an 8-billion-weight model with an 8,192-token context. Which format?

Q4_K_M is about 4.9 GB plus roughly 1 GB of cache: comfortable. Q8_0 at 8.5 GB plus cache would still fit, at about 60% of the speed. F16 at 16 GB will not.
