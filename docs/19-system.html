Chapter 19

Build the whole thing

Can you build every part yourself, from random numbers to an agent that uses a tool, on a laptop, in one sitting?

Yes. This chapter is one file, code/ch19_system.py, that bolts together the engines of the earlier chapters. It writes its own training data, trains a model of 108,032 weights on your CPU in about five minutes, and runs that model inside a harness with three tools. The result is a very small assistant that answers questions like "what is 23 times 45?" by asking a calculator.

It is limited on purpose, and it is complete. Every part that a large system has is here in a form you can read in one evening, and the model below is running in your browser now.

The format is the design

The model was trained on conversations that look like this:

U what is 23 times 45?        the user
C mul 23 45                   the model asks for a tool
R 1035                        the harness answers
A 23 times 45 is 1035.        the model reports

Each line starts with a letter that says who is speaking. That is this system's chat template, and the model learned it the only way a model learns anything: by predicting the next character of thousands of examples. Nobody programmed "when you see a sum, write C". It is the likeliest continuation of the text it was shown.

This is what "a model trained for tool calling" means at any size. The training data contains requests in an agreed layout at the moments where a tool helps. Note what the model does not learn: arithmetic. The line beginning with R was never its to write. During training it only saw results appear. In use, the harness writes that line.

Where the weights come from

A question that comes up: could a large model simply write out the weights of a small one? Not usefully. The weights of even this model are 108,032 numbers whose values only make sense together, and nobody, person or model, can write them down by thinking. They are found by training.

What can be written is the program that finds them, and it is short. The training function in this chapter is twenty-five lines. Run it and five minutes later you hold a file of weights that works on any computer with Python, and in a browser on a phone. The recipe is the product. The weights are what the recipe leaves behind.

What it learned, and what it did not

One pair of numbers in ten was kept out of the training data. The evaluation asks 200 questions using only those pairs.

On 200 questions with unseen number pairsCorrect
The tool call200 of 200
The call and the final answer200 of 200

So it did not memorise sums. It learned a procedure: copy the two numbers into a request, wait, copy the result into a sentence. A caution from chapter 14 applies even to a perfect score: the standard-error formula gives ± 0 here, which is wrong. Zero failures in 200 tries is compatible with a true failure rate of up to about 1.5%.

Step outside what it was shown and it breaks, confidently.

QuestionWhat it did
what is 123 plus 4?Called add 12 4 and answered "12 plus 4 is 16."
what is 5 plus 5 plus 5?Called add 5 5 and answered "5 plus 5 is 10."
what is the capital of france?Called sub 9 3 and answered "9 minus 3 is 6."

It has no way to say "I do not know", because no example ever showed it that sentence. It produces the nearest thing it has a shape for. This is the small, fully visible version of what is called hallucination in large models: fluent output in a learned form, with nothing behind it.

Make it yours

The file is meant to be changed. Each of these is under an hour, and each teaches the part it touches.

  1. Add a tool. Put 'max' in the tool table, add "what is the larger of 12 and 7?" to the generator, extend the call format, retrain.
  2. Teach it to decline. Add questions it cannot answer to the data, with the answer "i only know arithmetic." Retrain and ask about France again.
  3. Widen its world. Allow three-digit numbers. Watch how much more training it needs, and why the window had to grow.
  4. Remove the mask. Run the evaluation with free sampling at temperature 1 and count the calls that no longer parse.
  5. Shrink it. Round the weights to 8 bits, then 4 (chapter 9), and run the evaluation after each.
  6. Break it on purpose. Train for 300 steps and read the traces of the failures. Which part fails first: choosing the tool, copying a number, or the sentence?

Build it

def held_out(a, b):
    return (7 * a + b) % 10 == 0            # one pair of numbers in ten is never shown in training

def conversation(rng, test=False):
    if not test and rng.random() < 0.1:     # small talk: answer directly, no tool
        q, a = CHAT[rng.integers(len(CHAT))]
        return f'U {q}\nA {a}\n\n'
    while True:
        a, b = int(rng.integers(100)), int(rng.integers(100))
        if held_out(a, b) == test:
            break
    word = list(WORDS)[rng.integers(3)]
    result = TOOLS[WORDS[word]](a, b)
    return (f'U what is {a} {word} {b}?\n'      # the user asks
            f'C {WORDS[word]} {a} {b}\n'         # the model writes a request
            f'R {result}\n'                      # the harness runs it and writes the result
            f'A {a} {word} {b} is {result}.\n\n')   # the model reports

def write_line(run, cache, logits, fmt=None, limit=70, **sampling):
    """Let the model write up to the end of a line. With `fmt`, only characters the format allows."""
    line, state = '', START
    while not line.endswith('\n') and len(line) < limit and cache['pos'] < run.block:
        if fmt:
            legal = moves(fmt, state)
            if not legal:
                break                                     # the format is complete
            mask = np.full(run.vocab, -np.inf)
            mask[[run.stoi[c] for c in legal]] = 0
            logits = logits + mask
        c = run.chars[sample_next(logits, **sampling)]
        if fmt:
            state = legal[c]
        line += c
        logits = run.step(run.stoi[c], cache)             # one token through the model, cache kept
    return line, logits

def feed(run, cache, text):
    for c in text:
        logits = run.step(run.stoi[c], cache)
    return logits

def answer(run, question, tracer=None, **sampling):
    tracer = tracer or Tracer()
    with tracer.span('agent', 'answer', input=question) as root:
        cache = run.new_cache()
        logits = feed(run, cache, '\nU ' + question + '\n')           # the prompt
        with tracer.span('model', 'choose', input='C or A?') as s:    # does it want a tool, or to answer?
            role, logits = write_line(run, cache, logits, fmt=[['C ', 'A ']], **sampling)
            s['output'] = role
        if role == 'C ':
            with tracer.span('model', 'write call') as s:
                call, logits = write_line(run, cache, logits, fmt=CALL, **sampling)   # always parseable
                s['output'] = call
            name, a, b = call.split()
            with tracer.span('tool', name, input=[int(a), int(b)]) as s:
                s['output'] = TOOLS[name](int(a), int(b))                              # the harness acts
            logits = feed(run, cache, f"R {s['output']}\nA ")                         # the result becomes context
        with tracer.span('model', 'write answer') as s:
            text, logits = write_line(run, cache, logits, **sampling)
            s['output'] = text
        root['output'] = text.strip()
    return root['output'], tracer.spans

The harness: let the model choose between a tool and an answer, keep the request parseable with the mask of chapter 13, run the tool, hand back the result, let the model finish.

def evaluate(run, n=200, seed=1):
    rng = np.random.default_rng(seed)
    rows = []
    for _ in range(n):
        lines = conversation(rng, test=True).split('\n')
        question, want_call, want_answer = lines[0][2:], lines[1][2:], lines[3][2:]
        got, spans = answer(run, question, temperature=0)
        calls = [s['output'].strip() for s in spans if s['name'] == 'write call']
        rows.append({'q': question, 'call ok': calls == [want_call], 'answer ok': got == want_answer})
    p = sum(r['call ok'] and r['answer ok'] for r in rows) / n
    return rows, p, math.sqrt(p * (1 - p) / n)

What this chapter glossed over

Scale changes what is possible, not what is there. This model copies two numbers and fills a sentence. A large model does things no one can yet fully explain. The parts list is the same. What emerges from the model part is not.

The data is synthetic and tiny. Real models learn language first, from enormous text, and tool use afterwards, from far fewer examples. Here one small file teaches both, which only works because the "language" has a dozen sentences.

One turn, one tool call. A real conversation has many of each, and the harness loops until the model stops asking.

The tools are harmless. Three pure functions. The questions of chapter 17 begin when a tool can change something.

Training time varies. Five minutes was measured on the machine that built this page. A run with a different random seed can land slightly differently, so check yours with --eval.

Check yourself

The model answers "23 times 45 is 1035." It was never taught to multiply. Where did 1035 come from?

From the harness. The model wrote mul 23 45, the harness ran the function and wrote R 1035 into the context, and the model copied that number into its sentence. Attention pointing at a few earlier characters is all it needs.

Why does it call a tool for "what is the capital of france?"

After a line starting with "U what is", every training example continued with a tool call. That continuation is overwhelmingly likely, so it is produced, with whatever numbers the model finds most plausible. It was never shown an alternative.

You add a fourth tool to the table in the code and do not retrain. What happens when you ask for it?

Nothing useful. The harness could run it, but the model has never seen its name in a request and gives it almost no probability. A large model can read a new tool's description and use it at once, because it learned to follow descriptions in general. This one learned three names.

Which parts of this system would you have to change to move it from your CPU to a GPU, and which would stay as they are?

Only the arithmetic underneath: the matrix products of training and inference would be handed to a library that runs on the GPU. The data, the format, the mask, the harness, the tracing and the evaluation do not care where the multiply-adds happen.
