Chapter 11

Memory, books and hands

The model's weights are fixed, it has never seen your documents, it forgets everything between calls, and all it can do is write text. How do you build something useful out of that?

By accepting one limit and working inside it. While it runs, the model knows exactly two things: what training left in its weights, and what is written in its context window. Your program cannot change the weights. So everything a system does to make a model useful in your situation comes down to choosing what text to put in the window.

Remembering a conversation, searching documents and using tools sound like three features. They are one mechanism used three ways.

The window is a budget

Chapter 10 showed that a chat works by sending the whole conversation again on every turn. That conversation shares the window with everything else you want the model to know, and the window is finite. Chapter 9 showed that making it larger costs memory, and chapter 8 that reading it costs time.

What you should have seen. At 12 turns: 4,650 of 8,192 tokens. At 30 turns it still fits, with 842 to spare. At 40 turns it is over by 658, and at 60 turns by 3,658. A window of 32,768 tokens holds the 60 turns with 20,918 to spare, at the cost in memory that chapter 9 worked out.

When the budget is exceeded something must go, and whatever goes, the model no longer knows. Every assistant that seems to "remember" is managing this budget out of sight: cutting old turns, replacing them with a summary, or storing them outside the window and fetching back only what looks relevant. Chapter 16 measures these choices. That last idea, fetching what is relevant, is the next section.

An open book: retrieval

You have a folder of notes, far too large for the window. For any one question only a few passages matter. So find them first, and put only those in the window.

Definitions

Retrieval-augmented generation, RAG for short, is answering a question in two steps: search your documents for the passages that fit the question, then give the model those passages along with the question.

A chunk is one of the passages the documents are cut into, so that each can be found by itself.

The search needs nothing beyond chapter 4:

  1. Cut the documents into chunks.
  2. Turn each chunk into a vector, in such a way that texts about the same thing get vectors pointing the same way. Do this once and keep the vectors.
  3. Turn the question into a vector the same way, and take the chunks whose vectors have the highest cosine with it.
  4. Write those chunks into the window above the question.

By hand: searching two notes

The simplest way to turn a text into a vector is to count its words. Take two notes, the cat sat and the dog ran, and the question cat sat. Give every word its own entry, in the order the, cat, sat, dog, ran:

TextVector of word countsCosine with the question
cat sat (the question)(0, 1, 1, 0, 0)
the cat sat(1, 1, 1, 0, 0)2 / (1.41 × 1.73) = 0.82
the dog ran(1, 0, 0, 1, 1)0

The first note wins, and it would go into the window. The second shares no word with the question, so its dot product is 0.

That is the limit of counting words. This demo builds its vectors from word counts, giving rare words more weight, a classic method called TF-IDF. It is easy to follow and needs no model, and it is blind to meaning: sluggish, slow and speed are unrelated to it. The fix is the idea of chapter 4 applied to whole passages.

Definition

An embedding model is a model that turns a whole passage into one vector, trained so that passages with similar meaning get vectors pointing the same way.

It is a transformer like the one you built, and the server of chapter 10 can run one next to the chat model. The script in this repository uses one if you name it, and falls back to word counts otherwise.

Hands: tools

A model can only write text. It cannot look at a clock, multiply reliably, or read a file. But your program can, so the two make a deal.

Definitions

A tool is a function of your program that the model is allowed to ask for.

A tool call is the model's request: a piece of text in an agreed format that names a tool and gives its arguments. The model writes the request. Your program runs the tool.

An agent is a model inside a loop that runs the tools it asks for and gives it the results, until it answers in plain text.

You describe each tool to the model: its name, what it does, what arguments it takes. The model has been trained so that, when a tool would help, it writes a tool call instead of an answer. Your program notices the request, runs the function, and adds the result to the conversation as a new message. Then it calls the model again. With the result now in its window, the model can answer, or ask for another tool.

Build it

def normalize(v):
    return v / (np.linalg.norm(v, axis=-1, keepdims=True) + 1e-9)

class Index:
    def __init__(self, chunks, embedder):
        self.chunks, self.embedder = chunks, embedder
        self.vectors = normalize(embedder(chunks))          # computed once, reused for every question

    def search(self, question, k=2):
        q = normalize(self.embedder([question]))[0]
        scores = self.vectors @ q                           # cosine similarity with every chunk
        best = np.argsort(-scores)[:k]
        return [(float(scores[i]), self.chunks[i]) for i in best]

def build_prompt(question, hits):
    context = '\n\n'.join(f'[{n + 1}] {chunk}' for n, (_, chunk) in enumerate(hits))
    return ('Answer the question using only the notes below. '
            'Cite the note number. If the notes do not contain the answer, say so.\n\n'
            f'NOTES\n{context}\n\nQUESTION\n{question}')

From code/ch11_rag.py. The index is a table with one vector per chunk. Each vector is scaled to length 1 first, so that a dot product with the question is already the cosine, and one multiplication scores every chunk.

def run_agent(question, max_steps=6, verbose=True):
    messages = [
        {'role': 'system', 'content': 'Use the tools when they help. Answer briefly when you are done.'},
        {'role': 'user', 'content': question},
    ]
    for _ in range(max_steps):
        reply = chat(messages, tools=TOOLS, temperature=0)
        messages.append(reply)
        if not reply.get('tool_calls'):            # plain text: the model is finished
            return reply['content']
        for call in reply['tool_calls']:           # the model asked for something
            name, args = call['function']['name'], call['function']['arguments']
            args = json.loads(args) if isinstance(args, str) else args
            try:
                result = str(REGISTRY[name](**args))
            except Exception as e:                 # errors go back to the model: it can retry
                result = f'error: {e}'
            if verbose:
                print(f'  tool  {name}({args}) -> {result[:80]!r}')
            messages.append({'role': 'tool', 'tool_call_id': call.get('id', ''), 'content': result})
    return 'Stopped: too many steps.'              # a loop needs a brake

The agent loop, complete: the five messages of the by-hand table, for any number of tool calls. It stops when the model answers in plain text, or after six rounds.

What makes this hard in practice

  • Small models make more mistakes in the format. They may call a tool that does not exist or write arguments that cannot be read. Chapter 13 removes that failure. The loop above sends the error back as the tool's result, which often lets the model correct itself.
  • Loops need brakes. A confused model can call tools forever. Always cap the number of steps.
  • Tools run with your permissions. Text written by a model, possibly influenced by a web page or document it just read, ends up as arguments to your functions. Offer few tools, check their arguments, and never hand the model's text to anything that runs it as a command. Chapter 17 is about this.
  • Retrieval finds similar text, not true text. If the right passage is not retrieved, or a wrong one is, the model will usually answer confidently from what it was given.

One more caution, about judging such systems. An agent can score well on a published test and fail on a task that looks almost the same to you. A published test is a fixed set of situations. A system adjusted until it passes them, or a model trained on text that resembled them, can succeed through patterns that hold there and nowhere else. The dependable measure is a small set of tasks from your own work, with answers you have checked. Chapter 14 builds one.

What this chapter glossed over

Cutting into chunks is a craft. Here each note is one chunk. Real documents must be cut, and where you cut changes what can be found. Too small and passages lose their context; too large and one vector has to stand for too many things, and the passage crowds the window.

Calling tools is a trained habit. Nothing in the transformer does it. A model writes tool calls only if it was trained on that format. Check that the model you download lists tool support.

How these scripts were tested. Retrieval runs fully offline and was tested as is. The agent loop was tested against the fake server in this repository, which picks tools by simple rules. A real model's behaviour will vary.

In short

  • While it runs, a model knows its weights and its context window. Everything a system adds reaches it as text in the window.
  • The window is a budget. By hand: 4,650 of 8,192 tokens at 12 turns, over by 658 at 40. What is cut, the model no longer knows.
  • Retrieval finds the few chunks that fit a question, by cosine between vectors, and writes them into the window. Counting words is blind to meaning; an embedding model is not.
  • A tool call is text the model writes to ask for a function. Your program runs it and writes the result into the window.
  • An agent is that exchange in a loop, and its whole state is the list of messages.

Check yourself

With word counts, what is the cosine between the question dog and the note the dog ran?

The question is (0, 0, 0, 1, 0), of length 1. The note is (1, 0, 0, 1, 1), of length 1.73. Their dot product is 1, so the cosine is 1 / 1.73 = 0.58.

A user says "as I told you last week…". What would have to be true for a local assistant to know what they mean?

The text of last week's conversation, or a summary of it, must be put into the current window. Either the program stored it and resends it, or it retrieves the relevant part. The model itself retained nothing.
