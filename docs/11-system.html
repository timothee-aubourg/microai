Chapter 11

Memory, books and hands

The model's weights are frozen, it has never seen your documents, it forgets everything between calls, and all it can do is produce text. How do you build something useful out of that?

By accepting one constraint and exploiting it. At run time, the model knows exactly two things: what is baked into its weights, and what is written in its context window. You cannot change the weights from your program. So everything a system does to make a model smarter about your situation comes down to choosing what text to put in the window.

Conversation memory, document search and tool use sound like three features. They are one mechanism used three ways.

The window is a budget

Chapter 10 showed that a chat works by resending the transcript on every turn. That transcript shares the window with everything else you want the model to know, and the window is finite. Chapter 9 showed that making it larger costs memory, and chapter 8 that reading it costs time.

What competes for the context window

Try this. Lengthen the conversation until the bar overflows. Then try to fix it three ways: a bigger window, fewer or smaller retrieved passages, or dropping old turns.

When the budget is exceeded something must go, and whatever goes, the model no longer knows. Every assistant that seems to "remember" is managing this budget behind the scenes: trimming old turns, replacing them with a summary, or storing them outside and fetching back only what looks relevant. That last idea is the next section.

An open book: retrieval

You have a folder of notes, far too large for the window. For any one question only a few passages matter. So find them first, and put only those in the prompt. This is retrieval-augmented generation, RAG, and it needs nothing beyond chapter 4.

  1. Cut the documents into passages, called chunks.
  2. Turn each chunk into a vector, with a model trained so that texts with similar meaning get vectors pointing in similar directions. Do this once and keep the vectors.
  3. Turn the question into a vector the same way, and take the chunks with the highest cosine similarity.
  4. Write those chunks into the prompt above the question.

Search the notes of this course

Try this. Ask something the notes cover, in their words. Then ask why is my laptop sluggish. The notes do discuss speed, but this demo compares texts by shared words, and there are none. That failure is the reason real systems use learned embeddings.

The demo above builds its vectors from word counts, weighting rare words more (a classic method called TF-IDF). It is transparent and has no model to download, and it is blind to meaning: sluggish and slow are unrelated to it. An embedding model fixes that. It is a transformer like the one you built, trained so that its output vector captures what a passage is about, and your local server can run one alongside the chat model. The script in this repository uses one if you name it, and falls back to word counts otherwise.

Hands: tools

A model can only emit text. It cannot look at a clock, multiply reliably, or read a file. But your program can, so the two make a deal.

You describe each available function to the model: its name, what it does, what arguments it takes. The model has been trained so that, when a function would help, it writes a specially formatted request instead of an answer. Your program notices the request, runs the function, and appends the result to the conversation as a new message. Then it calls the model again. With the result now in its window, the model can answer, or ask for another tool.

One tool call, message by message

Try this. Press Next and read who wrote each message. This trace is scripted to show the flow; run code/ch11_agent.py to watch a real model do it.

Notice what the model did at the third message: it wrote text. It did not calculate anything. The arithmetic happened in your program. And notice that the "state" of the whole process is just the growing list of messages. Put that exchange inside a loop that continues until the model answers in plain text, and you have what is called an agent.

Build it

def normalize(v):
    return v / (np.linalg.norm(v, axis=-1, keepdims=True) + 1e-9)

class Index:
    def __init__(self, chunks, embedder):
        self.chunks, self.embedder = chunks, embedder
        self.vectors = normalize(embedder(chunks))          # computed once, reused for every question

    def search(self, question, k=2):
        q = normalize(self.embedder([question]))[0]
        scores = self.vectors @ q                           # cosine similarity with every chunk
        best = np.argsort(-scores)[:k]
        return [(float(scores[i]), self.chunks[i]) for i in best]

def build_prompt(question, hits):
    context = '\n\n'.join(f'[{n + 1}] {chunk}' for n, (_, chunk) in enumerate(hits))
    return ('Answer the question using only the notes below. '
            'Cite the note number. If the notes do not contain the answer, say so.\n\n'
            f'NOTES\n{context}\n\nQUESTION\n{question}')

def run_agent(question, max_steps=6, verbose=True):
    messages = [
        {'role': 'system', 'content': 'Use the tools when they help. Answer briefly when you are done.'},
        {'role': 'user', 'content': question},
    ]
    for _ in range(max_steps):
        reply = chat(messages, tools=TOOLS, temperature=0)
        messages.append(reply)
        if not reply.get('tool_calls'):            # plain text: the model is finished
            return reply['content']
        for call in reply['tool_calls']:           # the model asked for something
            name, args = call['function']['name'], call['function']['arguments']
            args = json.loads(args) if isinstance(args, str) else args
            try:
                result = str(REGISTRY[name](**args))
            except Exception as e:                 # errors go back to the model: it can retry
                result = f'error: {e}'
            if verbose:
                print(f'  tool  {name}({args}) -> {result[:80]!r}')
            messages.append({'role': 'tool', 'tool_call_id': call.get('id', ''), 'content': result})
    return 'Stopped: too many steps.'              # a loop needs a brake

The agent loop, complete.

What makes this hard in practice

  • Small models make more mistakes in the format. They may call a tool that does not exist or pass malformed arguments. The loop above sends the error back as the tool's result, which often lets the model correct itself.
  • Loops need brakes. A confused model can call tools forever. Always cap the number of steps.
  • Tools run with your permissions. Text written by a model, possibly influenced by a web page or document it just read, ends up as arguments to your functions. Offer few tools, check their arguments, and never pass model output to eval or a shell.
  • Retrieval finds similar text, not true text. If the right passage is not retrieved, or a wrong one is, the model will usually answer confidently from what it was given.

One more caution, about judging such systems. An agent can score well on a published benchmark and fail on a task that looks almost the same to you. A benchmark is a fixed set of situations; a system tuned on it, or a model whose training data resembled it, can succeed through regularities that hold there and nowhere else. The dependable measure is a small set of tasks from your own work, with answers you have checked.

What this chapter glossed over

Chunking is a craft. Here each note is one chunk. Real documents must be cut, and where you cut changes what can be found. Too small and passages lose their context; too large and they dilute the vector and crowd the window.

Tool calling is a convention, not a capability of the architecture. A model does it only if it was trained on that format. Check that the model you download lists tool support.

How these scripts were tested. Retrieval runs fully offline and was tested as is. The agent loop was tested against the fake server in this repository, which picks tools by simple rules. A real model's behaviour will vary.
