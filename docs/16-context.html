Chapter 16

Spending the window

Every step of an agent sends the whole conversation again. What does that cost, and what do you do when it stops fitting?

The session of chapter 15 ended as a conversation of 3,025 characters. To get there the model read 12,749 characters, because each of its five requests contained everything before it. A longer task makes this worse quickly: the text grows by a steady amount per step, so the total read grows with the square of the number of steps.

Two budgets are being spent. One is time: reading costs computation. The other is room: the window is finite (chapter 11). They are managed with different tools, and the tools interfere with each other. That interference is the subject here.

Reading and writing are different work

A request has two phases. First the model reads the prompt. All of those tokens are known in advance, so they can be processed together. Then it writes, and each new token has to wait for the one before it. The reading phase is often called prefill and the writing phase decode.

You feel them separately. The pause before the first word appears is the reading. The speed of the words after that is the writing. An agent step typically reads thousands of tokens and writes a few dozen, so its cost is mostly reading.

Do not read it twice

Chapter 8 introduced the KV cache: for every token read, the model stores a key and a value per layer, so that later tokens can attend to it without recomputing it. Those stored numbers depend only on that token and the tokens before it, never on what comes after. So they stay valid for any text that begins the same way.

A server can use this between requests. It keeps the cache of the last request. When the next one arrives it compares the two token by token, keeps the cache up to the first difference, and computes only the rest. This is a prefix cache. Measured on the model of this course, with five requests that each extend the previous one by nine characters:

Forgets between requests25, 34, 43, 52, 61215
Keeps the cache, text only grows25, 9, 9, 9, 961

The second row does 3.5 times less work and produces the same scores: the script checks every request against a computation from scratch. The third row is the warning. One character changed near the beginning, and the cache was worth nothing, because every later token had attended to it.

From this follows the first rule of building agents: keep the beginning of the conversation fixed, and only ever add to the end. No clock in the system prompt. The same tools in the same order at every step. No rewriting of earlier messages. llama.cpp's server reuses the common beginning of consecutive requests by default, and hosted services price cached input lower for the same reason.

One session, four ways to run it

Try this. Start with "Only add to the end" and note the total. Switch to the clock. Then make the session long enough to cross the window line, and try the two ways of shrinking it.

When it no longer fits

Adding to the end cannot go on forever. Past the window line the request is refused, or the oldest text falls out without notice. Three tools make the conversation smaller, in order of violence.

Clip at the source. Cut a long tool result before it enters the conversation, as clip does in chapter 15. This costs nothing later, because nothing already read is changed.

Trim old results. A file read ten steps ago has usually done its job. Replace old results with their first lines.

Compact. Ask the model to summarise the work so far, and replace the middle of the conversation with that summary.

The last two rewrite text the model has already read, so they break the first rule. From the first changed character on, the cache is void and everything is read again. Measured on a session of six file reads of 1,500 characters each: trimming takes it from 10,870 to 5,722 characters and leaves the first 883 identical. Compacting takes it to 4,036 and leaves the first 483 identical.

So the two budgets pull against each other. The experiment shows the way out: trimming a little at every step pays the re-reading price at every step, while compacting rarely, in one large cut, pays it once and then enjoys a short conversation that grows at the end again. Shrink seldom and shrink a lot.

Memory is a decision about the window

Chapter 11 said the model's only memory is the list of messages. Everything called memory in an agent is a way of choosing what goes back into that list.

Notes on disk. The agent writes what it learned into a file with its ordinary tools. A later session reads the file at the start. The memory is as good as what was written down.

Retrieval. Chapter 11's search, pointed at past conversations or notes: fetch the few passages that match the present task.

A fresh window. Hand a side task to a helper agent. It spends its own window on the reading and returns three lines.

Build it

class PrefixCache:
    """Keep the keys and values of the last text. For the next text, compute only what differs."""
    def __init__(self, run):
        self.run, self.ids, self.cache = run, [], run.new_cache()

    def read(self, ids):
        same = 0
        while same < min(len(ids), len(self.ids)) and ids[same] == self.ids[same]:
            same += 1                                  # how long is the shared beginning?
        same = min(same, len(ids) - 1)                 # always compute the last token: we need its scores
        for layer in self.cache['k'] + self.cache['v']:
            del layer[same:]                           # everything after the first difference is void
        self.cache['pos'] = same
        for t in ids[same:]:
            logits = self.run.step(t, self.cache)      # the only real work
        self.ids = list(ids)
        return logits, len(ids) - same                 # scores for the next token, tokens computed

From code/ch16_context.py. A prefix cache on top of the runner of chapter 8: find the shared beginning, void the rest, compute what is new.

def trim_results(messages, keep=2, limit=200):
    """Old tool results are most of an agent's context. Shorten all but the latest `keep`."""
    out, seen = [], 0
    for m in reversed(messages):
        if m['role'] == 'tool':
            seen += 1
            if seen > keep and len(m['content']) > limit:
                m = {**m, 'content': m['content'][:limit] + f' [trimmed: {len(m["content"]) - limit} more characters]'}
        out.append(m)
    return out[::-1]

def compact(messages, summarize, keep=4):
    """Replace the middle of a long conversation with a summary. `summarize` is one more model call."""
    cut = len(messages) - keep
    while cut > 2 and messages[cut]['role'] == 'tool':
        cut -= 1                                       # never separate a result from the request before it
    if cut <= 2:
        return messages
    note = summarize(messages[2:cut])
    return messages[:2] + [{'role': 'user', 'content': 'Summary of the work so far:\n' + note}] + messages[cut:]

Two ways to shrink a conversation. Both keep a tool result next to the request that caused it, because a result without its request confuses the model and is rejected by some servers.

What this chapter glossed over

Characters stand in for tokens. The session sizes are counted in characters. Divide by about four for tokens of English text. The table on our own model counts real tokens, since for it a token is a character.

The experiment is arithmetic. It adds up sizes under stated rules. The fixed part, 1,921 characters of system prompt and tool descriptions, is the measured figure from chapter 15. The rest is set by the sliders.

A summary loses things. What to keep is a judgment the model makes for you, and a detail dropped there is gone. Good harnesses keep the full record on disk so it can be searched.

Real servers have more moving parts. A local server keeps a small number of caches. A summarising request is itself a request, and on a server with a single cache it can push out the conversation it was meant to help.

A full window is also a worse window. Models tend to use a long, cluttered context less reliably than a short, relevant one. Size is not only a cost.

Check yourself

Someone adds "The current time is 14:32:07" as the first line of the system prompt. What happens to the cost of a twenty-step task?

If the time is refreshed on each request, the first line differs every time, so the shared beginning has length zero and every request is read in full. Put changing information at the end, in the newest message, where nothing after it depends on it.

Why does the cache become invalid after the first difference, and not only at the changed token?

Each token's stored keys and values were computed by attending to all the tokens before it. Change one early token and every later token would have computed something different. Only what came before the change is untouched.

Trimming old results at every step keeps the window small. Why does it cost more reading than compacting now and then?

Each trim changes text two steps back, so each request is read again from that point on: about two results' worth per step instead of one. A compaction costs one larger re-read, after which the conversation again grows only at the end.

An agent "remembers" your preferences from last week. Where are they stored?

Not in the model: its weights did not change. They are in text that the harness saved and now puts back into the request, as a note file read at the start or a retrieved passage.
