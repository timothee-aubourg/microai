Chapter 23

As small as it goes

The agent of chapter 19 is a file of 432 KB. How much of that does the job need?

Chapter 22 ended on a model small enough to live in the processor's cache. Size decides where a model can run at all: on a phone, in a browser tab, on a board with no graphics processor. So far the course has made models smaller in one way, by rounding the weights after training (chapter 9). This chapter takes the agent you trained in chapter 19 and makes it as small as it will go, by every means available, without letting it get worse.

That last condition needs a test that cannot be argued with. Chapter 19 graded 200 questions drawn at random. Here the test is every question there is: 1,000 pairs of numbers that were kept out of training, each with plus, minus and times. That makes 3,000 questions, and an answer counts only if the tool call and the final sentence are both exactly right. The model of chapter 19 gets 3,000 of 3,000.

Rounding afterwards has a floor

The first thing to try is what chapter 9 did: keep the trained model and store each weight on fewer bits.

Eight bits cost one question and make the file almost four times smaller. Four bits lose 184 questions. With three values per weight, nothing is left: not one question, not even "hello".

Rounding does not consult the model. The weights were trained to work together at full precision, and each one is then moved a little without regard for the others. A little is harmless. Below some number of bits the errors add up to a different model.

Three values

The smallest useful weight is not one bit. A bit can say "add" or "subtract", and a model also needs to say "ignore".

Definition

Ternary weights can take only three values: minus one, zero or plus one. Each matrix also has one ordinary number, its scale, that every weight in it is multiplied by.

By hand: a product without multiplying

Take three inputs, 0.5, −1.0 and 2.0, and one column of ternary weights: +1, 0, −1, with a scale of 0.3. The output is the weighted sum.

0.3 × (+1 × 0.5 + 0 × (−1.0) + (−1) × 2.0) = 0.3 × (0.5 − 2.0) = −0.45

Look at what the weights did. The +1 said "add this input", the −1 said "subtract this one", the 0 said "skip it". There is one multiplication, by the scale, at the end. A matrix of ternary weights turns chapter 18's millions of multiply-adds into additions and subtractions.

By hand: five weights in a byte

Three values are one digit in base 3. Five such digits make 3 × 3 × 3 × 3 × 3 = 243 combinations, and a byte holds 256. So five weights fit in one byte. Add 1 to each weight to get a digit of 0, 1 or 2, then read the five digits as a number.

Pack five weights

Try this. Tap each weight to change it. Find the five weights that give the byte 0, and the five that give the largest byte. How many of the 256 values of a byte are never used?

What you should have seen. Five weights of −1 give the byte 0. Five weights of +1 give 242, the largest. The values 243 to 255 are never used: 13 of 256 are wasted, which is why this packing costs 1.6 bits per weight and not the 1.58 that three values strictly need.

Train it rounded

Rounding a finished model to three values gave 0 of 3,000. The way out is to stop treating rounding as something done to a model afterwards.

Definition

Quantization-aware training rounds the weights in every forward pass of training, so the model learns to do its job with the rounded values. The full-precision weights are kept underneath and are the ones gradient descent adjusts.

Rounding has no useful slope: move a weight a hair and its rounded value usually does not change at all. So the backward pass of chapter 3 pretends the rounding was not there and hands the gradient to the kept weight. A kept weight that is pushed the same way many times eventually crosses a boundary, and its rounded value flips.

def ternary(w):
    """Round a matrix to -1, 0 or +1 times ONE number. Returns the three-valued matrix and that number."""
    scale = np.abs(w).mean() + 1e-8
    return np.clip(np.round(w / scale), -1, 1), scale
def forward(self, idx, targets=None, trace=None):
    """Compute with the three-valued weights, learn on the full-precision ones underneath."""
    latent = self.p
    self.p = dict(latent)
    self.p['wpe'] = self.where * self.size['wpe']
    for k in (self.stored if self.three else []):
        q, _ = ternary(latent[k].data)
        three = latent[k] + (q - latent[k].data)               # value: -1, 0 or +1. gradient: passes straight to latent
        self.p[k] = three * self.size[k]                       # times the one number of this matrix
    try:
        return super().forward(idx, targets, trace)
    finally:
        self.p = latent

Remove what the task does not use

With weights this cheap, the rest of the file starts to matter. Three more things were taken out.

  • The position table. Chapter 4 learned one vector per position. Here the vector for each position is computed from sines and cosines, so nothing is stored. One trained number says how strongly positions count.
  • The weights of the normalisation. Chapter 6's layer normalisation had a gain and an offset per number. Here it only rescales.
  • Width. The model of chapter 19 used vectors of 64 numbers. Models of that width and of several narrower ones were trained, each for 6,000 steps on the same conversations, and graded on the same 3,000 questions.

Read the table from the top. Ordinary weights tolerate a narrow model well: at width 32 the full-precision model misses one question, and rounding it to 8 bits costs one more. Three-valued weights need more width for the same result. At width 32 they miss 215 questions, at width 48 they miss 2, and at width 64 none.

Now compare sizes. Width 64 in three values takes 20,369 bytes and answers everything. Width 32 in 8 bits takes 27,676 bytes and misses 2. So the wider three-valued model is both smaller and better. Further down, the picture is less tidy. Below width 32 the three-valued models learned nothing useful in the steps they were given, while an ordinary model of width 16 still got 2,911 right. There is a floor here too. It is lower than the floor of rounding, and it is found by measuring.

The result

The condition was that the model must not get worse, so the chosen model is the smallest one that answered everything: width 64, the width chapter 19 used, with 101,248 three-valued weights. It was trained for 6,000 steps, about 7 minutes on one processor core. If you can live with 2 wrong answers in 3,000, the width-48 model does the job in 11,618 bytes.

Notice the row for numpy: the two models run at about the same speed. Numpy multiplies by −1, 0 and +1 exactly as it multiplies by any other number, so it gains nothing from the three values. The gain in arithmetic needs an engine written for them, which is the subject of the last section.

At 19.9 KB the whole model fits in the first and fastest layer of the processor's cache, the 48 KB one of chapter 22. It also fits on this page. The box in the experiment below holds every byte of it.

Ask the small one

Try this. Ask a few sums. Each question goes to both models: the one of this chapter and the one of chapter 19. Look for a difference between their answers. Then ask for something neither was trained on.

What you should have seen. On sums with numbers below 100 the two models write the same call and the same sentence. The model that is 21 times smaller does the job. Outside what they were trained on, both fail, and not always in the same way. Making a model smaller did not make it less general, because it was never general. It was built for one job and graded on that job.

It runs on anything

A model made of additions needs very little to run. code/tiny_agent.py is the whole agent in one file: it reads the 19.9 KB, runs the model and the tool loop, and uses nothing but Python's standard library.

def times(x, w):
    """x @ W for a three-valued W: sums and differences, then one multiplication per output."""
    scale, add, sub = w[0], w[1], w[2]
    pick = x.__getitem__
    return [scale * (sum(map(pick, a)) - sum(map(pick, s))) for a, s in zip(add, sub)]

def norm(x):
    mean = sum(x) / len(x)
    x = [v - mean for v in x]
    size = math.sqrt(sum(v * v for v in x) / len(x) + 1e-5)
    return [v / size for v in x]

def step(m, token, cache):
    """One token through the model. `cache` keeps the keys and values of the tokens before it."""
    d, H = m['d'], m['H']
    hd, pos = d // H, len(cache[0][0]) if cache else 0
    if not cache:
        cache.extend(([], []) for _ in m['layers'])
    row, scale = m['wte'][3][token], m['wte'][0]
    x = [scale * row[j] + m['where'] * (math.sin if j < d // 2 else math.cos)(pos / 50.0 ** (2 * (j % (d // 2)) / d)) for j in range(d)]
    for layer, (keys, values) in zip(m['layers'], cache):
        a = norm(x)
        q = times(a, layer['wq'])
        keys.append(times(a, layer['wk']))
        values.append(times(a, layer['wv']))
        mixed = []
        for h in range(H):                                  # each head: score every earlier token, then average
            lo, hi = h * hd, (h + 1) * hd
            scores = [sum(q[j] * k[j] for j in range(lo, hi)) / math.sqrt(hd) for k in keys]
            top = max(scores)
            weights = [math.exp(s - top) for s in scores]
            total = sum(weights)
            mixed += [sum(w * v[j] for w, v in zip(weights, values)) / total for j in range(lo, hi)]
        x = [u + v for u, v in zip(x, times(mixed, layer['wo']))]
        hidden = times(norm(x), layer['w1'])
        hidden = [0.5 * v * (1 + math.tanh(0.7978845608 * (v + 0.044715 * v * v * v))) for v in hidden]
        x = [u + v for u, v in zip(x, times(hidden, layer['w2']))]
    return times(norm(x), m['out'])                         # one score per character

At full size

Most local models you download are still made the way chapter 9 described: trained at full precision, then rounded to 4 or 5 bits. That is the cheap route, because it needs no retraining, and at 4 bits it loses little.

Training with the rounding in place is the route below that. In 2025 Microsoft Research published a model of 2 billion weights trained from the start with three-valued weights, BitNet b1.58 2B4T, and reports 0.4 GB for its weights outside the embedding table. Its training was the expensive part: the model had to be trained that way from the first step, on 4 trillion tokens. An existing model cannot be converted.

The measurement of this chapter shows the trade in small. At equal width, three-valued weights did worse than ordinary ones. They needed a wider model to catch up, and still came out smaller. Whether that trade pays at full size depends on what training costs, which is why rounding afterwards remains the common choice.

What this chapter glossed over

It is the same narrow job. This is not a small general assistant. It answers sums of two numbers below 100 in one phrasing, and three fixed lines of small talk. A general model has a floor on its size too, and it is many thousands of times higher.

Two changes were needed before it trained at all. With the scale of each matrix derived from its kept weights, and positions added at a fixed strength, the width-32 model did not learn to copy numbers. Making each scale, and the strength of the positions, a trained number fixed that. The script contains only the version that worked.

The training examples were laid out differently. Each row here is one conversation starting at position 0, as in chapter 21. Chapter 19 cut windows out of a long stream. The comparison between the two chapters is therefore not only about the weights.

One run each. Every row of the tables is one training run with one seed. Another run moves the counts. The width-48 model was also trained for 12,000 steps in place of 6,000, and scored 2,964, fewer than before. More training was a different run, not a better one, and a narrow model that learned nothing here might learn with another seed.

The activations are not rounded. The numbers flowing through the model are still ordinary floating-point numbers. Full-size systems of this kind round those as well, to 8 bits.

Other ways to shrink a model. Training a small model to imitate a large one (distillation) and removing weights that matter least (pruning) are both left out.

In short

  • Rounding a trained model has a floor. The model of chapter 19 keeps 2,999 of 3,000 answers at 8 bits, 2,816 at 4 bits and none at three values.
  • Ternary weights are −1, 0 or +1 times one scale per matrix. A matrix product becomes sums and differences, and five weights fit in a byte.
  • Quantization-aware training rounds in every forward pass and lets the gradient adjust full-precision weights kept underneath. The model learns to work rounded.
  • The result is 20,369 bytes against 432,128, 21 times smaller, with 3,000 of 3,000 held-out questions right. It runs in plain Python with no library.
  • Smaller has a price that has to be measured. At width 32, three-valued weights miss 215 questions where ordinary ones miss 1, and below width 32 they learned nothing.

Check yourself

The chapter 19 model rounded to three values scores 0. A model trained with three values scores almost everything. Both files hold only −1, 0 and +1. What is the difference?

Which model the values belong to. The first set are the nearest three-valued neighbours of weights that were trained to work at full precision; nothing ever checked that the neighbours work. The second set were used in every forward pass of training, so the loss was measured on them and the training adjusted them until they worked.

Why does a ternary weight need 1.6 bits in the file and not 2?

Because weights are packed five to a byte. Five three-valued digits make 243 combinations, which fit in the 256 values of one byte: 8 bits for 5 weights is 1.6 each. Storing each weight on its own would need 2 bits, since 1 bit holds only two values.

Rounding gives no gradient. How can a model be trained through it?

The backward pass treats the rounding as if it were not there and passes the gradient to the full-precision weight kept underneath. That weight moves a little at each step, and when it crosses a boundary its rounded value changes.

You need the smallest file that passes a test. Why is "use fewer bits" not always the answer?

Because fewer bits per weight can require more weights. Here the three-valued model needed width 64 to answer everything, where a full-precision model of width 32 missed a single question. Size is weights times bits, and the two pull against each other. The table settles it, not a rule.
