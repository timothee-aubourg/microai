Chapter 36

Releasing it, and watching it

A new version is ready. How do you put it in front of people without finding out the hard way that it is worse?

In every chapter so far a model was trained, measured once, and the chapter ended. A system in use does not end. The model is trained again, the guard is repaired as in chapter 35, a tool is added. Each of these makes a new version, and each new version can be worse than the old one in a way nobody intended. And when nothing changes on your side, the requests change on the other.

Three habits answer this, in order. Each one catches what the one before cannot.

Definitions

A release gate is a fixed test that a new version must pass before any user sees it.

A canary is a new version given a small share of the real traffic, and watched, before it gets the rest.

Drift is a change in the requests, or in the answers, after release. Nothing in the system changed. The world did.

In production is the system of chapter 34: the trained agent behind the guard, with the check and the filter. code/ch36_release.py prepares three candidates to replace the agent:

  • Same. The production model again. It must pass everything, or the tests are wrong.
  • Wrong file. The pre-trained model of chapter 24, shipped by mistake.
  • More sums. The production model trained further on 2,000 worked sums and nothing else, for 1,000 steps. A well-meant change: more practice at the main task.

1. The gate

The gate tests the model alone on the test of chapter 24: 300 unseen sums, 300 requests for the secret, three lines of small talk. A candidate is blocked if it is worse than production by more than chance explains.

By hand: is 293 worse than 297?

"Same" got 293 sums right of 300 where production got 297. It is the same model, so the difference of 4 is pure chance: the answers are drawn, and the two tests drew differently. A gate has to know this. The noise of a difference between two counts out of n is

√( p1(1 − p1)/n + p2(1 − p2)/n ) = √( 0.977 × 0.023 / 300 + 0.990 × 0.010 / 300 ) = 0.010

That is 1.0 points. The rule used here: blocked if worse by more than twice the noise, 2.1 points, which is 6 sums of 300. A drop of 4 passes.

def worse(k_new, k_old, n):
    """Is the candidate's count lower than production's by more than chance explains?"""
    p_new, p_old = k_new / n, k_old / n
    noise = math.sqrt(p_new * (1 - p_new) / n + p_old * (1 - p_old) / n)     # standard error of the difference
    return p_old - p_new > 2 * max(noise, 1 / n)

def gate(candidate, production, metrics):
    """Blocked if any metric of the list got worse. Returns the names of the metrics that did."""
    return [m for m in metrics if worse(candidate[m], production[m], candidate['of'][m])]

The lesson is about what goes into the test, more than about the rule. The gate must hold every behaviour you want to keep. The behaviour you just changed is the one least likely to have got worse.

2. The canary

Suppose a candidate gets past the gate, or the gate tested only sums. The next protection is to let it answer only a small share of the real requests, inside the whole system, and compare it with production.

Real requests have no answer key. So the canary needs a signal that can be read without one. The system already produces one: the check of chapter 34 asks again when a sum is answered without a tool result. Production does this on 1 of 358 sums. The canary counts how often the candidate does, and raises the alarm when that count would happen by chance less than one time in a thousand.

def canary(run, clf, p0, requests, rng, alarm=0.001):
    """The candidate answers its share of the traffic. Stop when its retries cannot be chance any more."""
    sums = retries = wrong = filtered = 0
    for n, (text, kind) in enumerate(requests, 1):
        t = serve(text, run, clf, rng)
        filtered += t['filtered']                                 # counted, but this canary does not look at it
        if kind == 'sum' and not t['blocked']:
            sums += 1
            retries += t['attempts'] > 1                          # needs no answer key
            wrong += post.grade(text, {'answer': t['reply']}) != 1    # for the record only: the canary cannot see this
            if tail(retries, sums, p0) < alarm:
                return {'alarm': True, 'requests': n, 'sums': sums, 'retries': retries, 'wrong': wrong, 'filtered': filtered}
    return {'alarm': False, 'requests': len(requests), 'sums': sums, 'retries': retries, 'wrong': wrong, 'filtered': filtered}

  • The same model never raised the alarm, in 10 runs of 300 requests. A canary that cries wolf is switched off within a week.
  • "More sums" was never noticed. Its fault is in refusing, and this counter looks at sums. A canary sees what its counters look at, and nothing else.

There is a second reason, and it is the more uncomfortable one. Inside the system, "more sums" did no harm at all in these runs. The guard stopped the requests for the secret before they reached it. Even the filter behind it had nothing to do: it acted on 0, 0, 0 of 300 requests in the three runs, against 1 of 600 in production. The other layers of chapter 34 covered for the broken model completely. That is good for the users today and dangerous for the team: one layer of protection has gone, no counter anywhere shows it, and the next request that slips past the guard meets a model that no longer refuses. Only a test of the model alone, the gate, could see it.

3. The watch

After release, the system writes one line for every request: what each part did. Chapter 14 called this a trace and used it to find out why one answer was wrong. Here it is used in bulk.

def serve(request, run, clf, rng):
    """One request through the production system. Returns one line of trace: what each part did."""
    t = {'request': request, 'score': round(guard.classify(clf, request), 2), 'blocked': False,
         'attempts': 0, 'call': None, 'filtered': False, 'echo': None}
    if t['score'] >= 0.5:                                         # the guard
        return dict(t, blocked=True, reply=post.REFUSAL)
    is_sum = sys2.SUM.fullmatch(request) is not None
    for _ in range(3):                                            # the agent, and the check of chapter 25
        e = post.episode(run, request, rng)
        t['attempts'] += 1
        if not is_sum or e['call'] is not None:
            break
    t['call'], t['filtered'] = e['call'], post.SECRET in e['answer']
    t['reply'] = post.REFUSAL if t['filtered'] else e['answer']  # the filter
    if is_sum:                                                    # does the reply talk about the numbers that were asked?
        t['echo'] = t['reply'].startswith(request[len('what is '):-1] + ' is ')
    return t

From these lines, three counters per day. None needs an answer key: requests blocked by the guard, sums where the check had to ask again, and replies about other numbers than the question's. The first four days define what is normal. After that, a counter raises the alarm on any day whose count would happen by chance less than one time in a thousand.

The experiment: 300 requests a day for eight days. From day 5 the users change. Three sums in ten now contain a three-digit number. The agent was trained on numbers up to 99, and its tool call has room for two digits.

At full size

  • A version is more than the weights. The model, the system prompt, the tool list, the guard and the harness code all change behaviour. A change to any of them goes through the gate.
  • Shadow first. Before a canary, many teams let the candidate answer copies of real requests and throw its replies away. Users see nothing, and the two versions can be compared on real traffic.
  • Then in steps. One request in a hundred, then five, then a quarter, then all, with a way back at every step. The way back has to be one switch, prepared in advance.
  • A model as judge. Where no simple counter exists, a second model grades a sample of live answers against written criteria. It is the classifier of chapter 28 used as a measuring instrument, and it has the same two kinds of error.
  • Traces have more in them. One span per step: each model call, each tool call, each retrieval, with its duration, its tokens and its cost. Latency and cost are watched with the same alarms as quality.
  • People still read. A sample of traces is read by a person every week. Counters only find the failures somebody thought to count.

What this chapter glossed over

Forgetting depends on how far the weights move. A gentler version of "more sums", 300 steps at a third of the rate, was tried first and changed nothing measurable. The version shown trains for 1,000 steps at the full rate.

The canary has one counter. Real canaries watch many, and with many counters some alarm by chance. The thresholds then have to be stricter.

Small regressions need patience. A candidate that is one point worse cannot be told from chance in 300 requests. Detecting it needs tens of thousands, or a larger test at the gate.

The drift is sudden and large. Real drift is often slow, and a day-against-last-week alarm can miss a change that creeps.

One run. One seed for the gate and the eight days, three for each canary and ten for "same".

In short

  • A release gate must test every behaviour you want to keep. "More sums" scored 298 of 300 on sums and refused the secret 0 times of 300.
  • A gate must also know chance: 293 against 297 is the same model.
  • A canary limits the harm of a bad release: the wrong file was caught within 8 requests. It sees only what its counters look at.
  • After release, one line of trace per request gives counters that need no answer key. They caught the drift on its first day, while the share of right answers fell from 99% to 67% unseen.
  • Layers hide each other's failures. Inside the system the broken model did no visible harm, so each layer also has to be tested alone.

Check yourself

A candidate scores 290 of 300 where production scored 296. Blocked or not, by the rule of this chapter?

The noise of the difference is about 1.2 points, so the limit is about 2.4 points, which is 7 sums. A drop of 6 passes. It may still be a real drop: 300 cases cannot tell, and a larger test would.

Why did the gate on sums let "more sums" through?

Because it was better at sums. The damage was in a behaviour that this gate did not test. A change is most likely to break what it was not aimed at, and that is what the test has to cover.

The canary's counter needs no answer key. Why does that matter?

Real requests arrive without one. Nobody knows the right answer to a live request at the moment it is served, so a signal that needs the answer cannot be computed. The counters that work are about the system's own behaviour: did a check fire, did a filter act, does the reply fit the request.

On day 5 nothing in the system had changed. What went wrong, and what noticed?

The requests changed: numbers of three digits, outside what the agent was trained on. Two counters computed from the traces left their normal range that same day. The replies themselves looked fine, each one a confident, well-formed sentence about the wrong numbers.
