Chapter 14

Knowing whether it works

The agent gave a wrong answer. Was it the model, the search, the tool, or your loop? And after you change something, how do you know it got better?

The agent of chapter 11 hands back one string. When the string is wrong, the fault can sit in several places. The model may have picked the wrong tool. It may have picked the right tool and written bad arguments. The tool may have failed. The search may have returned the wrong passage, and the model answered faithfully from it. The loop may have hit its step limit. From the final string alone these all look the same.

A second problem follows the first. You find a fault and fix it, perhaps by rewording the system prompt. The example that failed now works. Did anything else break? A model's behaviour is not local: a sentence added for one case shifts the probabilities in every other case.

Both problems have the same answer, and it is not clever. Write down everything the agent does. Then ask it the same questions every time, and count.

Write everything down

Wrap each model call and each tool call so that it notes four things: what went in, what came out, how long it took, and whether it failed. One such note is a span. The spans of one run, with the record of which call started which, form a trace.

The tracer in this chapter is about twenty lines, and it does not edit the agent. The loop of chapter 11 calls chat and looks tools up in a table. The tracer swaps both for versions that do the same work and take notes, runs the loop, and puts the originals back.

Below are nine questions put to that agent, with the trace of each run.

Nine tasks, nine traces

Three of the nine fail, and for three different reasons. In (3 + 4) * 12 the model span shows the arguments it wrote: 3 + 4) * 12, with the opening bracket lost. The calculator span after it is marked as failed. In 17% of 2340 the first model span asks for the search tool: the wrong tool. In the last task the model calls the calculator, reports the result and stops, with half the question unanswered. Bad arguments, wrong tool, half the job. The final answers alone would not have told you which.

Look also at the input of each model span. The second call of a run receives everything the first one did, plus the request and the tool's result. After a search, the input grows from under 200 characters to about 1,400. This is the context budget of chapter 11, measured.

Ask the same questions every time

An evaluation is three things: a fixed list of tasks, a grader that decides pass or fail without a person looking, and a count. You run it before a change and after, and compare.

The tasks should come from your own use. The nine here are small on purpose. The grader makes two kinds of check.

Checks on the answer. Does the final text contain the right number, or one of the expected words? This is what the user cares about.

Checks on the path. Did the calculator run, and without an error? Did a search result contain the passage that holds the answer? These read the trace, not the answer. They matter for two reasons. An answer can be right for a bad reason: a model that multiplies in its head will be right on small numbers and wrong on large ones, and only the missing calculator call shows it. And a path check says where a failure is. "The right passage was never retrieved" sends you to the search. "It was retrieved and the answer is still wrong" sends you to the prompt or the model.

A task passes when all its checks pass. Here that gives 6 of 9.

How far to trust a score

Six of nine is 67%. Suppose you add three sentences to the system prompt and get seven of nine, 78%. Is the agent better?

Think of each task as a coin that lands "pass" with some unknown probability. An evaluation flips n such coins and reports the fraction of passes. Flip again, with new tasks of the same kind or with the same tasks and a model that samples, and the fraction comes out different. The typical size of that wobble is the standard error:

standard error = √( p (1 − p) / n )

where p is the pass rate and n the number of runs. About two scores in three land within one standard error of the truth, and nearly all within two.

RunsStandard error at a 70% pass rate
9± 15 points
20± 10 points
100± 4.6 points
400± 2.3 points

With nine tasks the wobble is fifteen points each way. Six of nine and seven of nine are the same result. The square root also sets the price of precision: to halve the uncertainty you need four times the tasks.

Two systems, many evaluations

Try this. System B is truly better than system A by the amount you choose. Each is evaluated 400 times on fresh tasks. With 20 tasks and a 5-point improvement, how often does the better system come out ahead? Then raise the number of tasks until it almost always does.

Worked out exactly for 20 tasks, a system that is truly five points better (75% against 70%) scores higher only 57% of the time. It ties 13% of the time and scores lower 30% of the time. At 400 tasks it scores higher 94% of the time. Small evaluations are still worth having, because they catch large breakages at once. They cannot rank two close versions.

The working loop

Put together, this is how an agent gets better.

  1. Run the evaluation. Read the traces of the failures, not only the count.
  2. Name the fault: wrong tool, bad arguments, missing passage, wrong wording, too many steps.
  3. Change one thing that addresses it: a tool description, the prompt, the chunking, a mask from chapter 13.
  4. Run everything again. A fix that breaks two other tasks is not a fix.
  5. When a real use fails in a new way, add it to the tasks. The list only grows.

One caution carries over from chapters 7 and 11. A prompt tuned until it passes a fixed set of tasks has, in a small way, been trained on them. Keep some tasks aside that you never look at while tuning, and check those at the end.

Build it

class Tracer:
    def __init__(self):
        self.spans, self.stack, self.t0 = [], [], time.perf_counter()

    @contextmanager
    def span(self, kind, name, input=None):
        s = {'id': len(self.spans), 'parent': self.stack[-1] if self.stack else None,
             'kind': kind, 'name': name, 'input': copy.deepcopy(input),      # a copy: the caller may change it later
             'start': round(1000 * (time.perf_counter() - self.t0), 2)}
        self.spans.append(s); self.stack.append(s['id'])
        t = time.perf_counter()
        try:
            yield s                                    # the work happens here and may set s['output']
        except Exception as e:
            s['error'] = f'{type(e).__name__}: {e}'    # record the failure, then let it continue upward
            raise
        finally:
            s['ms'] = round(1000 * (time.perf_counter() - t), 2)
            self.stack.pop()

From code/ch14_trace.py. A span is opened, the work runs inside it, and the span is closed whatever happens.

def traced(tracer, kind, name, fn):
    """The same function, with every call recorded as a span."""
    def wrapper(*args, **kwargs):
        with tracer.span(kind, name, input={'args': args, 'kwargs': kwargs}) as s:
            s['output'] = fn(*args, **kwargs)
            return s['output']
    return wrapper

def run_traced(question, tracer=None, **kw):
    """Run the agent of chapter 11, unchanged, with its model calls and tool calls recorded."""
    tracer = tracer or Tracer()
    chat, registry = agent.chat, agent.REGISTRY
    agent.chat = traced(tracer, 'model', 'chat', chat)
    agent.REGISTRY = {name: traced(tracer, 'tool', name, fn) for name, fn in registry.items()}
    try:
        with tracer.span('agent', 'run_agent', input=question) as root:
            root['output'] = agent.run_agent(question, verbose=False, **kw)
    finally:
        agent.chat, agent.REGISTRY = chat, registry    # put the originals back
    return root['output'], tracer.spans

Recording the agent of chapter 11 without changing a line of it.

def grade(task, answer, spans):
    """Return {check: passed}. Some checks read the final answer, others read what the agent did."""
    tools = [s for s in spans if s['kind'] == 'tool']
    out = {}
    if 'number' in task:                               # outcome: the right number is in the answer
        found = [float(x) for x in re.findall(r'-?\d+\.?\d*', answer.replace(',', ''))]
        out['answer'] = any(abs(x - task['number']) <= 1e-3 * abs(task['number']) for x in found)
    if 'says' in task:                                 # outcome: the answer uses one of these words
        out['answer'] = any(word in answer.lower() for word in task['says'])
    if 'calls' in task:                                # path: these tools ran, and did not fail
        worked = {s['name'] for s in tools if 'error' not in s}
        out['tools'] = all(name in worked for name in task['calls'])
    if 'retrieves' in task:                            # path: the search found the right passage
        out['retrieval'] = any(task['retrieves'] in str(s.get('output')) for s in tools if s['name'] == 'search_notes')
    return out

From code/ch14_eval.py. The grader: checks on the answer, and checks on the path, read from the trace.

def evaluate(tasks, repeat=1):
    rows = []
    for task in tasks:
        for _ in range(repeat):                        # a real model is random: one run is one sample
            tracer = Tracer()
            try:
                answer, _ = run_traced(task['q'], tracer)
            except OSError:
                raise                                  # no server: stop, this is not the agent's fault
            except Exception as e:
                answer = f'crashed: {type(e).__name__}: {e}'       # a crash is a failed task, with its trace
            checks = grade(task, answer, tracer.spans)
            rows.append({'q': task['q'], 'answer': answer, 'checks': checks,
                         'passed': all(checks.values()), 'spans': tracer.spans})
    return rows

def score(rows):
    """Pass rate, and the standard error that says how far to trust it."""
    n = len(rows)
    p = sum(r['passed'] for r in rows) / n
    return p, math.sqrt(p * (1 - p) / n)

The evaluation, and the number that says how far to trust its result.

What this chapter glossed over

The traces above come from the fake server. Its "model" picks tools with a few rules. The score of 6 in 9 describes those rules and no model. Its timings are also unlike a real run: a real model call takes seconds and dominates the trace, while the tools still take milliseconds. Run code/ch14_eval.py against the server of chapter 10 to see your own model's version.

Graders are the hard part. A check for "397.8" fails a correct answer that says "about 398". Loosen it and it passes wrong ones. For free-form answers people often ask a second model to judge. That judge is itself a model that makes mistakes: before trusting it, compare its verdicts with your own on a sample.

Comparing on the same tasks is sharper. The experiment above gives each system fresh tasks. If both versions run on the same tasks, compare task by task: which ones flipped from fail to pass, and which the other way. That removes the luck of the draw in the tasks.

A real model is random. With sampling on, the same task can pass once and fail once. Run each task several times (--repeat) and count runs, not tasks.

A trace contains everything. The user's words, the retrieved documents, the tool results. It deserves the same care as the data it copies. On your own machine it is a file you control, which is one more argument for running locally.

Tools exist for this. Tracing products add token counts, cost, a viewer and a shared record format. What they record is what the twenty lines here record.

Check yourself

On an arithmetic task the answer check passes and the tools check fails. What happened, and does it matter?

The model gave the right number without calling the calculator. It computed in its own weights, which is unreliable for anything but small numbers. The user saw a correct answer this time. The path check caught a habit that will produce wrong answers later.

After a prompt change the score goes from 14 of 20 to 16 of 20. What have you learned?

Little from the count. At 20 runs the standard error is about ten points, and the change is ten points. Look instead at which tasks flipped. Two that now pass and none that broke, with traces showing the intended behaviour, is real evidence. To rank the two prompts by score alone you need many more tasks.

The tracer stores a copy of each input, not the input itself. Why?

The agent keeps one list of messages and appends to it at every step. A span that stored the list itself would show, after the run, the final conversation in every model span. The copy freezes what the model received at that moment.

In a real trace the model spans take four seconds each and the tool spans two milliseconds. Where do you look to make the agent faster?

At the model calls: fewer steps, less text in the window, a stable beginning of the conversation so the cache of chapter 8 can be reused, or a smaller model. Speeding up the tools would change nothing you could notice.
