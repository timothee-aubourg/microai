Chapter 27

Many people at once

One model, a hundred people asking. Does each of them have to wait for the ninety-nine others?

Every chapter so far has had one reader and one model. A model that is offered as a service answers many people at the same moment, on the same weights. If each request had to wait for the one before it to finish, a service with a hundred users would feel a hundred times slower than the model on your own machine. It does not, and the reason is the one chapter 18 gave for the speed of a single pass.

Definitions

Latency is how long one request takes, as the person who made it experiences it.

Throughput is how much work the whole system finishes per second, counted over everybody.

A batch is a group of texts sent through the model together, in one pass.

The two are in tension. A cook who makes one dish at a time serves each guest as fast as possible and few guests per hour. A cook who fills the oven serves more guests per hour, and each waits a little longer. Serving a model is the choice of how full to run the oven.

What a batch costs

A pass does two things: it reads the weights, and it does arithmetic with them for each text. Put sixteen texts in one pass and the arithmetic is done sixteen times. The weights are still read once.

code/ch27_serve.py measures both ends of that. First the course model, whose 1.4 MB sit in the processor's cache (chapter 22), so that reading the weights costs almost nothing and the arithmetic is everything.

People do not arrive together

Real requests arrive at random moments and have different lengths. The simplest batching waits until a batch is full, runs it to the end, and starts the next. Then a request that arrives a moment late waits for a whole batch, and a short request waits for the longest one in its batch.

Definition

Continuous batching rebuilds the batch at every pass. A request joins at the next pass after it arrives and leaves at the pass where it finishes, so nobody waits for anybody else's request to end.

def serve(arrivals, step_seconds, together):
    """Requests arrive at the given times; each wants LENGTH tokens. Returns when each one finished.
    together = 1: one request at a time. together = 16: every pass advances up to 16 requests by one token."""
    waiting, active, done, clock = list(range(len(arrivals))), {}, {}, 0.0
    while waiting or active:
        while waiting and arrivals[waiting[0]] <= clock and len(active) < together:
            active[waiting.pop(0)] = LENGTH                    # a free place: the next request joins, even mid-way
        if not active:
            clock = arrivals[waiting[0]]                       # nothing to do: wait for the next arrival
            continue
        clock += step_seconds(len(active))                     # one pass, for everyone who is active
        for r in list(active):
            active[r] -= 1
            if active[r] == 0:
                done[r] = clock
                del active[r]
    return np.array([done[r] - arrivals[r] for r in range(len(arrivals))])

From code/ch27_serve.py. A server in twenty lines: at each pass, let waiting requests in, advance everyone by one token, let finished ones out.

At half its capacity the one-at-a-time server is the quicker one for most people, because it gives each request the whole machine. As arrivals approach its capacity, waits grow. Past it, they grow without limit: requests arrive faster than they leave, and the slowest of the 2,000 wait more than forty minutes. The server with sixteen places takes three times the load the other can carry, with nearly every request done in under ten seconds.

Turn up the arrivals

Try this. Start at half the capacity of the one-at-a-time server and raise the arrivals step by step. Find the point where its waiting time takes off. Then switch to the small model and do the same.

What you should have seen. For the large model the one-at-a-time server holds up to its capacity and then fails abruptly: at one and a half times its capacity the typical wait is already over a thousand seconds, while the server with sixteen places barely moves. For the small model the two servers fail at almost the same point. Batching only helps where a pass is dominated by reading the weights. That is true of every model too large for the cache, and of none that fits in it.

What limits the batch

  • Memory for the context. Every request in the batch has its own KV cache (chapter 22). Sixteen requests with long contexts can need more memory than the weights. This, more than arithmetic, is what caps the batch on a graphics card.
  • Arithmetic, eventually. Reading the weights is shared, the arithmetic is not. As the batch grows the pass slowly lengthens, and each person's tokens arrive more slowly. A service chooses the largest batch at which each user still gets an acceptable speed.
  • Shared beginnings. Requests that start with the same system prompt can share its cached keys and values (chapter 16), which saves both time and memory.
  • Waiting for the first token. People notice the delay before the first word more than the speed after it. That delay is the time to read the prompt, which is why chapter 16's prefix cache matters so much to a service.

Build it

def pass_seconds(model, batch, repeats=7):
    """One pass of the model over `batch` texts of 64 tokens at once. Best of several timings."""
    x = np.random.default_rng(0).integers(0, model.vocab_size, (batch, model.block_size))
    best = 1e9
    for _ in range(repeats):
        t0 = time.perf_counter()
        model.forward(x)
        best = min(best, time.perf_counter() - t0)
    return best

What this chapter glossed over

The queue is a simulation. It uses pass times that were measured, and requests that were invented: 2,000 of them, 48 tokens each, arriving at random. Real requests vary in length and come in bursts.

A matrix is not a model. The 1 GB matrix stands for a model in which reading the weights dominates. A real model adds attention over each request's own context, which is not shared.

One core, no graphics processor. On a graphics processor the arithmetic for a batch runs in parallel, so batching helps even more than the second table shows. The small model would also gain there.

The two-vector row. Two vectors took twice as long as one, and four took no longer than two. The library switches to a different routine above one vector. The row is reported as measured.

Left out. Several machines behind one address, deciding which machine takes a request, and what a token costs to serve.

In short

  • Latency is one person's wait. Throughput is the work finished for everybody. Serving trades one against the other.
  • A pass reads the weights once however many texts are in the batch. For a 1 GB matrix, sixteen vectors took 2.3 times as long as one: 7 times the throughput.
  • For a model that fits in the cache there is nothing to share, and batching gained nothing: about 600 tokens per second in total at every batch size.
  • Continuous batching lets requests join and leave at every pass. In the simulation it carried three times the load the one-at-a-time server can carry, with nearly every request done in under ten seconds.
  • The batch is limited by the memory each request's context needs, and by the speed each user will accept.

Check yourself

Why does a batch of sixteen cost little more than a batch of one for a large model, and sixteen times more for our small one?

For the large model most of a pass is spent fetching the weights from memory, and that happens once per pass whatever the batch. For the small model the weights sit in the cache, fetching is free, and all the time is arithmetic, which is done once per text.

With sixteen together, each person's request took 9.7 seconds, not 4.2. Is the batched server worse for users?

For a user who would otherwise be served at once, yes, a little. For the sixteenth user of a busy server it is far better: 9.7 seconds against 67. Which matters depends on how busy the server is, which is what the experiment shows.

A graphics card has room for the weights and 20 GB more. Each request's context needs 2 GB of KV cache. How large can the batch be?

Ten. Each request in the batch needs its own cache, and ten of them fill the 20 GB. Shorter contexts, or a shared prefix, allow more.

Why does a server past its capacity get slower and slower, instead of settling at a slow speed?

Requests arrive faster than they are finished, so the line of waiting requests grows for as long as that lasts. Each new arrival waits for a longer line than the one before.
