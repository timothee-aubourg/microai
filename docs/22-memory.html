Chapter 22

Where the weights live

A model writes as fast as memory delivers its weights. Which memory, and what happens when the model is too big for it?

Chapter 18 gave one rule for the speed of a large model: tokens per second is at most the memory's speed divided by the model's size. It treated memory as one thing. A real computer has several memories, and they differ a great deal in size and in speed. Three questions sort them out. How much does it hold? How fast does it deliver? And which processor can reach it?

This chapter follows the weights through each of those places: the small fast memory inside the processor, ordinary RAM, the memory on a graphics card, the single shared pool of recent laptops and small desktops, and the disk the file came from.

A ladder of memories

Start with something you can measure on any machine. Take a block of numbers and read all of it, again and again, and count the gigabytes read per second. Then make the block bigger. code/ch22_memory.py does this with blocks from 256 KB to 1 GB. This is what it printed on the computer that built this course.

Size of the blockRead per second, one core

The same instruction, on the same processor, runs about 4 times faster on a small block than on a large one. Nothing changed in the arithmetic. What changed is where the block sits.

A processor keeps a little memory of its own, on the same chip, a few millimetres from where the arithmetic happens. This one has three layers of it, of 48 KB, 2 MB and 260 MB, each larger and slower than the one before. The steps in the table are those layers. Blocks up to 1 MB fit in the 2 MB layer. Blocks from 4 MB to 256 MB fit only in the 260 MB layer. The 1 GB block fits in none of them. It has to come from the RAM modules elsewhere on the board, and the processor has to wait for it.

Definitions

The cache of a processor is a small, very fast memory on the processor's own chip. It holds copies of the data used most recently. It is not the KV cache of chapter 8, which is something a program keeps.

RAM is the main memory of the computer: large, slower than the cache, and emptied when the power goes off.

Memory bandwidth is how many gigabytes per second a memory can deliver to the processor that reads it.

By hand: where does our model sit?

Our model has 345,504 weights of 4 bytes each: 345,504 × 4 = 1,382,016 bytes, about 1.4 MB. That fits in the 2 MB layer of this processor's cache. So memory is not what limits it, as chapter 18 found.

A model of 8 billion weights at 4.85 bits each takes 8 × 4.85 ÷ 8 = 4.85 GB. No cache holds that. Every token it writes, all 4.85 GB travel from RAM to the processor, at the speed of the bottom row of the table.

Two pools and a narrow door

Chapter 18 showed why this arithmetic wants a graphics processor. A graphics card brings its own memory with it, soldered beside its processor and built for speed. A desktop computer with such a card therefore has two separate pools of memory, each next to its own processor.

Definitions

VRAM is the memory on a graphics card. Only the graphics processor reads it directly. It is several times faster than RAM and, on cards sold to individuals, between 8 and 32 GB.

To offload layers is to place some of a model's layers on the graphics card and leave the rest in RAM, to be computed by the CPU.

The two pools are joined by a slot on the board. That link is the narrow door. By its specification it carries about 32 GB per second in the version common on current boards (16 lanes, each of 16 gigabits per second), against 1,008 GB per second inside a GeForce RTX 4090. So nobody fetches weights through it for every token. The weights cross it once, when the model is loaded. After that, each layer is computed by the processor that sits next to it, and only the small vector for the current token crosses from one side to the other.

By hand: a model that does not quite fit

Take a model of 40 GB, a card with 24 GB of VRAM that delivers 1,008 GB per second, and desktop RAM that delivers 89.6 GB per second. The card takes 24 GB of layers. The other 16 GB stay in RAM.

For each token, every weight is read once, each from where it sits. So it is the times that add up.

WhereWeights thereDelivered atTime per token
VRAM24 GB1,008 GB/s24 ÷ 1,008 = 0.024 s
RAM16 GB89.6 GB/s16 ÷ 89.6 = 0.179 s
Both40 GB0.202 s

One token every 0.202 seconds is at most 4.9 tokens per second. The smaller part of the model, the part in RAM, takes more than seven times as long as the larger part on the card. With all 40 GB in RAM the ceiling would be 2.2. With a 24 GB model entirely on the card it would be 42.

tokens per second ≤ 1 / (GB in the first memory / its speed + GB in the second / its speed + …)

Where does it go, and how fast is that?

Try this. Keep the GeForce RTX 4090 and move the model's size from 20 GB up through 24, 26 and 30 GB. Watch the ceiling as the first gigabytes spill into RAM. Then choose a machine with unified memory and repeat.

What you should have seen. Up to 24 GB the ceiling falls gently, as chapter 18 predicts: 50 tokens per second at 20 GB, 42 at 24 GB. Then it drops off a ledge. At 26 GB it is 22, about half, although only 2 GB of the 26 are in RAM. Those 2 GB are read eleven times more slowly, and take about as long as the 24 GB on the card. On a machine with unified memory there is no ledge. The same slide gives a smooth curve that starts lower and keeps going, far past the sizes where the card had already given up.

One pool

The second way to build a computer puts the CPU and the graphics processor on one chip and gives them a single memory to share.

Definition

Unified memory is one pool of memory that the CPU and the graphics processor both read directly. There is no separate VRAM, and nothing has to be copied from one side to the other.

Phones have always been built this way. Apple's computers have been since 2020, and several small desktops sold for running models locally now are too. These are the makers' published figures, with the ceiling of this chapter's 40 GB model worked out from them.

Three things follow from the table.

  • Unified memory is slower than VRAM and much larger. A model that fits on a card runs faster on the card. A model that does not fit on any card you own runs on the unified machine, and that is the comparison that counts.
  • The pool is shared with everything else. The operating system, the browser and the model all draw on it, so the whole of it is never free for weights. Makers set a limit: on the AMD machine above, up to 96 of the 128 GB can be assigned to the graphics processor.
  • It is fixed at purchase. To reach those speeds the memory is soldered next to the chip. You cannot add more later, as you can with RAM modules or a second graphics card.

This is also why chapter 20's experts matter so much on these machines. A mixture of experts needs a great deal of memory to hold and reads only a small part of it for each token. A large, moderately fast pool is exactly what that asks for.

The context needs room too

The weights are not the only thing that must fit. Chapter 8 introduced the KV cache: for every token in the window, every layer keeps one key and one value, so that earlier tokens need not be recomputed. It sits in the same fast memory as the weights, and it grows with the length of the conversation.

By hand

Our model has 3 layers, vectors of 96 numbers and a window of 64 tokens. Two vectors per token per layer:

2 × 3 layers × 96 numbers × 64 tokens = 36,864 numbers = 147,456 bytes

That is about a tenth of the 1.4 MB of weights. Now a full-size model. Llama 3.1 8B has 32 layers and keys of 1,024 numbers, stored on 2 bytes each.

Tokens in the windowKV cacheWeights at 4.85 bits

With the window filled to the 131,072 tokens this model allows, the cache is three and a half times the size of the model. A long session with an agent (chapter 16) can run out of memory with a model that fitted easily at the start.

Does it still fit with its context?

Try this. Take the 8-billion-weight model on a 12 GB card. It fits. Now lengthen the context step by step, and find the length at which it stops fitting. Then try the same on a machine with more memory.

What you should have seen. At 8,192 tokens the model and its cache take 5.9 GB of the 12. The total passes 12 GB a little above 50,000 tokens. Nothing about the model changed. Only the conversation got longer. When that happens a runtime either refuses the request, or moves part of the model to RAM and falls off the ledge of the first experiment.

Getting it into memory

Before any of this, the file has to get from the disk into memory. There are two ways to open it, and ch22_memory.py times both on a file of 256 MB.

Definition

To map a file is to ask the operating system to make it appear as memory without copying it. Each part is fetched from the disk the first time it is touched.

Runtimes such as llama.cpp map the model file. The program starts at once, two programs that use the same model share one copy, and if memory runs short the operating system can drop pages of the file and fetch them again later.

That last convenience is also a trap. If the model is larger than the free memory, the system keeps dropping and refetching pages, and every token then waits for the disk. A fast disk delivers a few gigabytes per second, a small fraction of what RAM does. The model still runs, at a token every few seconds, and nothing on the screen says why.

Other places a model runs

  • Several graphics cards. The layers are divided among the cards, and the vector for the current token is handed from one to the next. Their memories add up, so two 24 GB cards hold a 40 GB model. The speed is still that of one card's memory, because each weight is still read once per token.
  • A phone. Unified memory, usually 8 to 16 GB shared with everything else, at well under 100 GB per second. Small models at a few bits per weight are what fit, which is the subject of chapter 23.
  • A neural processing unit. Many recent laptops and phones carry a third processor built to run small networks at very low power. Whether a given runtime can use it for a language model depends on the runtime and on the model. Check before counting on it.
  • A data-centre card. The same design as a desktop card with more memory, of a faster kind, and many of them wired together. The sums of this chapter are the same sums with larger numbers.

Build it

def read_speed(nbytes, seconds=0.25):
    """Read a block of `nbytes` again and again. Returns gigabytes read per second."""
    block = np.ones(nbytes // 4, dtype=np.float32)
    np.dot(block, block)                              # once to warm up
    reads, t0 = 0, time.perf_counter()
    while time.perf_counter() - t0 < seconds:
        np.dot(block, block)                          # touches every number once
        reads += 1
    return reads * nbytes / (time.perf_counter() - t0) / 1e9

def ladder(sizes):
    return [(n, max(read_speed(n) for _ in range(3))) for n in sizes]

def ceiling(places):
    """At most how many tokens per second, when the weights are spread over several memories?
    places: (gigabytes that sit there, gigabytes per second it delivers), one pair per memory."""
    seconds_per_token = sum(gb / speed for gb, speed in places)   # every weight is read once per token
    return 1 / seconds_per_token

A model spread over several memories. Times add up.

def kv_cache_bytes(layers, width, context, bytes_per_number=2):
    """Each layer keeps one key and one value (2 vectors of `width` numbers) for every token in the window."""
    return 2 * layers * width * context * bytes_per_number

def load_two_ways(nbytes):
    """Write a file of `nbytes`, then open it twice: by reading it all, and by mapping it."""
    with tempfile.NamedTemporaryFile(delete=False) as f:
        f.write(np.ones(nbytes // 4, dtype=np.float32).tobytes())
    t0 = time.perf_counter()
    with open(f.name, 'rb') as g:
        copy = g.read()                                   # every byte is copied into our memory now
    t_read = time.perf_counter() - t0
    t0 = time.perf_counter()
    with open(f.name, 'rb') as g:
        view = mmap.mmap(g.fileno(), 0, access=mmap.ACCESS_READ)   # nothing is copied: pages arrive when touched
    t_map = time.perf_counter() - t0
    t0 = time.perf_counter()
    first = np.frombuffer(view, dtype=np.float32, count=1024).sum()   # use the first 4 KB
    t_first = time.perf_counter() - t0
    del first, copy
    os.remove(f.name)
    return t_read, t_map, t_first

What this chapter glossed over

The ceilings are ceilings. As in chapter 18, real speeds are commonly half to three quarters of them. The published bandwidth of a unified memory is shared by the CPU and the graphics processor, and a model rarely gets all of it.

The split is by layers. A runtime places whole layers on the card, so the share on the card moves in steps, and the KV cache of each layer goes with it. The experiment treats it as a smooth quantity.

Keys are narrower than the model. The 1,024 numbers per key of Llama 3.1 are a quarter of that model's width of 4,096. Recent models share each key among a group of attention heads to make the cache smaller. A model without that trick needs four times the cache.

The ladder was measured once, on one machine. It is a server processor with an unusually large cache. A laptop's ladder has the same shape with different numbers, and the script prints yours.

The loading times do not include the disk. The file had just been written and was still held in memory by the operating system. The table times the copy that reading makes and mapping avoids.

Left out. Memory spread over several processor sockets, the difference between the kinds of RAM chips, heat and power limits, and how servers with many cards are wired.

In short

  • A computer has several memories. Each step away from the processor is larger and slower: cache, RAM, disk. On the machine that built this course, a block that fits in the cache is read about 4 times faster than one that does not.
  • A graphics card has its own fast memory, VRAM. A model that fits there runs at its speed. A model that does not is split, and the times add up: 2 GB too many can halve the speed.
  • Unified memory is one pool for CPU and graphics processor: slower than VRAM, much larger, shared with the rest of the system, and fixed at purchase.
  • The KV cache needs room beside the weights and grows with the context: 17.2 GB for an 8-billion-weight model at 131,072 tokens.
  • Model files are mapped, not read. If the model is larger than free memory, every token waits for the disk.

Check yourself

A friend's 16 GB card runs a 14 GB model at 40 tokens per second. They load a 20 GB model and get 6. The card is the same. What happened?

4 GB of the model did not fit and stayed in RAM, where the CPU computes those layers. Time per token is the sum over both memories, and RAM is around ten times slower per gigabyte, so the small part in RAM dominates.

Why can a machine with 128 GB of unified memory at 273 GB per second be the better choice than a card with 32 GB at 1,792?

For any model above 32 GB. The card cannot hold it, so part of it runs from RAM at RAM's speed. The unified machine holds all of it in one pool and reads all of it at 273 GB per second. For a model that fits in 32 GB, the card is several times faster.

A model fits with 3 GB to spare. After an hour of work with an agent it slows to a crawl. Name a likely cause.

The context grew, and the KV cache with it, until model and cache no longer fitted in the fast memory. Shortening the context (chapter 16) brings the speed back.

Our own model runs at thousands of tokens per second on one CPU core. Which memory is it read from?

The processor's cache. At 1.4 MB it fits there, so the weights never have to travel from RAM. That is the subject of the next chapter: a model small enough changes which rung of the ladder it lives on.
