Chapter 18

The machine underneath

Why does a language model want a graphics card, and what decides how many tokens per second you get?

The same model file can write three words a second on one computer and two hundred on another. Chapter 9 explained how large the file is. This chapter explains why the machine around it matters so much, starting from what the work is made of.

One kind of work, repeated

Open any layer of chapter 6 and you find the same operation: multiply a number by a weight, add it to a running total.

Definition

A multiply-add is one multiplication followed by one addition to a running total. It is the unit in which the work of a model is counted.

By hand: counting the work

Chapter 5 multiplied the vector (2, 1) by a matrix with the columns (1, 0) and (0.5, −1):

Entry of the resultComputationMultiply-adds
first2 × 1 + 1 × 02
second2 × 0.5 + 1 × −12

Four multiply-adds, one for each number in the matrix. That holds at any size: multiplying a vector by a matrix costs one multiply-add per weight in it. To write one token, each weight in the model is used about once. So our model of 345,504 weights does a few hundred thousand multiply-adds per token, and a model with eight billion weights about eight billion.

Two properties of this work decide everything that follows. It is completely regular: the same step, over long rows of numbers, with no decisions in between. And it touches every weight, every token.

Two kinds of processor

Definitions

A CPU is the processor that runs a computer's ordinary programs. It has a handful of cores, each able to work through its own list of instructions.

A GPU, the graphics processor, has thousands of simple lanes that all do the same operation at the same time, and its own fast memory next to them.

A CPU is built for variety. It has few cores, often 8 to 16, and each is very good at following instructions that branch and change from one moment to the next. Each core can also do the same operation on 8 or 16 numbers at once.

A GPU was built to colour millions of pixels, which is the same small calculation for each pixel. It is poor at varied work and superb at regular work.

The arithmetic of a model is the most regular work there is. That is the whole reason for the match.

You can feel the value of regularity without a GPU. Here is one matrix-times-vector product, 262,144 multiply-adds, done twice on the same CPU: once as a plain loop, one step at a time, and once handed over as a single block to numpy, the library of fast number routines that all the code of this course uses.

How the work is presentedTimeMultiply-adds per second
One at a time, in a Python loop6.39 ms41 million
As one block, to numpy0.0115 ms22,700 million

The same numbers, the same result, 554 times faster. Measured with code/ch18_hardware.py on the machine that built this page. Most of the gap is the overhead of Python, and the rest is the processor being allowed to do several numbers per step and keep them close at hand. A GPU pushes the same idea much further.

On this CPU, each input gets about 2.5 times cheaper. On a GPU, with far more lanes to fill, the effect is much larger. Two things you have met depend on it. Reading a prompt is fast per token because all its positions go through together (chapter 16). And a server answers many users at once by pushing their tokens through the model side by side, which is called batching. Chapter 27 measures it.

The real limit: how fast memory delivers

Writing is different from reading. It produces one token at a time, so there is nothing to put side by side. And for each token, every weight must travel from memory to the processor. For a large model that journey, not the arithmetic, is what takes the time. The rate at which memory can deliver is the memory bandwidth of chapter 9, in gigabytes per second, and it sets a ceiling:

tokens per second ≤ memory bandwidth / size of the model

One core of the machine that built this page reads memory at about 12 GB per second. An eight-billion-weight model at 4.85 bits per weight (chapter 9) is 4.85 GB. Twelve divided by 4.85: at most about three tokens per second, however fast the arithmetic. The same sum on other hardware:

Bandwidths are the published figures for each product. The DDR5 row is computed: 5,600 million transfers a second, 8 bytes each, two channels. Real speeds are lower than the ceiling, commonly half to three quarters of it.

This one line explains several things at once. A graphics card is fast at writing mainly because its memory is fast. Quantization (chapter 9) speeds a model up because fewer bytes have to travel. And a model twice as large writes half as fast on the same machine.

What will it do on that machine?

Try this. The widget starts on a graphics card with 24 GB of memory and a model of 8 billion weights at 5 bits each. Grow the model to 20 billion weights, then to 40. Then lower the bits per weight to 3. Then pick other machines.

What you should have seen. At 8 billion weights the model is 5.0 GB, it fits, and the ceiling is 202 tokens per second, with 101 to 151 to expect in practice. At 20 billion it is 12.5 GB and the ceiling falls to 81: a larger model is slower on the same machine. At 40 billion it is 25.0 GB and does not fit in 24 GB, and the widget says the ceiling no longer applies. At 3 bits per weight the same 40 billion weights take 15.0 GB, fit again, and have a ceiling of 67.

It has to fit

The second number on a graphics card is the size of its memory. The weights, plus the KV cache of chapter 8, must fit in it. If they do not, part of the model stays in ordinary RAM and is computed by the CPU, and the speed falls toward the slower of the two. A card with less memory is not a slightly slower card. For a model that does not fit, it is a different class of machine.

Apple's recent computers make the opposite trade. Their memory is one pool shared by CPU and GPU: slower than a graphics card's own memory, and much larger. They run big models at moderate speed, where a single graphics card cannot load them at all. Chapter 22 goes through these kinds of memory one by one.

Training asks for more

Everything above is about using a model. Training (chapter 7) multiplies the demand. It processes many examples at once, keeps the intermediate numbers of every layer for the backward pass (chapter 3), and repeats this millions of times. That is why a model is trained on rooms full of GPUs and then runs on one.

Measure this device

Try this. Press the button. Your own phone or computer will do the three measurements of this chapter, in the browser, in about a second.

What you should have seen. Three results, which depend on your device. On the machine that built this page: 419 million multiply-adds per second in one lane, so an 8-billion-weight model would take about 19 seconds per token at that rate. Memory read at about 5.6 GB per second, a ceiling of 1.1 tokens per second for a 4.85 GB model. And the model of this course at 1,481 tokens per second, because it is 23,155 times smaller. A browser uses one lane and none of the processor's tricks, so these are low figures for any device. The point is the gap between the first two results and the third.

Build it

def multiply_one_at_a_time(A, x):
    """A matrix times a vector, written out: for each row, multiply and add along it."""
    out = []
    for row in A:
        total = 0.0
        for a, b in zip(row, x):
            total += a * b                 # one multiply-add: the unit of work of a neural network
        out.append(total)
    return out

From code/ch18_hardware.py. The slow version of a matrix product: one multiply-add per pass through the inner loop. The fast version is A @ x.

What this chapter glossed over

No GPU was used. The measurements are from one CPU. The GPU figures are published specifications, not measurements made for this course.

The ceiling is for one stream of text. A server writing for many users at once reads the weights once per step for all of them, so its total rate can be many times the single-stream ceiling. Then arithmetic becomes the limit again.

Reading a prompt is limited by arithmetic. The prefill of chapter 16 does a great deal of computation for each byte of weights fetched, so it is limited by the processor's speed and not by memory.

More than two kinds of chip. Phones and laptops now carry small neural processors, and data centres use chips made only for this arithmetic. The two questions stay the same: how many multiply-adds per second, and how fast can the weights arrive.

Power and heat. A laptop slows down when it gets warm. Sustained speed can be well under the first minute's.

In short

  • The work of a model is multiply-adds, about one per weight for each token written: eight billion for an eight-billion-weight model.
  • The work is perfectly regular, which suits a GPU: thousands of lanes doing the same step. Handing the same work over as one block made it 554 times faster on one CPU.
  • Processing many inputs together costs less per input. Reading a prompt and serving many users both depend on that.
  • Writing is limited by how fast memory delivers the weights: tokens per second ≤ bandwidth ÷ model size.
  • The model and its cache have to fit in the fast memory. One that does not fit runs far slower than the sum predicts.

Check yourself

A matrix has 96 rows and 384 columns. How many multiply-adds does it cost to multiply one vector by it?

96 × 384 = 36,864, one for each weight in the matrix. This is the first matrix of the MLP in our model, used once for every position.

You quantize a model from 16 bits per weight to 4. The arithmetic is the same number of multiply-adds. Why does it write faster?

Because a quarter as many bytes have to travel from memory per token, and for a large model that travel is the limit. The ceiling, bandwidth divided by size, goes up fourfold.

A 12 GB model on a graphics card with 8 GB of memory runs far slower than the bandwidth sum predicts. Why?

It does not fit. A third of the weights sit in ordinary RAM and are processed by the CPU, at the CPU's memory speed. Every token has to pass through that slow third.

Why can a server answer forty users at nearly the speed of one, while one user cannot get a forty-times-faster answer?

Forty streams can be put side by side: one trip through the weights serves all of them. One stream is a chain, each token waiting for the last. You can widen the road, and you cannot shorten the queue.

The loop and the numpy call did the same 262,144 multiply-adds. Where did the factor of 554 come from?

Mostly from overhead around each step in the loop: looking up what to do next, wrapping every number in an object. The block version runs a tight routine that does several numbers per instruction and reads memory in order. Regular work only pays when it is presented as a block.
