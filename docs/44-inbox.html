Chapter 44

Asleep most of the time

An agent that works for you all day is not running all day. What wakes it, and what stops two wake-ups from trampling each other?

Every agent so far was called by someone who then waited for the answer. An always-on agent works while nobody waits: it answers a message that came in at night, reacts when a payment fails, checks on something it promised to check. It runs the same loop as the agent of chapter 15. What changes is everything around the loop.

The first surprise is that such an agent is asleep almost all the time. It wakes for an event, does one short stretch of work, saves what happened, and sleeps again.

Definitions

An event is anything that should wake the agent: a message from the person, a notification from another service (a webhook), or a timer it set itself (chapter 45).

A run is one stretch of work: read the new events, act, save what happened. A session is the record of messages and tool calls a run works in, which a later run can open again.

An event inbox is a table where every event is written before anything else happens, with an id and a status. A worker reads the table, and only the worker starts runs.

By hand: one minute of a busy afternoon

At 14:00:00 the person sends "move my 3 pm to 4 pm". At 14:00:15 they add "and tell Sam". At 14:00:40 a calendar service sends a notification about the change, and at 14:03:00 it sends the same notification again, because it did not hear back. Each run takes 20 seconds to start and 10 seconds per event it handles.

Calling the agent directly from each source starts four runs: at 14:00:00, 14:00:15, 14:00:40 and 14:03:00. The first two overlap. Both read the agent's notes when they start and write them back when they end, so the second write, at 14:00:45, replaces the first, made at 14:00:30, with a copy that never saw "move my 3 pm". And the duplicate notification is handled twice.

With an inbox, the four events are written to the table as they arrive. The second notification has the same id as the first and is not written again. One worker takes the first message at once (14:00:00 to 14:00:30), then the second (14:00:30 to 14:01:00), then the notification (14:01:00 to 14:01:30). Three runs instead of four, one after the other: nothing overwritten, nothing done twice.

A working day, three ways

code/ch44_inbox.py simulates 20 working days of eight hours for one person. Each day brings 40 bursts of one to three messages from the person, half a minute apart at most, and 60 notifications from other services, of which 15% are sent a second time with the same id. One run in twenty crashes part-way. Every run reads the agent's memory when it starts and writes it back when it ends. Nothing here needs a model: a run's length stands for its model passes.

Averages per day over 20 simulated days, of about 150 events (142 different ones). "Memory overwritten": runs whose saved work was replaced by another run that had read memory before it.

  • Direct calls lose and repeat. A crashed run takes its event with it: 6 a day, gone without a trace. The 8 notifications sent twice are acted on twice. And because a burst of messages starts runs that overlap, 52 runs a day have their saved work overwritten by another one.
  • An inbox fixes all three by construction. The table keeps an event until a run has finished it, so a crash only delays it. The id stops a duplicate at the door. One worker means one run at a time, so nothing overwrites anything.
  • Batching saves runs. Taking every waiting event together cut 149 runs to 126, and the busy time from 75 to 67 minutes, because the fixed start of a run is paid once per batch.
  • The price is waiting. A direct run starts at once. With one worker, an event that arrives during a run waits for it: up to about 3 minutes here, after a crash.

Events that arrive during a run

The person sends "actually, make it 5 pm" while the run about "move my 3 pm" is still working. Three choices: leave it for the next run, fold it into the running one at its next step, or stop the run and start again with both. Folding in is what a person would do. It needs the run to look at the inbox between its steps.

One simulated day

Try this. Run a day each way and compare the timelines. Then raise the chance of a crash and watch what each way does with the events of a crashed run.

What you should have seen. With direct calls, runs stack on top of each other during bursts, and crashed runs (raspberry) leave their events lost. With the inbox there is never more than one run at a time, a crash is followed by a later run that picks the same events up, and with batching fewer, longer runs cover the same day.

At full size

  • The inbox is a database table. A handler, usually a web address that services can call, writes each event and answers at once. Slower checks, such as screening the text for planted instructions (chapter 17), happen later, inside the run.
  • One inbox per person to start with, and one active worker per inbox. Several workers on one inbox bring back the overwriting this chapter measured.
  • Ids come from the source. Services that send notifications attach an id to each, and send again when they are unsure, so dropping repeats by id is standard.
  • Durable execution engines provide the table, the retries and the single worker as a service, for teams that would rather not build them.

What this chapter glossed over

It is a simulation. The events, crash rate and run lengths are chosen, not measured on a real service. The direction of every result follows from the mechanism; the sizes depend on the choices.

"Overwritten" assumes the simplest memory: read it all at the start, write it all at the end. Memory that merges changes, or locks, overwrites less, at the cost of more machinery.

A crash here happens inside the run. The handler that writes the table can fail too; real systems make that write the one thing that must not fail.

In short

  • An always-on agent sleeps, wakes for an event, does one run, saves, and sleeps again. The loop inside a run is the loop of chapter 15.
  • Calling the agent directly from every source lost 6 events a day to crashes, handled 8 twice, and let overlapping runs overwrite each other's memory 52 times.
  • An event inbox with one worker lost none, repeated none and overwrote none: the table keeps an event until a run finishes it, and drops a repeat by its id.
  • Taking every waiting event in one run cut the runs from 149 to 126. The price of one worker is a wait of up to a few minutes.

Check yourself

Why is "asleep most of the time" the normal state of an always-on agent?

Because it only needs to work when something happens. Between events there is nothing to do, and keeping a model running would cost without doing anything. It wakes for an event, does one run and sleeps.

A notification service sends each event again if it gets no answer within a second. What must the handler do, and what must the inbox do?

The handler answers at once, before any slow work, so that fewer events are sent twice. The inbox drops an event whose id it already has, so the ones that are sent twice anyway are handled once.

Two workers read the same inbox to go faster. What problem from the table comes back?

Two runs at once on the same person's memory: each reads it at its start and writes it back at its end, so one can overwrite the other's work. One worker per inbox avoids it; more workers need memory that merges or locks.

A run crashes. Where are its events, with direct calls and with an inbox?

With direct calls they existed only inside the run, so they are gone. With an inbox they are still in the table, marked pending, and the next worker takes them.
