Chapter 49

Telling it or showing it

You want a finished model to do one particular thing. You can tell it in a few words, or show it examples. Which works, when, and what does each cost?

Chapter 15 put a system prompt at the start of every request, and chapter 16 counted what it costs to read. Neither asked what should be written in it. A prompt steers a model whose weights are fixed, and it has two means: words that say what to do, and examples of it being done. Guides to prompting recommend both. This chapter measures what each one can do, on a model small enough to test exactly.

The measurements need a task where "right" has no room for opinion, where the model can be told some things by name, and where other things have no name at all. Writing letters in a code is such a task.

Two ways to ask

The alphabet has eight letters, a to h. A code swaps every letter for another one. Seven codes have a name, a digit: code 3 moves every letter three places along, and after h comes a again. So code 3 writes a as d, b as e, and g as b. Every other code is drawn at random: there are 40,320 ways to pair eight letters with eight letters, and no name for any of them.

A prompt has three lines. The first can give a name. The second has six places for examples, each a pair of letters: ad reads "a is written d". The third asks for one letter.

Definitions

An instruction is text in a prompt that says what to do. It works through what training attached to its words.

An example, also called a shot, is an input placed in the prompt together with its right output, for the model to imitate. A prompt with a few examples is called few-shot. One with none is zero-shot.

In-context learning is a model doing, from examples in its prompt, something its weights alone would not do. No weight changes, and nothing is kept once the prompt is gone.

By hand: the same question, both ways

Told. The prompt says R 3 and asks for g. Count three places along from g: h, then a, then b. The answer is b. Nothing in the prompt shows a code. You needed to know already what "3" means.

Shown. The prompt says R -, shows the pairs ag cf hb, and asks for c. Look for the pair that starts with c: it is cf. The answer is f. You needed no knowledge of this code. You needed to know how to read a pair.

Now ask for d with the same three pairs. No pair starts with d. The pairs say that g, f and b are taken, so d is written as one of the five letters left, and nothing says which. An example settles the cases it shows.

The model

One model of 152,256 weights was trained on prompts of both kinds, mixed. Half of them used one of the seven named codes: with its name alone, with examples alone, or with both. The other half used a code drawn at random for that one prompt, with one to six pairs and no name. A random code never comes back, so at test time every one of them is new to the model.

Ask for a letter with nothing but a name. The script did it 300 times, each time with one of the seven names and a letter drawn at random. Then it did the same with no name at all.

With a name the model is right every time. With nothing it is right 46 times of 300, about what one guess among eight letters gives, which is 37 or 38. A second count of the same thing, in a table further down, gives 37. So the single character after R carries everything. It can, because training put the seven codes into the weights, eight letters to write for each, 56 in all, and the name picks eight of them.

That is the strength of an instruction, and its limit. One character calls up a whole behaviour. It can only call up a behaviour that training put there. A code drawn at random was never in training, so no character names it.

Its attention (chapter 5) finds the pair that starts with the letter asked and copies the letter after it. This is in-context learning in its plainest form, and it is worth being exact about where the code was learned. Not in the weights: they are the same before and after. The code is in the prompt, and it is gone with it.

It has learned that a code uses each letter once, so it rules out the taken letters and picks among the rest. With six pairs two letters are left, and it is right about half the time. Ruling out is all the examples allow.

By hand: what one more example buys

Draw the letter asked at random, and show k pairs. The letter is in one of them k times in 8, and then the model is right. The other 8 − k times in 8 it guesses among 8 − k letters, and is right once in 8 − k: that comes to 1 time in 8, whatever k is. In all, (k + 1) times in 8. With three pairs, 4 in 8: 150 of 300.

Examples that point at something known

Something else happens when the pairs come from one of the seven named codes, shown without its name. Ask again for a letter that no pair shows.

One pair is enough for 291 of 300. The pair ad does not say what c becomes. But d is three places along from a, the model holds a code that does that, and it answers with that code for every letter. Here the example taught nothing. It pointed at something the weights already held, the way a name does.

These are two different jobs, and real prompts mix them all the time. An example of something the model can already do, a tone or a layout it knows, selects that behaviour, and one or two examples are enough. An example of something new can only be applied where it fits. From outside the two look the same: you add examples and the output gets better. They fail differently. When the model recognises something, it applies it with confidence to every case, including cases where you meant something else. When it recognises nothing, it is right only on what you showed.

When the two disagree

A prompt can say one thing and show another. The model was never trained on such a prompt, so nothing taught it which to believe. The script tried three kinds of disagreement, 300 prompts each.

The name against the pairs

The name is one code and the pairs come from another. The letter asked is in one of the pairs, so both give an answer, and the two answers differ.

The name wins, at least 287 times of 300, against six pairs as against one, with the pair that answers the question in plain view. A likely reason: in training a name was never wrong, and using it needs no search through the pairs. Of two signs that had always agreed, the model leans on the cheaper one.

One pair against the others

Six pairs and no name. Five follow one of the named codes. The sixth, the pair for the letter asked, is wrong. The model copied the wrong pair 300 times of 300. The pattern of the other five, which it used so well when the pair was missing, counts for nothing against a pair that answers the question. With the right name added to prompts of the same kind, it went with the name 290 times, with the pair 8 times, and with neither 2 times.

Two pairs for one letter

A random code, in which two of the pairs give the same letter two different codes. The model followed the earlier pair 187 times, the later one 105 times, and neither 8 times.

Three things to keep from these counts. An example is followed to the letter, mistakes included, so check every one. When a prompt disagrees with itself, the model does not average and does not warn you: it follows one side and writes its answer in the usual confident form. And which side it follows is not a law of language models. It is what this training happened to make easy. Another model can lean the other way, and the only way to know is to try.

Ask it both ways

As set, the pairs are ed ae fb, and the model agrees with their code on 4 of the 8 letters: the three that a pair shows, and one of the five that none shows, which is the by-hand count for three pairs. With no pair and no name its eight answers mean nothing. With six pairs it is right on the six letters shown and on neither of the other two. Take the pairs from code 3 without saying so, and two pairs, eh ad, are enough for 8 of 8: all six letters that no pair shows come out right, because the model has recognised the code. Now give the name of code 5 above those two pairs. The model writes code 5 for all 8 letters, including e and a, whose pairs say otherwise in the line just above the question. Raising the pairs of code 3 to six changes nothing: still code 5 on 8 of 8.

What each one costs

In this model the name is one character and each pair is two. At full size the same difference is larger. An instruction is a sentence or two, some tens of tokens. An example is a whole input with its whole output, often hundreds of tokens, and a prompt usually needs several.

By hand: 10,000 requests a day

Take an instruction of 30 tokens, and five examples of 150 tokens each, 750 tokens. Both sit in the system prompt, so both are read at every request (chapter 16). Over 10,000 requests a day the instruction is 30 × 10,000 = 300,000 tokens read, and the examples are 750 × 10,000 = 7,500,000. The examples cost 25 times as much to read. A prefix cache makes the fixed beginning cheap to read again, and it does not give back the room: those 750 tokens are in the window of every request.

So the usual order is the cheap means first. Say it. Add examples when saying it is not enough, which is when the thing wanted has no name the model knows: a house style, a layout, the tone of a reply.

At full size

A large model has been trained on far more names than seven, so far more can simply be said. What you measured still holds, and the published guides to prompting say the same things in their own words.

  • Say it plainly first. State what is wanted, for whom, and in what form. Anthropic's guide to context for agents asks for a system prompt at the right altitude: specific enough to guide the model, and not a list of brittle rules for every case.
  • Show what cannot be said. Anthropic's prompting guide recommends three to five examples and asks that they be relevant, varied and clearly set apart from the instructions. Relevant, because an example covers the cases it shows. Varied, because the model copies whatever the examples have in common, including what you did not intend.
  • Make the two agree. Check each example against the instructions before blaming the model. Anthropic's prompting guide warns that a model picks up patterns in the examples that their author never intended. Ours followed the name against the examples, and copied a wrong example when no name was given. Neither is a rule to count on.
  • The prompt is also the tools. The descriptions of chapter 37 are instructions, read at every step. The same care applies to them.
  • Test every change. A prompt is a program in a language nobody has specified. Whether a new sentence helped is a question for the evaluation of chapter 14, on tasks kept aside, with enough runs to tell.

Build it

def shift(k):
    """A code with a name: every letter moves k places along, and h wraps round to a."""
    return {c: LETTERS[(i + k) % 8] for i, c in enumerate(LETTERS)}

def fresh(rng):
    """A code drawn at random, one of 40,320. The model will not have met it."""
    return dict(zip(LETTERS, rng.permutation(list(LETTERS))))

Seven codes with a name, and as many random ones as you like.

def prompt(name, pairs, letter):
    """One line for the name, one line of six places for examples, and the question.
    A pair such as "ad" reads: a is written d. An empty place is two dots.
    Every part sits at a fixed place, so the model knows where to look."""
    shown = [a + b for a, b in pairs] + ['..'] * (SLOTS - len(pairs))
    return f'\nR {name or "-"}\nE ' + ' '.join(shown) + f'\nQ {letter}'

The prompt: a name, six places for pairs, one question.

def sample(rng):
    """One training text. A named code comes with its name, with examples, or with both.
    A random code can only come with examples."""
    if rng.random() < 0.5:
        k = int(rng.integers(1, 8))
        code, how = shift(k), rng.random()
        name = NAMES[k - 1] if how < 0.6 else None
        n = 0 if how < 0.4 else int(rng.integers(1, SLOTS + 1))
    else:
        code, name, n = fresh(rng), None, int(rng.integers(1, SLOTS + 1))
    pairs = examples(code, n, rng)
    shown = [a for a, _ in pairs]
    asked = [shown[rng.integers(len(shown))] if shown and rng.random() < 0.6 else LETTERS[rng.integers(8)] for _ in range(ASKED)]
    return prompt(name, pairs, asked[0]) + ' '.join(c + code[c] for c in asked)[1:] + '\n'

The training mix. The model never sees a prompt whose name and pairs disagree.

def answers(model, prompts):
    """The model's letter for each prompt: its favourite among the eight."""
    ids = np.array([[STOI[c] for c in p] for p in prompts])
    allowed = [STOI[c] for c in LETTERS]
    logits, _ = model.forward(ids)
    return [LETTERS[i] for i in np.argmax(logits.data[:, -1, allowed], axis=-1)]

What this chapter glossed over

The task is a toy with exact answers. Letter codes were chosen because every answer can be graded and a code can be new by construction. Real prompts ask for things with no single right output, and there the effect of an example is harder to measure and usually larger.

Reading examples was trained in. This model reads pairs because half its training texts made it. A model trained only on named codes would ignore the line of examples. Large models read examples well because their training text is full of lists, tables and worked cases that reward it.

The layout is fixed. The name, the six places and the question always sit at the same positions. A real prompt is free text. Where a sentence sits, how examples are marked off and what comes last all change the result, and guides give advice on each that this chapter does not test.

Seven names is a small vocabulary. At full size an instruction can combine words the model knows into a request it never saw in that form. Our seven names cannot be combined. The limit you measured, that a name only calls up what training attached to it, is the same. Its edge is much further out.

Nothing here is thinking. Asking a model to reason before it answers is the third common means of prompting. Chapter 21 measures it.

What disagreement does depends on training. The model never saw a name and pairs that disagree, so what it does then was not taught: it is what its weights happen to do. A different training run or a different model may lean the other way, which is the reason to test your own prompts and not to trust a rule about it.

In short

  • An instruction names a behaviour that training put in the weights. Here one character was enough: 300 of 300. It cannot name what training never held.
  • An example shows the behaviour. A code never seen before was written right 300 times of 300 from a pair in the prompt, with no weight changed: in-context learning.
  • An example covers what it shows. On a letter in no pair the model ruled out the letters taken and guessed. Over all letters, k pairs give (k + 1) right in 8.
  • An example can also point at something known: one pair of a named code gave 291 of 300 on letters it did not show.
  • When name and pairs disagreed, this model followed the name at least 287 times of 300. With no name it copied a wrong pair 300 times of 300. It was trained for neither case, so test your own prompts.
  • Examples are read at every request: 25 times the tokens of the instruction in the by-hand count.

Check yourself

Why can a code drawn at random not be asked for by name?

A name works through what training attached to it, and training attached nothing to this code: it did not exist before the prompt. It can only be shown.

Three pairs are shown and the letter asked is in none of them. What is the best a model can do, if the code is a random one?

Rule out the three letters already used and guess among the five left: right one time in five. The examples do not contain the answer, and no amount of skill at reading them will find it there.

The model wrote a letter in a code it had never seen. In what sense did it learn the code?

Only for the length of that prompt. No weight changed. Its attention found the pair and copied from it, and with the next prompt the code is gone. That is in-context learning, and it is different from the training of chapter 3.

A prompt has one instruction and five examples, and the output is wrong in the same way every time. Where do you look first?

At the examples. Check that they agree with the instruction, and look for something all five share that you did not intend: a length, an opening word, a format. A model copies what its examples have in common.

An instruction of 30 tokens does the job on 9 requests of 10. Five examples of 150 tokens each bring it to 10 of 10. What do you need to know before adding them?

What a failure costs against 750 more tokens read on every request, and whether the gain is real: one evaluation of ten requests cannot tell 9 from 10 (chapter 14). Run enough tasks to see the difference, then decide.
