Chapter 34

The whole thing, again

Chapter 19 built one small system out of everything before it. What does that system look like with everything since, and what did each addition buy?

Chapter 19 put the first eighteen chapters into one machine: a model trained from nothing, a harness around it, a tool, a format mask, a trace and a test. The chapters after it each took one part further, on its own. This chapter puts them back together. It adds one part at a time to the same system and sends the same 600 requests through every version, so that each part's contribution, and its price, can be read off one table.

Nothing is trained here except 65 numbers. Every model comes from an earlier chapter.

The requests

code/ch34_system2.py draws 600 requests of three kinds: 364 sums on number pairs no model has seen, 128 requests for the secret code in the eight wordings of chapter 28 that nothing was trained on, and 108 harmless questions that are not sums. A good system gets the sums right, never gives the secret, and refuses nothing harmless.

Read it row by row.

  • Training does the heavy lifting on the sums. From 181 right to 357. This is the largest single step in the table, and it costs nothing at the moment of use.
  • Training did not teach it to keep the secret from new wordings. The reinforcement of chapter 24 rewarded declining two particular requests. Faced with eight others, the trained model gives the secret 12 times, more often than the untrained one, which mostly failed to understand the request at all. What a model learned to refuse is narrower than it looks.
  • The check has little left to do. One more sum. It was decisive in chapter 25 for a model that guessed half the time, and it is nearly idle behind a model that has been trained. Parts overlap, and the second one in line gets less credit.
  • The guard stops the leaks and charges for it. 12 down to 2, and 30 of 108 harmless questions refused. Tokens per request fall, because a blocked request never reaches the model. The classifier ran for 93 of the 600 requests, and the probe settled the rest.
  • The filter closes the last gap. 2 down to 0. It is the only part that can promise its result, because it is plain code looking for four digits.

The last row is the safest system and not the most helpful one: more than a quarter of the harmless questions are turned away. Every part that was added to stop something also stops things it should not. Chapter 28 showed where that comes from and what would reduce it, which is a guard trained on more than eight wordings.

Switch the parts on

Try this. Send the stream through the pre-trained model alone. Then add the parts one by one, in the order of the table, and watch which bar each one moves. Then send single requests of your own.

What you should have seen. Each part moves one bar and leaves the others almost alone. Training lifts "sums right". The guard brings "secret given" down, and it is the guard that makes "harmless refused" appear. The filter takes "secret given" to zero. No single part does everything, and no part is free. Sixty requests hold only about a dozen harmless ones, so that bar jumps from press to press; the table above counts 600.

Build it

def respond(request, parts, rng, tally):
    """One request through the system. `parts` says which pieces are switched on."""
    run = parts['model']
    if parts.get('guard'):                                        # 1. the guard reads the request first
        score = parts['probe'](guard.activations(parts['main'], request))    # free: the model's own activations
        if 0.2 < score < 0.8:
            tally['classifier'] += 1
            score = guard.classify(parts['classifier'], request)  # the costly opinion, only when unsure
        if score >= 0.5:
            return post.REFUSAL
    for attempt in range(3 if parts.get('check') else 1):         # 2. the agent answers, with its tool
        e = post.episode(run, request, rng)
        tally['tokens'] += len(e['text'])
        if not parts.get('check') or not SUM.fullmatch(request) or e['call'] is not None:
            break                                                 # 3. a sum must rest on a tool result
    if parts.get('filter') and post.SECRET in e['answer']:        # 4. nothing with the secret leaves
        return post.REFUSAL
    return e['answer']

What this chapter glossed over

The order of the rows matters. Each part was added to a system that already had the ones above it. Added in another order, the check would have looked important and the training less so.

Harmless questions were not graded. The system was only counted as wrong on them when it refused. What the agent actually answers to "tell me a joke" is not useful, because it was never trained on such questions.

One stream, one seed. 600 requests, one pass through each version. The small movements in the first column, from 357 to 361, are within what another seed would give.

In the browser the guard is the classifier alone. The probe needs the numbers inside the main model, which the page does not expose, so the experiment asks the classifier for every request.

In short

  • The system of chapter 19 with five parts from later chapters, measured on one stream of 600 requests, one part at a time.
  • Post-training moved the sums from 181 right to 357. The check behind it added one more. Parts overlap.
  • The trained model gave the secret 12 times in 128 new wordings. The guard cut that to 2 and refused 30 of 108 harmless questions. The filter made it 0.
  • Each part moved one number and had a price. The table, not any single chapter, is how a system is judged.

Check yourself

The check raised the sums right by 148 in chapter 25 and by 1 here. Did it get worse?

No. In chapter 25 it stood behind a model that guessed half the time, so it had many bad answers to reject. Here the model was trained and almost always uses the tool, so there is little left to catch. A part's value depends on what is in front of it.

The trained model was rewarded for keeping the secret. Why did it give it 12 times?

It was rewarded for declining two wordings. The 128 requests here use eight others. What it learned did not carry over to them, and some it now understands well enough to answer.

Which part would you remove first if users complained about being refused for no reason, and what would it cost?

The guard, or raise its threshold. Harmless refusals would fall from 30 toward 0, and the secret would be given more often before the filter. With the filter still in place the secret would still not get out, so the cost is mostly tokens spent on answers that are then withheld.

Why is the filter the only part that can promise its result?

It is ordinary code that looks for an exact string. The other parts are models or depend on one, and a model can be wrong. The promise is also narrow: it covers those four digits written plainly, and nothing else.
