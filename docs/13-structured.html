Chapter 13

Staying inside the lines

The agent of chapter 11 stalls when the model writes a tool call your program cannot read. Can you make that impossible instead of unlikely?

In chapter 11 the model asked for a tool by writing text: a name and some arguments, in a fixed layout. Your program parsed that text. One missing bracket or one invented tool name, and there is nothing to run. The loop there sent the error back to the model and hoped for a better second try.

You can raise the odds by asking. "Answer only in this format" in the prompt helps a great deal. But a program is a stricter reader than a person. A format that comes out right 99 times in 100 fails once every hundred calls, and an agent makes many calls per task.

The better fix sits in a place you already own. Chapter 8 showed that the model only produces scores, and that small functions reshape those scores before the dice are rolled. Temperature and top-k reshape them by size. One more function can reshape them by legality: it knows the format, it knows how far along the text is, and it gives every character that would break the format a score of minus infinity. After the softmax, minus infinity is a probability of exactly zero, as with the causal mask of chapter 5.

Definitions

A format is a rule that says which texts are acceptable: "a name in capitals, a colon, a line break, one sentence".

A mask is the list of tokens that the format does not allow at the current step. Their scores are replaced by minus infinity.

Constrained decoding is sampling with such a mask at every step. What comes out is called structured output: text that is certain to fit the format.

The mask rarely had to act, and when it did, the format held.

A format is a small machine

The mask needs one thing: at every step, the list of characters that may come next. Something has to keep track of where the text is in the format. Here a format is a list of parts, read left to right. A part is either "between this many and that many characters from this set" or "exactly one word from this list". The first format in the experiment reads: two to twelve capitals, a colon, a line break, one capital, eight to forty lowercase letters, spaces, commas or apostrophes, one closing mark, a line break.

Call the thing that keeps track a machine. Its whole memory is two things: which part it is in, and what has been written of that part. From there it can answer the only question the sampling code asks. If the current part can still grow, its characters are allowed. If it has reached its minimum, the first characters of the next part are allowed too. When the last part is complete nothing is allowed, and the loop stops. The model gets no vote on stopping.

The model itself never learns that a format exists. It sees the characters written so far, as always, and proposes what it likes. The mask deletes the proposals that do not fit.

The middle columns are the point of the chapter. The mask column is 100% by construction, not by luck: the script asserts it.

The last column is the price, the number from the by-hand example averaged over every step. At each step the model spreads its belief over 65 characters, and the mask deletes the share that sits on characters the format does not allow. For the first format that share averages under 5%. The model was going to write something close to this anyway, and the mask only catches the occasional slip. For the line in capitals it is 26%. The model almost never writes that way, so the mask overrules it again and again, and what comes out is legal and poor. Try it above.

So the mask does not replace the prompt. Describe the format to the model as well, so that it is already trying to produce it. Then the mask is a safety net that is rarely touched, not a hand forcing every character.

Allowed is not the same as likely

The second format restricts the speaker to four names. Three appear in the training text. The fourth, HAMLET, never does. Here is how often the model writes each name on its own, and how often it writes it under the mask:

ROMEO2.18%27.0%

HAMLETunder 0.001%14.5%

Left alone, the model prefers ROMEO and JULIET to MERCUTIO by about thirteen to one. Under the mask MERCUTIO wins. The reason is that the mask works one character at a time. At the first character it keeps R, J, M and H and rescales. Many speakers in the plays begin with M, so M is a likely first letter. Once M is drawn, the list allows only E, then R, and the rest of the name is forced. The model was betting on other names beginning with M and got MERCUTIO. HAMLET rides in on the letter H the same way.

The mask guarantees the shape. It does not promise that, among the legal outputs, you get the one the model thought best. For a choice among a few whole answers, the faithful method is to compare the probability of each whole answer, which is the "model alone" column rescaled to add up to 100%.

On a real model

Three things change at full size, and the idea does not.

Tokens, not characters. A real model draws tokens of several characters (chapter 2). A token is allowed if its characters, taken one after another, are all allowed. The runtime of chapter 10 tests every token in the vocabulary against the machine at each step, and prepares a good deal in advance to keep that fast.

Richer formats. The format you will want most is JSON: the layout of tool calls and of most data passed between programs. JSON nests, one set of braces inside another, so its machine has to remember how deep it is.

Definitions

A grammar is a description of a format that can nest, written as rules a program can follow.

A JSON Schema is a description of the JSON you expect: which fields, and what kind of value in each. It is the same kind of description you gave for the arguments of a tool in chapter 11. Runtimes build the grammar from it.

The stop. A real model ends its turn with a special token. The grammar allows that token only when the format is complete.

The client of chapter 10 passes extra options straight to the server, so asking for structured output is one more argument:

from llm import chat

schema = {'type': 'object',
          'properties': {'city': {'type': 'string'}, 'year': {'type': 'integer'}},
          'required': ['city', 'year']}
reply = chat([{'role': 'user', 'content': 'Where and when was the first modern Olympics? Reply in JSON.'}],
             response_format={'type': 'json_schema', 'json_schema': {'name': 'answer', 'schema': schema}})
print(reply['content'])        # text that always parses, with exactly these two fields

The response_format field as documented for Ollama and for llama.cpp's llama-server. The schema asks for two fields, a city as text and a year as a whole number.

Build it

def moves(fmt, state):
    """Which characters may come next, and which state does each one lead to?
    An empty answer means the format is complete."""
    i, s = state
    out = {}
    while i < len(fmt):
        part = fmt[i]
        if isinstance(part, list):                        # one word from a list
            for w in part:
                if w.startswith(s) and len(w) > len(s):
                    out.setdefault(w[len(s)], (i, s + w[len(s)]))
            may_end = s in part
        else:                                             # min..max characters from a set
            chars, lo, hi = part
            if len(s) < hi:
                for c in chars:
                    out.setdefault(c, (i, s + c))
            may_end = len(s) >= lo
        if not may_end:
            break                                         # this part is not finished yet
        i, s = i + 1, ''                                  # it may be over: the next part may begin
    return out

From code/ch13_constrain.py. The format as a machine: where am I, what may come next.

def generate_constrained(run, prompt, fmt, **sampling):
    cache = run.new_cache()
    for c in prompt:
        logits = run.step(run.stoi[c], cache)
    state, text, removed = START, '', []
    while True:
        legal = moves(fmt, state)                         # ask the format, not the model
        if not legal:
            return text, removed                          # format complete: stop
        mask = np.full(run.vocab, -np.inf)
        mask[[run.stoi[c] for c in legal]] = 0            # 0 for allowed, -inf for everything else
        p = np.exp(logits - logits.max()); p /= p.sum()
        removed.append(1 - p[mask == 0].sum())            # how much of the model's belief the mask deleted
        nxt = run.chars[sample_next(logits + mask, **sampling)]   # the dice of chapter 8, on masked scores
        state, text = legal[nxt], text + nxt
        logits = run.step(run.stoi[nxt], cache)

The generation loop of chapter 8 with one addition: the mask is added to the scores before the draw.

def follows(fmt, text):
    """Does `text` start with something in the format? Returns (characters read, completed)."""
    state = START
    for n, c in enumerate(text):
        legal = moves(fmt, state)
        if not legal:
            return n, True                                # completed; the rest is ignored
        if c not in legal:
            return n, False                               # broke the format at character n
        state = legal[c]
    return len(text), not moves(fmt, state)

The same machine used as a checker, for text written without the mask.

What this chapter glossed over

Shape is not truth. The mask guarantees that a field holds a number. It cannot make it the right number. Check values in your own code, as you would with any input from outside.

A cut-off answer is still broken. If generation hits its length limit halfway through the format, you receive half of it. Leave room, and check why the model stopped.

Our format language is tiny. It has no nesting and no repetition of groups, and it requires that a part which may end shares no character with the part after it, so that one state is enough. Real grammars lift these limits with more bookkeeping and the same mask.

Runtimes support part of it. JSON Schema is large, and each runtime handles some of it. A part it does not know may be ignored without an error. Keep schemas simple.

How this was tested. The masked sampler runs on the model of this course, in Python and in your browser, and the numbers above come from it. The response_format snippet follows the published documentation of Ollama and llama.cpp and has not been run against a real server.

In short

  • Constrained decoding adds one step to sampling: characters the format does not allow get a score of minus infinity, so a probability of exactly 0.
  • The format is followed by a small machine that knows where the text is and what may come next. The model is not changed.
  • Measured on our model: 10.0%, 2.5% and 0.0% of texts fit the three formats without the mask, and 100% with it, at any temperature.
  • The share of belief the mask removes is its price: 4.7% per character for a format the model nearly writes anyway, 26.2% for one it never writes.
  • The mask guarantees the form. It does not make the content right, and among the allowed outputs it does not pick the one the model thought best.

The second, with probability 1: it is the only one left. The mask removed 0.9 of the model's belief. The text fits the format, and the model thought this character unlikely.

You raise the temperature to 2 with the mask on. Can the format break?

No. Temperature divides the scores, and minus infinity divided by anything is still minus infinity. The illegal characters keep a probability of zero at any temperature. What changes is which legal character is drawn.

Why can this course's model not be constrained to write JSON?

Its vocabulary is the 65 characters of the Shakespeare text, and those include no brace, bracket or double quote. A mask can only remove options. It cannot offer a token the model does not have.

On one task the mask removes 0.1% of the model's belief per step. On another it removes 60%. What does each number tell you?

In the first, the model was already writing the format and the mask is insurance. In the second, the mask is overruling the model most of the time. The output will have the right shape and probably poor content. Fix the prompt, or pick a format closer to what the model writes naturally.

You constrain the agent's tool name to the list of real tools and its arguments to each tool's schema. Which failures from chapter 11 disappear, and which remain?

Gone: a tool that does not exist, and arguments that do not parse. Remaining: choosing the wrong tool, and passing well-formed arguments with the wrong values. Those are mistakes of judgment, and the next chapter is about finding them.
