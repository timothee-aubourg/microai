Chapter 15

The program around the model

A coding assistant lists your files, runs your tests and edits a line. A model can only write text. What is the rest made of?

Chapter 11 showed the trick in miniature: the model writes a request, and your program carries it out. Tools that do real work on a real project, such as Claude Code or Pi, are that same trick with more care around it. The program that provides the care has a name: the harness.

A harness is ordinary software. Nothing in it is learned. It consists of five things: a system prompt, a set of tools, a loop, rules about what may run without asking, and some care for the context window. This chapter builds one in a hundred lines and shows exactly what travels between it and the model.

Four tools are enough to start

Our harness gives the model four tools.

ToolWhat the harness does when asked
readReturns the content of a file in the project.
writeCreates a file, or replaces its whole content.
editReplaces one passage in a file. The model quotes the old text, which must occur exactly once.
bashRuns a shell command in the project folder and returns its output.

The first three cover files. The fourth covers everything else a computer can do: run the tests, search, install a package, use git. A model that can write shell commands can use any program that already exists.

This short list is a real design. Pi, an open-source harness, gives the model exactly these four tools by default, with a system prompt of under a thousand tokens. Claude Code makes the other choice and builds in more: next to Bash, Read, Edit and Write it has tools to find files and search their content, to fetch web pages, to keep a to-do list and to start a helper agent, among others. Few general tools keep the request small and leave the model to combine them. Many special tools cost more room in every request and are easier to control one by one.

Note how edit works. The model has no cursor. It can only quote. So it names the place to change by quoting the text that is there now, and the harness refuses if that text is missing or occurs twice.

What the model actually receives

The model takes one sequence of tokens (chapter 6). It has no second input for tools and no third one for results. So before each call the server flattens everything, the system prompt, the tool descriptions and every message so far, into one text. The layout of that text is the model's chat template: the layout it saw in training, with special tokens that mark who is speaking.

The way back is the same. When the model "calls a tool" it writes text in an agreed layout, and the server parses that text into the structured request your loop receives. Below is one task, start to finish, with each request shown as the model gets it.

The loop

The loop has four beats, and it is the loop of chapter 11.

  1. The model writes. Either a request for a tool, or a final answer.
  2. The harness decides. May this request run? The next chapter but one is about this line.
  3. The harness acts. It runs the tool. If the tool fails, the error message is the result.
  4. The result becomes context. It is appended to the conversation, cut down if it is long, and the loop goes around.

Two details matter more than they look. Errors are returned to the model as text, because a model that sees "no such file" can try another path, while a crashed loop cannot. And results are clipped before they go in. One command that prints fifty thousand lines would otherwise fill the window by itself. Our clip keeps the start and the end, which is where commands put what matters.

What real harnesses add

Everything below is more of the same five things.

Instructions from the project. A file in the repository, named CLAUDE.md or AGENTS.md by convention, is read at the start and placed in the system prompt: how to run the tests, what not to touch.

Tools from elsewhere. A protocol called MCP lets a separate program offer tools. The harness asks it for their descriptions and adds them to the request. Each one costs room in every request, used or not.

Helper agents. A tool whose implementation is another loop, with its own fresh window. It does a side task and returns only a summary, so the main window stays small.

Housekeeping. Shortening the conversation when it grows (chapter 16), permissions and a sandbox (chapter 17), traces (chapter 14), and an interface that streams text, shows changes and lets you interrupt.

Pi leaves most of these out on purpose and lets you add them as extensions. Reading a small harness like it is the fastest way to see that there is no further secret.

Build it

def inside(root, path):
    """Resolve `path` inside the project folder, or refuse."""
    root, full = os.path.realpath(root), os.path.realpath(os.path.join(root, path))
    if os.path.commonpath([root, full]) != root:
        raise PermissionError(f'{path} is outside the project folder')
    return full

def read(root, path):
    with open(inside(root, path)) as f:
        return f.read()

def write(root, path, content):
    full = inside(root, path)
    os.makedirs(os.path.dirname(full), exist_ok=True)
    with open(full, 'w') as f:
        f.write(content)
    return f'wrote {len(content)} characters to {path}'

def edit(root, path, old, new):
    text = read(root, path)
    if text.count(old) != 1:                              # the model must point at exactly one place
        raise ValueError(f'the old text occurs {text.count(old)} times in {path}; it must occur once')
    return write(root, path, text.replace(old, new))

def bash(root, command):
    r = subprocess.run(command, shell=True, cwd=root, capture_output=True, text=True, timeout=60)
    return f'exit code {r.returncode}\n{r.stdout}{r.stderr}'

REGISTRY = {'read': read, 'write': write, 'edit': edit, 'bash': bash}

SYSTEM = ('You are a coding assistant working in a project folder on the user\'s machine. '

What the model is told: the tool descriptions and the system prompt. This text is the model's whole knowledge of the harness.

def clip(text, limit=4000):
    """A tool result goes into the context window, so it gets a budget: keep the start and the end."""
    if len(text) <= limit:
        return text
    return text[:limit // 2] + f'\n[... {len(text) - limit} characters left out ...]\n' + text[-limit // 2:]

def run(task, root, approve=lambda name, args: True, max_steps=12, on_step=None):
    messages = [{'role': 'system', 'content': SYSTEM}, {'role': 'user', 'content': task}]
    for _ in range(max_steps):
        reply = llm.chat(messages, tools=TOOLS, temperature=0)       # 1. the model writes
        if on_step:
            on_step(messages, reply)
        messages.append(reply)
        if not reply.get('tool_calls'):
            return reply['content'], messages                        # no request: the model is done
        for call in reply['tool_calls']:
            name, args = call['function']['name'], call['function']['arguments']
            try:
                args = json.loads(args) if isinstance(args, str) else args
                if approve(name, args):                              # 2. the harness decides
                    result = REGISTRY[name](root, **args)            # 3. the harness acts
                else:
                    result = 'denied: this action was not allowed'
            except Exception as e:
                result = f'error: {type(e).__name__}: {e}'           # a failure is also just text
            messages.append({'role': 'tool', 'tool_call_id': call.get('id', ''),
                             'content': clip(str(result))})          # 4. the result becomes context
    return 'Stopped: too many steps.', messages

The loop, with the four beats numbered.

def segments(messages, tools):
    """The request as the model receives it: ONE text, cut here into labelled pieces.
    This follows the layout that Qwen 2.5 models were trained on. Each model family has
    its own, called its chat template, and the server applies it for you."""
    out = [('system prompt', '<|im_start|>system\n' + messages[0]['content']),
           ('tool descriptions',
            '\n\n# Tools\n\nYou may call one or more functions to assist with the user query.\n\n'
            'You are provided with function signatures within <tools></tools> XML tags:\n<tools>\n'
            + '\n'.join(json.dumps(t) for t in tools) + '\n</tools>\n\n'
            'For each function call, return a json object with function name and arguments within '
            '<tool_call></tool_call> XML tags:\n<tool_call>\n'
            '{"name": <function-name>, "arguments": <args-json-object>}\n</tool_call><|im_end|>\n')]
    for m in messages[1:]:
        if m['role'] == 'tool':
            out.append(('tool result', '<|im_start|>user\n<tool_response>\n' + m['content'] + '\n</tool_response><|im_end|>\n'))
        elif m.get('tool_calls'):
            calls = [{'name': c['function']['name'], 'arguments': json.loads(c['function']['arguments'])} for c in m['tool_calls']]
            out.append(('model', '<|im_start|>assistant\n' + '\n'.join(
                '<tool_call>\n' + json.dumps(c) + '\n</tool_call>' for c in calls) + '<|im_end|>\n'))
        else:
            out.append(('user' if m['role'] == 'user' else 'model', f"<|im_start|>{m['role']}\n{m['content']}<|im_end|>\n"))
    return out + [('cue', '<|im_start|>assistant\n')]                # the model continues from here

What this chapter glossed over

The "model" above is a script. The fake server plays one fixed routine: run the tests, read, fix one known bug, run again. It shows what the harness does and says nothing about what a model can do. The harness has not been run against a real model for this course.

Templates differ. The layout shown is the one Qwen 2.5 models were trained on. Other families use other markers and other ways of writing a tool call. Use the wrong one and the model sees a layout it never learned.

With a real model, bash is real. It can delete files and reach the network. Work in a folder you can afford to lose until you have read chapter 17.

Left out. Streaming, interrupting a run, several tool calls in one reply, long-running commands, images.

Check yourself

The model has never been told what edit does in any special way. How does it know?

From the tool description: a name, one sentence and the argument names, which the server writes into the request as text. The model reads it the way it reads anything. A vague description gives a model that misuses the tool.

You connect a server that offers forty more tools. The agent uses two of them. What did the other thirty-eight cost?

Their descriptions are in every request of the session, so they take room in the window and time to read at every step. They can also distract: more choices, more wrong choices. Offer the tools a task needs.

Why does a failed command go back to the model as text, when the harness could stop with an error?

Because the model can often recover: a missing file suggests another path, a failed test says what to fix. Stopping throws away the work so far. The brake against endless retries is the step limit.

Two harnesses use the same model and give different results on the same task. Name three places the difference can come from.

The system prompt, the tool descriptions and which tools exist, how results are clipped or summarised, the step limit, what is loaded from the project at the start. All of it is text in the request, and the request is all the model has.
