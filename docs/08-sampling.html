Chapter 8

Rolling the dice

The trained model outputs 65 probabilities. Why not simply pick the most likely character every time?

Try it and you get a model stuck in a rut. The single most likely continuation of common text is more common text, so always taking the favourite tends to circle through the same safe phrases. The opposite policy, sampling exactly according to the probabilities as chapter 1 did, has its own flaw: the model gives a little probability to many poor options, and over hundreds of draws one of them will be picked and derail the passage.

Good text lives between these two. The settings you see in every model interface are three ways to reshape the probabilities before rolling the dice. None of them touches the model. They act on its output, the logits of chapter 6.

Definitions

Greedy decoding is always taking the most likely token. Nothing is left to chance.

Temperature is a number T by which the logits are divided before the softmax. Below 1 it sharpens the distribution; above 1 it flattens it.

Top-k keeps the k most likely tokens and removes all the others.

Top-p, also called nucleus sampling, keeps the smallest set of most likely tokens whose probabilities add up to at least p, and removes the rest.

pi = softmax(scorei / T)

By hand: three tokens, three settings

Suppose the model gives three tokens the scores 2, 1 and 0. Chapter 5 worked out the softmax of such a list. Here it is at three temperatures:

0.54, 2, 00.87, 0.12, 0.02
21, 0.5, 00.51, 0.31, 0.19

The softmax turns differences between scores into ratios between probabilities. Dividing by 0.5 doubles every difference, so the favourite pulls further ahead: 0.87 instead of 0.67. Dividing by 2 halves every difference and the three tokens move towards equal shares. At a temperature of 1 the model's own probabilities are untouched. As the temperature goes to 0 the favourite takes everything, which is greedy decoding.

Now the two cuts, on the probabilities at temperature 1:

The rescaling divides what is kept by its total: 0.67 / 0.91 = 0.73. Top-k is simple and blunt: sometimes only two options are sensible, sometimes fifty, and k is the same for both. Top-p adapts. When the model is sure, a few tokens reach the threshold and the rest is cut. When it is unsure, many tokens are kept.

Sampling from the trained model

What you should have seen. At 0.8 the next character is open: I 14.4%, T 14.1%, W 13.4%, A 11.5%, and many more. At temperature 0 the bars show I at 100% and the text soon loops: "the state of the state, That will strike an an of the state", again and again. At 2.0 the favourites fall to about 7% each, nearly level with unlikely characters, and the text falls apart into strings like gawfry and dogmunAble. At 0.8 it reads as Shakespeare-like lines with speakers' names. With top-p at 0.90 the tail of the list is cut and the survivors rise a little, I to 15.7%.

Generation is a loop, and the loop is wasteful

To write 200 characters the model runs 200 times, each time on the text so far plus one more character. Done the plain way, step 200 computes again everything it computed for the first 199 characters at step 199. Almost all of that work is repeated.

The causal mask of chapter 5 makes the waste avoidable. An earlier position never reads later ones, so nothing computed for it can change when the text grows. In particular its attention keys and values are fixed for good.

Definition

The KV cache is the store of the keys and values of every token already processed, in every layer. A new token only computes its own query, compares it with the stored keys, and adds its own key and value to the store.

At 64 tokens, a full window of our model, the totals are 45,760 against 2,080: the cache does a twenty-second of the work.

Measured on our model with code/ch08_sample.py, processing the same 60 characters and getting the same outputs to within rounding: 89 milliseconds computing everything again, 33 with the cache. The gap in time is smaller than the gap in comparisons because the model is small and does other work besides. It widens quickly with the size of the model and the length of the text.

The cache explains two things you will notice when running a real model in chapter 10. First, memory use grows with the length of the conversation: the cache stores a key and a value per token, per layer. Second, programs that run models report two speeds. Reading your prompt is fast per token, because all its positions can be processed in one pass. Writing the reply is slower per token, because each token must wait for the one before.

When the window is full

Chapter 2 defined the context window: the most tokens a model can look at in one go. Ours is 64 characters, because the position table of chapter 4 has 64 rows. What happens at character 65?

The generation loop in this repository handles it in the bluntest way: it keeps the most recent half of the text, 32 characters, rebuilds the cache from them, and carries on. Programs that run real models offer the same choice in more refined forms: stop, or drop the oldest part of the conversation and process the rest again. Either way, what falls out of the window is gone. The model has no other memory. Chapter 11 is about living with that.

Build it

def sample_next(logits, temperature=1.0, top_k=0, top_p=1.0, rng=np.random.default_rng()):
    if temperature == 0:
        return int(np.argmax(logits))                 # greedy: always the favourite
    z = logits / temperature                          # <1 sharpens, >1 flattens
    if top_k:
        z = np.where(z < np.sort(z)[-top_k], -np.inf, z)   # keep the k best
    p = np.exp(z - z.max()); p /= p.sum()             # softmax
    if top_p < 1.0:                                   # nucleus: smallest set worth top_p
        order = np.argsort(-p)
        before = np.cumsum(p[order]) - p[order]       # probability mass ranked ahead of each token
        p[order[before >= top_p]] = 0
        p /= p.sum()
    return int(rng.choice(len(p), p=p))

def step(self, token, cache):
    """Process ONE new token. `cache` holds the keys and values of all earlier tokens."""
    w, H, hd = self.w, self.H, self.d // self.H
    pos = cache['pos']
    x = w['wte'][token] + w['wpe'][pos]
    for i in range(self.L):
        a = self.ln(x, w[f'h{i}.ln1.g'], w[f'h{i}.ln1.b'])
        q = (a @ w[f'h{i}.attn.wq']).reshape(H, hd)            # only the NEW token asks a question
        cache['k'][i].append((a @ w[f'h{i}.attn.wk']).reshape(H, hd))
        cache['v'][i].append((a @ w[f'h{i}.attn.wv']).reshape(H, hd))
        K = np.stack(cache['k'][i], axis=1)                    # (H, pos+1, hd): old keys are reused
        Vv = np.stack(cache['v'][i], axis=1)
        s = np.einsum('hd,htd->ht', q, K) / np.sqrt(hd)        # one row of scores, not a T x T table
        s = np.exp(s - s.max(-1, keepdims=True)); s /= s.sum(-1, keepdims=True)
        x = x + np.einsum('ht,htd->hd', s, Vv).reshape(self.d) @ w[f'h{i}.attn.wo']
        h = self.ln(x, w[f'h{i}.ln2.g'], w[f'h{i}.ln2.b']) @ w[f'h{i}.mlp.w1']
        h = 0.5 * h * (1 + np.tanh(np.sqrt(2 / np.pi) * (h + 0.044715 * h * h * h)))
        x = x + h @ w[f'h{i}.mlp.w2']
    cache['pos'] += 1
    return self.ln(x, w['ln_f.g'], w['ln_f.b']) @ w['wte'].T

One new token through the model, reusing the keys and values of all earlier ones.

def generate(self, prompt, n, on_token=None, **sampling):
    ids = [self.stoi[c] for c in prompt]
    cache = self.new_cache()
    for t in ids[-self.block:]:                    # "prompt processing": fill the cache
        logits = self.step(t, cache)
    for _ in range(n):
        nxt = sample_next(logits, **sampling)      # draw one token...
        ids.append(nxt)
        if on_token:
            on_token(self.chars[nxt])
        if cache['pos'] == self.block:             # context window full: keep the recent half
            cache = self.new_cache()
            for t in ids[-self.block // 2:-1]:
                self.step(t, cache)
        logits = self.step(nxt, cache)             # ...and feed it back in
    return ''.join(self.chars[i] for i in ids)

The loop that turns a predictor into a writer.

What this chapter glossed over

There is no best setting. Low temperature suits tasks with one right answer, such as extracting a date. Higher temperature suits tasks where variety is the point. Defaults around 0.7 to 1.0 with a top-p near 0.9 are conventions, not laws.

Same prompt, different answers. Sampling is random by design. Fixing the random seed makes a run repeatable on the same machine and software. Temperature 0 removes the dice, though tiny numerical differences between machines can still change a close call.

More settings exist. Programs that run models add penalties for repetition, a cut called min-p and others. Each is another small function between the scores and the dice, like the one above.

In short

  • The model gives scores. How a character is drawn from them is ordinary code, and it changes the text a great deal.
  • Temperature divides the scores before the softmax. By hand, scores of 2, 1 and 0 gave the favourite 0.87 at 0.5, 0.67 at 1 and 0.51 at 2. At 0 our model loops; at 2 it writes noise.
  • Top-k keeps a fixed number of tokens. Top-p keeps as many as it takes to reach a share of the probability.
  • The KV cache stores the keys and values of tokens already read, so each new token costs one row of comparisons. Over a full window of 64: 2,080 comparisons instead of 45,760.
  • Past the context window, the oldest text is dropped. The model has no other memory.

Check yourself

Three tokens have probabilities 0.5, 0.3 and 0.2. What does top-p = 0.7 keep, and with what probabilities?

0.5 alone is under 0.7; 0.5 + 0.3 = 0.8 reaches it. The first two are kept and rescaled by their total: 0.5 / 0.8 = 0.625 and 0.3 / 0.8 = 0.375.

Temperature 1 with top-k set to 1. What do you get?

Greedy decoding, the same as temperature 0. Only the favourite survives the cut, so it gets probability 1 whatever the temperature.

How many numbers does the KV cache of our model hold when the window is full?

A key and a value of 96 numbers, for each of 64 positions, in each of 3 layers: 2 × 96 × 64 × 3 = 36,864 numbers. The same sum for a large model and a long conversation reaches gigabytes, as chapter 9 shows.

Why would the cache be wrong without the causal mask?

If earlier positions could read later ones, adding a token would change what every earlier position computes, and their stored keys and values would be out of date. The mask is what makes the past fixed.
