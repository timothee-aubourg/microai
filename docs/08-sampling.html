Chapter 8

Rolling the dice

The trained model outputs 65 probabilities. Why not simply pick the most likely character every time?

Try it and you get a model stuck in a rut. The single most likely continuation of common text is more common text, so always taking the favourite tends to circle through the same safe phrases. The opposite policy, sampling exactly according to the probabilities, has its own flaw: the model gives a little probability to many poor options, and over hundreds of draws one of them will be picked and derail the passage.

Good text lives between these two. The settings you see in every model interface, temperature, top-k and top-p, are three ways to reshape the probabilities before rolling the dice. None of them touches the model. They act on its output.

What the three knobs do

Temperature divides the model's raw scores by a number T before the softmax of chapter 5.

pi = softmax(scorei / T)

Recall that the softmax turns score differences into probability ratios. Dividing by T = 0.5 doubles every difference, so the favourite pulls further ahead. As T approaches 0 the favourite takes everything. T = 2 halves the differences and flattens the distribution toward uniform noise. T = 1 leaves the model's own probabilities untouched.

Top-k keeps the k most likely tokens and discards the rest. Simple, but blunt: sometimes only two options are sensible, sometimes fifty.

Top-p, also called nucleus sampling, adapts. It keeps the smallest set of tokens whose probabilities add up to p, say 0.9, and discards the long tail. When the model is sure, that set is one or two tokens. When it is unsure, the set is wide.

Generation is a loop, and the loop is wasteful

To write 200 characters the model runs 200 times, each time on the text so far plus one more character. Done naively, step 200 recomputes everything for the 199 characters already processed at step 199. Almost all of that work is repeated.

The causal mask of chapter 5 makes the waste avoidable. An earlier position never looks at later ones, so nothing computed for it can change when the text grows. In particular its attention keys and values are fixed forever. Store them. Then a new token only has to compute its own query, compare it with the stored keys, and add its own key and value to the store. This is the KV cache, and every runtime uses it.

Work per token, with and without the cache

Try this. Each small square is one query-key comparison in one attention head. Drag the slider to generate more tokens and compare how much is computed at this step (blue) on each side.

Without the cache, the comparisons per new token grow with the square of the length and their total with its cube. With it, each token costs one row. Measured on our model with code/ch08_sample.py, processing the same 60 characters and getting the same outputs to within rounding: 89 milliseconds recomputing everything, 33 with the cache. The gap is modest because the model is tiny and its window short; it widens quickly with both.

The cache explains two things you will notice when running a real model in chapter 10. First, memory use grows with the length of the conversation: the cache stores a key and a value per token, per layer. Second, runtimes report two speeds. Reading your prompt is fast per token, because all positions can be processed in one parallel pass. Writing the reply is slower per token, because each one must wait for the one before.

When the window is full

Our model has 64 position rows and cannot see further back than that. The generation loop in this repository handles a full window in the bluntest way: it keeps the most recent half of the text, rebuilds the cache from it, and carries on. Real runtimes offer the same choice in more refined forms: stop, or drop the oldest part of the conversation and reprocess. Either way, what falls out of the window is gone. The model has no other memory. Chapter 11 is about living with that.

Build it

def sample_next(logits, temperature=1.0, top_k=0, top_p=1.0, rng=np.random.default_rng()):
    if temperature == 0:
        return int(np.argmax(logits))                 # greedy: always the favourite
    z = logits / temperature                          # <1 sharpens, >1 flattens
    if top_k:
        z = np.where(z < np.sort(z)[-top_k], -np.inf, z)   # keep the k best
    p = np.exp(z - z.max()); p /= p.sum()             # softmax
    if top_p < 1.0:                                   # nucleus: smallest set worth top_p
        order = np.argsort(-p)
        before = np.cumsum(p[order]) - p[order]       # probability mass ranked ahead of each token
        p[order[before >= top_p]] = 0
        p /= p.sum()
    return int(rng.choice(len(p), p=p))

def step(self, token, cache):
    """Process ONE new token. `cache` holds the keys and values of all earlier tokens."""
    w, H, hd = self.w, self.H, self.d // self.H
    pos = cache['pos']
    x = w['wte'][token] + w['wpe'][pos]
    for i in range(self.L):
        a = self.ln(x, w[f'h{i}.ln1.g'], w[f'h{i}.ln1.b'])
        q = (a @ w[f'h{i}.attn.wq']).reshape(H, hd)            # only the NEW token asks a question
        cache['k'][i].append((a @ w[f'h{i}.attn.wk']).reshape(H, hd))
        cache['v'][i].append((a @ w[f'h{i}.attn.wv']).reshape(H, hd))
        K = np.stack(cache['k'][i], axis=1)                    # (H, pos+1, hd): old keys are reused
        Vv = np.stack(cache['v'][i], axis=1)
        s = np.einsum('hd,htd->ht', q, K) / np.sqrt(hd)        # one row of scores, not a T x T table
        s = np.exp(s - s.max(-1, keepdims=True)); s /= s.sum(-1, keepdims=True)
        x = x + np.einsum('ht,htd->hd', s, Vv).reshape(self.d) @ w[f'h{i}.attn.wo']
        h = self.ln(x, w[f'h{i}.ln2.g'], w[f'h{i}.ln2.b']) @ w[f'h{i}.mlp.w1']
        h = 0.5 * h * (1 + np.tanh(np.sqrt(2 / np.pi) * (h + 0.044715 * h * h * h)))
        x = x + h @ w[f'h{i}.mlp.w2']
    cache['pos'] += 1
    return self.ln(x, w['ln_f.g'], w['ln_f.b']) @ w['wte'].T

One new token through the model, reusing the keys and values of all earlier ones.

def generate(self, prompt, n, on_token=None, **sampling):
    ids = [self.stoi[c] for c in prompt]
    cache = self.new_cache()
    for t in ids[-self.block:]:                    # "prompt processing": fill the cache
        logits = self.step(t, cache)
    for _ in range(n):
        nxt = sample_next(logits, **sampling)      # draw one token...
        ids.append(nxt)
        if on_token:
            on_token(self.chars[nxt])
        if cache['pos'] == self.block:             # context window full: keep the recent half
            cache = self.new_cache()
            for t in ids[-self.block // 2:-1]:
                self.step(t, cache)
        logits = self.step(nxt, cache)             # ...and feed it back in
    return ''.join(self.chars[i] for i in ids)

What this chapter glossed over

There is no best setting. Low temperature suits tasks with one right answer, such as extracting a date. Higher temperature suits tasks where variety is the point. Defaults around 0.7 to 1.0 with a top-p near 0.9 are conventions, not laws.

Same prompt, different answers. Sampling is random by design. Fixing the random seed makes a run repeatable on the same machine and software. Temperature 0 removes the dice, though tiny numerical differences between machines can still change a close call.

More samplers exist. Runtimes add repetition penalties, min-p and others. Each is another small function between the scores and the dice, like the one above.

Check yourself

Temperature 1 with top-k set to 1. What do you get?

Greedy decoding. Only the favourite survives the cut, so it gets probability 1 whatever the temperature.

How many numbers does the KV cache of our model hold when the window is full?

A key and a value of 96 numbers, for each of 64 positions, in each of 3 layers: 2 × 96 × 64 × 3 = 36,864 numbers. The same sum for a large model and a long conversation reaches gigabytes, as chapter 9 shows.

Why would the cache be wrong without the causal mask?

If earlier positions could attend to later ones, appending a token would change what every earlier position computes, and their stored keys and values would be stale. The mask is what makes the past immutable.
