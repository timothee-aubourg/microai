Chapter 2

Cutting text into tokens

Why don't language models read letters? And why not whole words?

In chapter 1 the model read and wrote single characters. That was a choice, and not the one real models make. Before a model can do anything with text, the text has to be cut into pieces, and each piece replaced by a number, because a model computes with numbers and nothing else. How you cut matters more than it seems: it decides how much text fits in the model's view, what the model has to waste effort on, and whether it can read a word it has never met. This chapter compares the options and then builds the one every modern model uses.

What the model actually sees

Definitions

A token is one of the pieces the text is cut into. Depending on the method, a token can be a single character, a whole word, or something in between.

The vocabulary is the fixed list of every token the model knows. A token's position in that list is its token ID. The model reads and writes token IDs; it predicts the next token exactly the way chapter 1 predicted the next character, with one probability per entry in the vocabulary.

The program that turns text into token IDs (encoding) and back (decoding) is the tokenizer.

So the question of this chapter is: what should the vocabulary contain? There are two obvious answers, and both fail in instructive ways.

Option one: characters

This is what chapter 1 did. The vocabulary is tiny (65 entries for our Shakespeare text) and nothing is ever unknown: any English text is a sequence of those characters. The costs come from how long the sequences become.

  • Less text fits in view. A model can only look at a limited number of tokens at once. With characters, 4,000 tokens are 4,000 characters: about a page. With pieces of four characters on average, the same 4,000 tokens hold four pages.
  • More work per sentence. Every token costs one step of computation. Writing a 1,000-word essay one character at a time takes about 5,500 steps instead of roughly 1,300.
  • Effort wasted on spelling. A character model has to learn that t, h, e together make a common word before it can learn anything about how that word is used. Part of what it can learn goes on spelling.
Definitions

The context window is the maximum number of tokens a model can look at in one go. Anything older falls out of view. Model descriptions quote it in tokens: 8,000, 128,000, a million.

A model's capacity is how much it can learn, roughly set by its number of parameters (chapter 1). Capacity spent on one thing, such as spelling, is not available for anything else.

Option two: whole words

Then make every word a token. Sequences become short, and the model never has to spell. Try it on our text: the training part of the Shakespeare file contains 183,746 words, of which 13,706 are different. That is the vocabulary.

Now read the held-out part with it. 6.6% of the words, one in fifteen, are not in the vocabulary: names such as Licio, Cambio and Vincentio, but also ordinary words such as affability, sciences, languages, packet and pupils. A word-level model has no token for any of them. All it can do is replace each one with a catch-all "unknown" token, and it cannot write them either.

Definition

An out-of-vocabulary word is a word that is not in a fixed word list. However large the list, new names, typos, technical terms, code and other languages keep producing them.

There is a quieter problem too, the one from chapter 1. Half the words in the vocabulary (6,544 of 13,706) appear exactly once in the training text, so the model sees them too seldom to learn anything about them. And each word is a separate entry with no visible relation to any other: the model has no way to see that science and sciences, or speak and speaking, share most of their letters and most of their meaning.

The idea: keep the pieces that recur

The solution used by essentially every modern language model is a compromise. Common words become one token. Rare words are built from smaller pieces that do recur: sciences can be science + s, and an unknown name can be spelled one letter at a time. The surprising part is that nobody designs these pieces. A very simple procedure finds them in the data, starting from the smallest pieces there are.

Starting point: bytes

To make sure that any text can be encoded, in any language and with any symbol, tokenizers start not from letters but from bytes, the units computers store everything in.

Definitions

A byte is a whole number from 0 to 255. Every file on a computer, including every text, is a sequence of bytes.

UTF-8 is the standard rule for writing text as bytes. Plain English letters, digits and punctuation take one byte each. Other characters take two, three or four.

Refresher: hexadecimal, or why bytes look like "c3"

Hexadecimal is counting in base 16 instead of base 10. It needs sixteen digits, so after 0–9 it uses a–f for ten to fifteen. Two hexadecimal digits cover exactly one byte: the first digit counts sixteens, the second counts ones.

So 41 is 4 × 16 + 1 = 65, the byte for A. c3 is 12 × 16 + 3 = 195. ff is 15 × 16 + 15 = 255, the largest byte. Programmers use hexadecimal for bytes because every byte is then exactly two characters wide.

A tokenizer that starts from the 256 possible bytes has a vocabulary of 256 and can encode anything at all, with nothing ever out of vocabulary. It also has all the problems of option one, and worse: sequences at least as long as character sequences. The next step fixes that.

Glue the most common pair, repeat

Here is the whole algorithm:

  1. Write the training text as bytes. Each byte is a token.
  2. Count every pair of neighbouring tokens.
  3. Take the most frequent pair and give it a new token number. Replace every occurrence of the pair by the new token.
  4. Go back to step 2. Stop after a chosen number of rounds.

Each round adds one entry to the vocabulary and makes the text shorter. Rather than describe it further, watch it run on the sentence from chapter 1.

What you should have seen. The first merge is a + t, the most frequent pair (in cat, sat and mat). Then t + h, then th + e: the word the is discovered in three merges without the algorithm knowing what a word is. After five merges the 22 bytes have become 11 tokens. Then something changes: from step 6 the best pair occurs only once. Merging a pair seen once is memorising the text, exactly the trap of chapter 1. On real text with millions of characters the counts stay high for many thousands of rounds, and you stop well before this happens.

Definitions

This procedure is called byte-pair encoding, or BPE. Each round produces a merge: a rule "token A followed by token B becomes token C". A trained tokenizer is the ordered list of merges, together with the 256 bytes it started from.

What you should have seen. The first merges are the commonest pairs in English: e␣ (an e ending a word), th, t␣ and s␣. By merge 19, the whole word the␣ has its own token. At 300 merges the example sentence needs 23 tokens instead of 45, about two characters per token: the curve under the slider falls steeply at first, then flattens, because each new merge applies to rarer and rarer pairs. Real tokenizers, with tens of thousands of merges learned on far more text, reach about four characters per token. Words Shakespeare never used still encode; they just fall back to smaller pieces. An emoji, never seen at all, falls back to its four single bytes, shown as x followed by the byte in hexadecimal.

Encoding new text

Once the merges are learned, encoding any new text is mechanical: write it as bytes, then apply the merges in the order they were learned, each to the whole sequence. Here is the word the hat, which never appeared in our toy sentence, encoded with the five merges learned above:

Three tokens: the␣, h, at. The tokenizer has never seen hat, but it can still encode it from pieces it knows. Decoding goes the other way: replace each token by its bytes and glue them together.

The trade

Every merge shortens the sequences and lengthens the vocabulary. Both have a price. Longer sequences mean more computation per sentence and less text in the context window. A larger vocabulary means a larger table of token vectors (chapter 4), a larger final layer that has to score every token, and rarer tokens that the model sees too seldom to learn well.

Models you can download settle on vocabularies from a few tens of thousands to a few hundred thousand tokens. GPT-2 used 50,257: 256 bytes, 50,000 merges and one special token. For ordinary English prose such tokenizers average roughly four characters, or three quarters of a word, per token. That ratio is the conversion rate behind every context-window size and every tokens-per-second figure you will read.

Tokens that are not text

A vocabulary also contains a handful of entries that correspond to no text at all. They are added by hand, not found by merging, and they let the model see the structure of a document.

Definition

A special token is a vocabulary entry that stands for a signal rather than for text: "a document starts here", "this speaker has finished". It is printed with a name such as <|im_end|>, but to the model it is a single token ID, not a sequence of characters.

Build it

The whole tokenizer fits in four short functions. merge does one replacement pass over a list of token IDs. train_bpe is the loop from this chapter: count the pairs, take the most frequent, give it the next free number (256, 257, …), replace it everywhere. encode replays the learned merges in order on new text, as in the the hat table. decode rebuilds each token's bytes and turns them back into text.

def merge(ids, pair, new_id):
    """Replace every occurrence of `pair` in ids with `new_id`."""
    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i + 1]) == pair:
            out.append(new_id); i += 2
        else:
            out.append(ids[i]); i += 1
    return out

def train_bpe(text, n_merges):
    ids = list(text.encode('utf-8'))            # start: one token per byte
    merges = {}                                 # (a, b) -> new token id, in learned order
    for k in range(n_merges):
        pairs = Counter(zip(ids, ids[1:]))      # count adjacent pairs
        if not pairs:
            break
        best = max(pairs, key=pairs.get)        # the most frequent pair...
        merges[best] = 256 + k                  # ...becomes a new token
        ids = merge(ids, best, 256 + k)
    return merges

def encode(text, merges):
    ids = list(text.encode('utf-8'))
    for pair, new_id in merges.items():         # replay the merges in the order learned
        ids = merge(ids, pair, new_id)
    return ids

def decode(ids, merges):
    vocab = {i: bytes([i]) for i in range(256)}
    for (a, b), new_id in merges.items():
        vocab[new_id] = vocab[a] + vocab[b]
    return b''.join(vocab[i] for i in ids).decode('utf-8', errors='replace')

For the rest of this course the small model keeps using characters, 65 of them. That keeps it small enough to run in your browser, and nothing else about it changes: swap the 65 characters for 100,000 tokens and every later chapter reads the same.

In short

  • A model reads and writes token IDs: positions in a fixed vocabulary. The tokenizer converts between text and IDs.
  • Characters never fail but make sequences long, so less fits in the context window. Whole words make sequences short but leave out-of-vocabulary words unreadable.
  • Byte-pair encoding starts from the 256 bytes, so anything can be encoded, then repeatedly merges the most frequent neighbouring pair. Frequent words end up as one token, rare ones as several.
  • English averages about four characters per token. Special tokens mark structure, such as the end of a chat turn.

What this chapter glossed over

Greedy is not optimal. BPE never reconsiders a merge. It finds a good vocabulary, not the best one, and production tokenizers add rules of their own, such as never merging across a space.

Tokens explain some odd failures. A model that sees strawberry as two or three opaque chunks has no direct view of its letters. Counting letters, reversing words and long arithmetic are harder for a language model than their difficulty for a person suggests, partly for this reason.

Tokenizers are not interchangeable. Each model ships with its own. The same sentence is a different number of tokens for different models, so token counts and speeds are only comparable within one model family.

Check yourself

Before any merge, how many tokens is the word "hello"? And "café"?

"hello" is five bytes, so five tokens. "café" is five as well: the é takes two bytes in UTF-8. Starting from bytes is what guarantees every string has an encoding.

A model has an 8,192-token context window. Roughly how many English words is that?

About 6,000, at three quarters of a word per token. For code or for other languages the ratio is usually worse.

Why not run a million merges and give every sentence its own token?

You would be back at the count table of chapter 1: a huge vocabulary of items each seen once, with nothing shared between them. Tokens are useful because they recur.
