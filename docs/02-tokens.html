Chapter 2

Cutting text into tokens

Why don't language models read letters? And why not whole words?

A model works on a sequence of symbols drawn from a fixed list, its vocabulary. Chapter 1 used characters. That choice has a cost you will feel later: the model has to spend its capacity on spelling, and a context window of 4,000 symbols holds only 4,000 characters, about a page.

Whole words fix that and break something else. The list of words is never finished. New names, typos, code, other languages: a word-level model meets things it has no symbol for, and can do nothing with them.

The solution used by essentially every modern language model sits in between. Common words become one symbol. Rare words are spelled out from smaller pieces. These pieces are called tokens, and the surprising part is that nobody designs them. A very simple greedy procedure finds them in the data.

Glue the most common pair, repeat

Start with the text as raw bytes, 256 possible symbols, so that any text at all can be represented. Count every pair of neighbouring symbols. Take the most frequent pair, and from now on treat it as one new symbol. Count again. Repeat a few hundred or a few hundred thousand times. This is byte-pair encoding, BPE.

Watch a tokenizer being born

Try this. Drag the slider from 0 upward and watch the sentence compress as pairs get glued. Then type a word Shakespeare never used, such as blockchain or 🤖. It still encodes: it just falls back to small pieces, down to single bytes (shown as x followed by a hexadecimal number).

The first merges are things like e␣ and th: the commonest letter pairs in English. A few hundred merges later whole words such as ␣the␣ have their own token. Nothing in the algorithm knows what a word is. Frequency alone discovers them.

The trade

Every merge shortens the sequence and lengthens the vocabulary. Both have a price. A longer sequence means more computation per sentence and less text fitting in the context window. A larger vocabulary means a larger table of token vectors (chapter 4) and rarer tokens that the model sees too seldom to learn well.

Models you can download settle on vocabularies from a few tens of thousands to a few hundred thousand tokens. GPT-2 used 50,257. For ordinary English prose such tokenizers average roughly four characters, or three quarters of a word, per token. That ratio is the conversion rate behind every context-window size and every tokens-per-second figure you will ever read.

Tokens that are not text

A vocabulary also contains a handful of special tokens that correspond to no text at all: one for "the document starts here", one for "this speaker has finished". They look like <|im_end|> when printed, but to the model each is a single symbol. In chapter 10 these turn a plain text predictor into a chat.

Build it

def merge(ids, pair, new_id):
    """Replace every occurrence of `pair` in ids with `new_id`."""
    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i + 1]) == pair:
            out.append(new_id); i += 2
        else:
            out.append(ids[i]); i += 1
    return out

def train_bpe(text, n_merges):
    ids = list(text.encode('utf-8'))            # start: one token per byte
    merges = {}                                 # (a, b) -> new token id, in learned order
    for k in range(n_merges):
        pairs = Counter(zip(ids, ids[1:]))      # count adjacent pairs
        if not pairs:
            break
        best = max(pairs, key=pairs.get)        # the most frequent pair...
        merges[best] = 256 + k                  # ...becomes a new token
        ids = merge(ids, best, 256 + k)
    return merges

def encode(text, merges):
    ids = list(text.encode('utf-8'))
    for pair, new_id in merges.items():         # replay the merges in the order learned
        ids = merge(ids, pair, new_id)
    return ids

def decode(ids, merges):
    vocab = {i: bytes([i]) for i in range(256)}
    for (a, b), new_id in merges.items():
        vocab[new_id] = vocab[a] + vocab[b]
    return b''.join(vocab[i] for i in ids).decode('utf-8', errors='replace')

For the rest of this course the small model keeps using characters, 65 of them. That keeps it small enough to run in your browser, and nothing else about it changes: swap the 65 characters for 100,000 tokens and every later chapter reads the same.

What this chapter glossed over

Greedy is not optimal. BPE never reconsiders a merge. It finds a good vocabulary, not the best one, and production tokenizers add rules of their own, such as never merging across a space.

Tokens explain some odd failures. A model that sees strawberry as two or three opaque chunks has no direct view of its letters. Counting letters, reversing words and long arithmetic are harder for a language model than their difficulty for a person suggests, partly for this reason.

Tokenizers are not interchangeable. Each model ships with its own. The same sentence is a different number of tokens for different models, so token counts and speeds are only comparable within one model family.

Check yourself

Before any merge, how many tokens is the word "hello"? And "café"?

"hello" is five bytes, so five tokens. "café" is five as well: the é takes two bytes in UTF-8. Starting from bytes is what guarantees every string has an encoding.

A model has an 8,192-token context window. Roughly how many English words is that?

About 6,000, at three quarters of a word per token. For code or for other languages the ratio is usually worse.

Why not run a million merges and give every sentence its own token?

You would be back at the count table of chapter 1: a huge vocabulary of items each seen once, with nothing shared between them. Tokens are useful because they recur.
