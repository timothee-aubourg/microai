Chapter 40

When a step fails

A tool call fails half-way through a job. Should the agent stop, try again, or be told what went wrong?

Tools fail. A network times out, a service is busy, a file is locked. In a job of several steps, one failure ruins the whole job unless something handles it. Two things can: the harness, which is code, and the model, which can read an error the way it reads a result.

Definitions

A transient error is a failure that goes away if you try again: the service was busy, the connection dropped.

A loop guard is a rule in the harness that stops an agent repeating itself, for example when it sends the same call several times in a row.

An action is idempotent when doing it twice has the same effect as doing it once. Reading a file is. Appending a line to it is not.

A rollback undoes the effects of a job that failed part-way, so that nothing is left half done.

By hand: how often a job survives

The agent of chapter 39 answers chains like what is 23 times 45 minus 17?, one call per link. Make its calculator fail one call in five, at random. A chain of two links needs two calls to succeed: 0.8 × 0.8 = 0.64. Three links: 0.8³ ≈ 0.51. So if the harness stops at the first error, between a third and a half of the jobs are lost to a tool that works 80% of the time.

Now let the harness try a failed call again, up to three times in all. A call is lost only if all three tries fail: 0.2³ = 0.008. A chain of three links then survives with probability (1 − 0.008)³ ≈ 0.98.

200 questions, a tool that fails one call in five

code/ch40_recover.py asks 200 chains of two and three links, with number pairs the agent never saw in training. With a reliable tool, it gets 199 right. Then the tool fails each call with probability 0.2, and the harness handles failures in one of four ways.

def tool_for(way, rng, fail=0.2):
    """What the harness does when the model sends a call, for each way of handling a failure."""
    def call(name, a, b):
        tries = 3 if way == 'retry quietly' else 1
        for _ in range(tries):
            if rng.random() >= fail:
                return str(w.TOOLS[name](a, b))               # the call worked
        if way == 'stop':
            raise GiveUp()                                    # the whole question fails
        if way == 'retry quietly':
            raise GiveUp()                                    # three failures in a row: give up too
        return w.BUSY if way == 'tell, clearly' else 'failed' # the model reads the error and decides
    return call

When the tool is down for good

A busy tool comes back. A broken one does not. Make every call fail and keep telling the model R error busy. It was trained to try again after that error, so it tries again, and again. Something has to stop it.

def guarded(call, repeats=3):
    """A loop guard: stop when the model sends the same call `repeats` times in a row."""
    last = []
    def wrapped(name, a, b):
        last.append((name, a, b))
        if len(last) >= repeats and len(set(last[-repeats:])) == 1:
            raise GiveUp()                                    # it is going round in circles
        return call(name, a, b)
    return wrapped

Our agent never reaches the limit of 8 calls. Its window fills after at most 5, and the harness stops when there is no room left, so "nothing" and "a limit of 8" give the same result here. A large model's window holds hundreds of thousands of tokens, so without a limit it would keep trying for a long time, and pay for every pass. The loop guard stopped ours after 3 calls every time, as soon as the pattern was clear.

Half a job

So far a failed job just gave no answer. Many real steps also change something: a file written, a row added, a message sent. Give each step of our job an effect: it writes its result to a ledger. If a step fails, the job stops. What is left in the ledger?

def job_with_ledger(run, nums, ops, values, rng, fail, mode):
    """Each step of the job writes its result to a ledger. Returns what the ledger holds afterwards.
    'as you go' writes at once; 'at the end' keeps the writes aside and adds them only if the job finished;
    'undo' writes at once and removes its own writes if the job fails."""
    ledger, pending = [], []
    def call(name, a, b):
        if rng.random() < fail:
            raise GiveUp()                                    # this step fails, and so does the job
        r = w.TOOLS[name](a, b)
        (ledger if mode != 'at the end' else pending).append(r)
        return str(r)
    start = len(ledger)
    try:
        got, _, _ = w.run_steps(run, w.prompt_for(nums, ops), on_result=call)
        ok = got == values[-1]
    except GiveUp:
        ok = False
    if mode == 'at the end' and ok:
        ledger += pending                                     # commit: all or nothing
    if mode == 'undo' and not ok:
        del ledger[start:]                                    # roll back what this job wrote
    return ledger, ok

Each step now fails one time in ten, so 157 of the 200 jobs finished. When each step wrote at once, 20 of the 43 failed jobs left writes behind: half a job, in a ledger that now looks as though work was done. The other 23 failed before writing anything. Writing only at the end, all or nothing, or undoing the writes of a failed job, left none. "At the end" means nothing is visible until the job is done. "Undo" means every step needs an inverse, and some actions, such as a sent message, have none.

At full size

  • Retries wait. A real harness waits before trying again, longer each time (one second, two, four), so that a busy service gets room to recover. This is called backoff.
  • Only idempotent calls are retried blindly. Reading again is safe. Paying again is not. Services that take payments accept a key with each request, so that the same request sent twice is carried out once.
  • Error messages are written for the model. An error that says what went wrong and what to do ("file not found: did you mean src/app.py?") lets the model recover. "Error" alone does not. The difference between our clear and vague errors is the small version of this.
  • Harnesses cap the loop. A maximum number of turns per task, and limits on time and cost, are standard settings. Some also notice when the same tool is called with the same arguments again and again.
  • Rollback uses what is already there. Coding agents keep the files in version control, so a bad change can be undone. Databases have transactions. A harness can also take a snapshot before a risky step, the checkpoint of chapter 39.

What this chapter glossed over

Failures here are independent coin flips. Real failures come in bursts: a service that is down stays down for a while, which is why retries wait.

Only one kind of error. The agent was trained on one error, "busy", whose answer is always to try again. Errors that call for a different action, such as a wrong argument, need training or instructions of their own.

The ledger is a list in memory. Undoing real effects, such as a sent email, is often impossible, which is the case for asking first (chapter 43).

One run, no sampling, 200 questions per way.

In short

  • A tool that fails one call in five lost 42% of the jobs when the harness stopped at the first error: 115 right of the 199 it got with a reliable tool.
  • Three quiet retries in the harness brought it back to 194, without the model knowing. That is safe for idempotent calls only.
  • Telling the model, in the error wording it was trained on, gave 175, at the cost of passes and context. A wording it never saw gave 130. Error messages are part of the interface.
  • Something must stop an agent that keeps calling a dead tool: a step limit, the window, or a loop guard, which stopped ours after three calls.
  • A job that fails part-way leaves half its effects unless writes wait for the end or are undone: 20 half-done jobs against 0. That is rollback.

Act it out

Two people, slips of paper, a calculator, a die · about 10 minutes

Play three of the figure's ways, and then a dead tool, with the job what is 23 times 45 minus 17? and a tool that fails on a roll of 1.

  1. One of you is the model, who only writes calls on slips. The other is the harness, who holds the calculator and the die. For every try at the tool, the harness rolls: 1 means the tool is busy, anything else means it works.
  2. Stop, then retry quietly. In the first round the harness ends the job at the first 1. In the second it rolls again, up to three tries per call, and hands the model only the number.
  3. Tell. On a 1 the harness hands back a slip R error busy, and the model writes the same call again on a new slip. Count the model's slips in each round.
  4. A dead tool. Now every roll counts as a 1. The model keeps sending the call. The harness stops the job when the same call arrives for the third time in a row: the loop guard.

In the first two rounds the model never knew a call had failed: whether the job finished was decided by the harness's rule. Telling cost a slip and room in the context for every failure, and the dead tool's loop ended only because a rule in the harness stopped it.

Check yourself

A tool fails one call in ten. A job needs five calls. If the harness stops at the first error, how often does the job finish?

0.9⁵ ≈ 0.59, so about six jobs in ten. With three tries per call, each call fails with probability 0.001, and the job finishes about 99.5% of the time.

Why can a harness retry a read without asking, but not a payment?

A read is idempotent: doing it twice changes nothing. A payment made twice is two payments. Retrying it needs a key that lets the service recognise the second request as the same one.

The model was told "R failed" and did worse than when told "R error busy". Both mean the call did not work. Why the difference?

The model learned what to do after one wording, the one in its training. The other is new text, and it has no learned response to it. Error messages are part of the interface the model reads, like tool descriptions.

An agent keeps calling a broken tool. Name two ways the harness can stop it, and what each costs.

A limit on the number of calls: simple, but it may also stop a long job that was going well. A loop guard on repeated identical calls: it stops a stuck agent early, but an agent that varies its call a little gets past it.
