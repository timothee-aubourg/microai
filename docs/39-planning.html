Chapter 39

A plan, then the steps

A job takes four tool calls, and each needs the result of the one before. Should the model decide one call at a time, or write the whole plan first?

The agent of chapter 19 answers one sum with one tool call. Real jobs take several calls, and the result of one is often an input of the next: find the file, then read it, then change a line in it. This chapter trains an agent for jobs like that and compares the two shapes such an agent can take.

Definitions

Step by step: the model writes one call, the harness runs it and writes the result into the context, and the model writes the next call having read that result. It is the loop of chapter 15, sometimes called ReAct.

Plan first: the model writes every call at once, as a plan, before any of them runs. The harness then runs the plan without asking the model again. Later steps refer to earlier results by number.

A checkpoint is a saved record of the work done so far, from which a job can resume after a crash instead of starting again.

The new agent

Our jobs are chains of sums, worked from left to right like a pocket calculator: what is 23 times 45 minus 17? means (23 × 45) − 17. Each link needs a call, and every call after the first uses the result of the one before. code/ch39_plan.py trains a model of 161,728 weights from random numbers, for 8,000 steps (about 45 minutes on a laptop), on 40,000 conversations of three kinds: chains of one to four links done step by step, the same done with a plan, and conversations with notes, which chapter 42 uses. Some step-by-step conversations include a tool that answers error busy, which chapter 40 uses.

def chain(rng, links, test=False):
    """Numbers and operations for one question, and every value along the way, left to right."""
    while True:
        nums = [int(x) for x in rng.integers(100, size=links + 1)]
        if one.held_out(nums[0], nums[1]) != test:   # the first pair of a test question was never trained on
            continue
        ops = [list(WORDS)[k] for k in rng.integers(3, size=links)]
        values, v = [], nums[0]
        for op, n in zip(ops, nums[1:]):
            v = TOOLS[WORDS[op]](v, n)
            values.append(v)
        if all(abs(x) < 10000 for x in values):      # keep every result to four digits
            return nums, ops, values

def question(nums, ops, names=None):
    """The words of the question. With `names`, some numbers are replaced by the name of a note."""
    show = [names.get(i, str(n)) for i, n in enumerate(nums)] if names else [str(n) for n in nums]
    return 'what is ' + show[0] + ''.join(f' {op} {x}' for op, x in zip(ops, show[1:])) + '?'

def step_by_step(nums, ops, values, rng=None, busy=0.0):
    """The conversation, one call at a time: the model sees each result before the next call."""
    lines, left = [], nums[0]
    for op, n, v in zip(ops, nums[1:], values):
        call = f'C {WORDS[op]} {left} {n}'
        while rng is not None and rng.random() < busy:          # the tool is busy: the same call again
            lines += [call, f'R {BUSY}']
        lines += [call, f'R {v}']
        left = v
    return lines + [f'A {values[-1]}.']

def plan_first(nums, ops, values):
    """The conversation with a plan: every call at once, then only the final result."""
    steps = [f'{WORDS[ops[0]]} {nums[0]} {nums[1]}'] + [f'{WORDS[op]} ${i} {n}' for i, (op, n) in enumerate(zip(ops[1:], nums[2:]), 1)]
    return ['P ' + ', '.join(steps), f'R {values[-1]}', f'A {values[-1]}.']

By hand: one job, both ways

Step by step, the context grows by one call and one result per link:

U what is 23 times 45 minus 17?
C mul 23 45
R 1035
C sub 1035 17
R 1018
A 1018.

Plan first, the model writes one line and is done. $1 means "the result of step 1". The harness runs the steps and writes only the final result:

U what is 23 times 45 minus 17?
P mul 23 45, sub $1 17
                    (the harness runs it: 1035, then 1018)

Both give 1018. Step by step took three passes of the model, and by the end its context held 81 characters. Plan first took one pass and 56 characters. The plan is shorter because no result in the middle is written into the context for the model to read.

Measured, by length of job

200 questions for each length, from one to four links, with a first pair of numbers the model never saw in training. Both ways use the same model, chosen by the first letter the harness writes for it.

def run_steps(run, prompt, max_calls=8, on_result=None):
    """Step by step: the model writes a call, the harness runs it and writes the result, and again.
    Returns the final number (or None), the calls made, and how many characters the model read."""
    cache = run.new_cache()
    logits, calls = feed(run, cache, prompt), []
    while cache['pos'] < run.block - 24 and len(calls) < max_calls:
        role, logits = write_line(run, cache, logits, fmt=[['C ', 'A ']])
        if role == 'A ':
            text, _ = write_line(run, cache, logits)
            return number(text.rstrip('.\n')), calls, cache['pos']
        call, logits = write_line(run, cache, logits, fmt=CALL)
        name, a, b = call.split()
        result = on_result(name, int(a), int(b)) if on_result else tool(name, int(a), int(b))
        calls.append((call.strip(), result))
        logits = feed(run, cache, f'R {result}\n')                     # the result is now in the context
    return None, calls, cache['pos']
def run_plan(run, prompt, on_result=None):
    """Plan first: the model writes every call on one line, without seeing any result.
    The harness then runs the steps in order, putting each result where the plan says $1, $2 ..."""
    cache = run.new_cache()
    logits = feed(run, cache, prompt + 'P ')                           # the harness asks for a plan
    plan, results = [], []
    while True:
        step, logits = write_line(run, cache, logits, fmt=STEP)
        plan.append(step.rstrip(', \n'))
        if not step.endswith(', ') or len(plan) > 8:            # the line is over: the plan is complete
            break
    for step in plan:
        name, a, b = step.split()
        a = results[int(a[1:]) - 1] if a.startswith('$') and 0 < int(a[1:] or 0) <= len(results) else number(a)
        if a is None:
            return None, plan, cache['pos']                            # the plan points at a step that does not exist
        r = on_result(name, a, int(b)) if on_result else tool(name, a, int(b))
        results.append(number(r))
        if results[-1] is None:
            return None, plan, cache['pos']
    return results[-1], plan, cache['pos']                              # the model needs no second pass

  • Both ways are almost always right: 797 and 799 of 800. The agent learned both shapes equally well, so on these jobs the difference is cost, not accuracy.
  • Passes. Step by step needs one pass per link and one for the answer: five for a chain of four. Plan first always needs one. At full size each pass is a request to the model, with its wait and its price.
  • Reading. Each result goes into the context and is read again by every later pass (chapter 16). For four links, step by step ends at 131 characters and plan first at 93. The window is 160: a chain of five links, at about 28 characters per link, would need about 159 of them step by step.

Why long jobs fail more often

If each step is right with probability p, and the steps fail independently, a job of n steps is right with probability pn. At p = 0.98, ten steps give 0.82 and fifty give 0.36. Our agent's steps are right far more often than 0.98: only 3 of 800 step-by-step jobs failed, so length barely shows here. It shows in chapter 40, where the tool fails one call in five.

What a plan cannot do

A plan is written before any result exists. That is its strength and its limit. Our chains never need to look at a result to know the next step: the words say it all. Many real jobs do. "Find the test that fails and fix it" cannot be planned call by call, because what to read second depends on what the first search returned. Only the step-by-step loop can react to a result.

Real agents mix the two. They write a short plan, a list of steps in words, keep it in the context, and work through it step by step, crossing steps off and rewriting the rest when a result changes the picture. That is re-planning. Our model was not trained to do it, so it is described here, not measured.

Long jobs, and crashes

A job of hours can be interrupted: the machine restarts, the session times out, a process is killed. Make a job of 20 questions in a row, and before each one let the process crash with a small probability. Without a checkpoint the job starts again from the first question. With one, the answers so far are saved and the job resumes where it stopped.

def long_job(run, questions, crash, rng, checkpoint):
    """A job of many questions in a row. Before each one the process may crash (probability `crash`).
    Without a checkpoint the job starts again from the first question; with one, from where it stopped."""
    done, passes, restarts = [], 0, 0                                  # `done` is what a checkpoint would save
    while len(done) < len(questions):
        if rng.random() < crash:
            restarts += 1
            if not checkpoint:
                done = []                                              # everything since the start is lost
            continue
        nums, ops, values = questions[len(done)]
        got, calls, _ = run_steps(run, prompt_for(nums, ops))
        passes += len(calls) + 1
        done.append(got == values[-1])
    return sum(done), passes, restarts

What you should have seen. For one link, step by step reads 48 characters in two passes and plan first 35 in one. The plan line uses $1, $2 … for the result of the step before. Both columns are right almost every time.

At full size

  • The step-by-step loop is the default. Coding agents call the model again after every tool result, because their tasks need to react to what they find.
  • Plans live in the context as text. A coding agent can keep a to-do list, write it at the start of a large task, and tick items off. The list keeps a long job on course and shows the person what is happening. Unlike our plan, it is a guide for the model, not a program for the harness.
  • Plan-then-execute is a workflow. When the steps are known in advance, writing them once and running them in code saves passes and context. Chapter 41 compares these choices.
  • Long jobs checkpoint to files. Agents that work for hours write their progress to disk: notes, a to-do file, commits in version control. A new session reads them and continues, which is also how they survive the compaction of chapter 16.

What this chapter glossed over

Our plans are easy. Every chain says its steps in order, and every step after the first uses the result just before it. Real plans branch, and steps can use any earlier result, or none.

The harness chooses the shape. It writes the first letter, C or P. A real agent decides for itself whether to plan.

Crashes are coin flips before each question, and a crash costs nothing but the lost work.

One run, no sampling, 200 questions per length.

In short

  • Step by step, the model reads each result before the next call. Plan first, it writes every call at once and code runs them.
  • On chains of one to four links both ways were right 797 and 799 times in 800. For four links the plan took one pass instead of five, and 93 characters of context instead of 131.
  • A plan cannot react to a result it has not seen. Jobs whose next step depends on what came back need the loop, or re-planning.
  • Errors multiply over a long job: a step right with probability p gives a job of n steps right with probability pn.
  • A checkpoint makes a crash cost a restart, not the work so far: 55 passes against 164 at one crash in ten questions.

Check yourself

Step by step, a job of three links takes how many passes of the model? And plan first?

Four step by step: one per call and one for the answer. One plan first: the model writes the plan and the harness does the rest.

Each step of a job is right with probability 0.95. How likely is a job of five steps to be right?

0.95⁵ ≈ 0.77, if the steps fail independently. Long jobs need steps that are much more reliable than they look one at a time.

"Search the documentation, then answer from what you find." Can this be written as a plan before the first step?

Only the first step. What to read next and what to answer depend on what the search returns. The rest has to be decided step by step, or re-planned after the search.

A job of 20 steps crashes at step 15. What does a checkpoint save, and what does it need to record?

It saves redoing steps 1 to 14. It needs to record enough to resume: which steps are done and their results, written somewhere that survives the crash.
